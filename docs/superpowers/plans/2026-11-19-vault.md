# Vault Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Everything secret and personal Unichat keeps goes to the person's cloud encrypted, in one vault opened by a recovery code, a password, a computer's own key, Google or a passkey; it can be turned off.

**Architecture:** A random vault key (VK) encrypts every file with AES-256-GCM; each way in is a slot file holding VK wrapped with that way's key. `SealedStorage` is a `Storage` that encrypts what goes in and decrypts what comes out, under `Unichat/Bóveda/`, so `SyncedPart` and `TextSync` run over it unchanged. `Cloud` picks plain storage (no vault), sealed storage (vault open here) or nothing personal (vault locked here).

**Tech Stack:** Java 25, JDK `javax.crypto` (AES-GCM, HMAC), Bouncy Castle `bcprov-jdk18on` (Argon2id only), Jackson, JavaFX 27, JUnit 5, the existing cloud fakes (`FakeDav`, `FakePCloud`, `FakeDropbox`).

**Spec:** `docs/superpowers/specs/2026-11-19-vault-design.md`

## Global Constraints

- Build: `JAVA_HOME=/opt/homebrew/opt/openjdk@25 ./mvnw verify -Pheadless-ui`; Java files under 800 lines, methods under 100; `ArchitectureTest` (JavaFX only in `ui`, `ui` talks to `service`/`cloud` as today).
- Every user-facing text through `I18n` in `messages.properties` and `messages_es.properties`; the repo (code, docs, commits) in English.
- AES-256-GCM, 96-bit random nonce per write, associated data = `"unichat-vault/1:" + logical path`; VK and slot keys 256 bits from `SecureRandom`.
- Recovery code: 160 random bits as 8 groups of 4 Crockford base32 characters (`ABCD-EFGH-…`); its key = HKDF-SHA-256(code bytes, info `"unichat-vault recovery"`).
- Password key: Argon2id, 64 MiB, 3 iterations, parallelism 1, 16-byte salt (stored in the slot's `params`); minimum 12 characters.
- Never in the vault: `cloud.*` (except `cloud.dropboxAppKey`, `cloud.pcloudClientId`), `stt.command`, `stt.engine`, `autosave.*`, `ai.folder`, `window.*`, `app.update.*`, `matrix.*`, `session.*`, `server.*` (except `server.telegram.apiId`/`apiHash`), markers. Media never.
- Nothing secret (VK, slot keys, code, password, tokens) in a log, an exception message or a toast (`Redactor`).
- Tests never wait for time (`src/test/CLAUDE.md`); UI tests headless; every fix and feature with a test watched failing first.
- Each task ends with `./mvnw verify` green and a commit on `feat/vault`.

## Review Focus

- A wrong password or recovery code: says so, writes nothing, can be tried again at once (no lockout, no partial state). → Task 2 `wrongSecretsOpenNothing`, Task 9 `aWrongPasswordSaysSoAndChangesNothing`.
- The cloud failing in the middle of the move into the vault: a plain copy is deleted only after its sealed copy was read back and opened. → Task 7 `aPlainCopyGoesOnlyOnceItsSealedCopyReadsBack`.
- A vault in the account that this computer hasn't opened: not one plain byte of settings, AI, texts or secrets leaves it. → Task 6 `aLockedVaultSendsNothingPlain`.
- One computer changes the key while another runs: the other keeps reading and writing without being opened again. → Task 8 `anotherComputerGoesOnAfterTheKeyChanges`.
- A recovery code typed with spaces, lowercase, no dashes, or O/I/L for 0/1/1: it opens. → Task 2 `aCodeTypedLooselyStillOpens`.
