# tests — notes for Claude

Tests run in Spanish (`unichat.language=es` in the pom), with `unichat.dataDir`, `unichat.autosaveDir` and `unichat.silent` set by surefire: never the real data dir.

## Waiting
- Wait on a future with `get()`, never `join()`: `join()` can't be interrupted, so JUnit's timeout never ends it and a future that never completes hangs the build for good (two agents lost an hour to it; lesson `test-future-join`).
- Tests never wait for a length of time nor carry a timeout of their own: no `Thread.sleep`, no `await(5, SECONDS)`, `poll(200, MILLISECONDS)`, `join(5000)`, `waitFor(30, …)` or `get(30, …)` (`.claude/lessons.tsv` catches them). They wait on what the code actually does: a latch or future the code completes, a listener, `FxWait.until` / `FxWait.settled` on screen, the code's own `flush()`. JUnit's global timeout (`junit-platform.properties`) is the only limit.
- To check that something did *not* happen, first wait for the point where it would have (flush, settled, the call that would have caused it returned). If the code gives no way to know when it's done, change the code so it does (a listener, a returned future, a flush) rather than guess a time.
- A time the code under test takes as input is given as zero or as no limit (`Duration.ZERO` with a program that never ends shows the timeout path; `NO_LIMIT` when it ends by itself), never a guess of how long something takes. The one timed pause allowed is a profiler's sampling rate (`ScrollPerfUiTest`'s sampler): it measures, it doesn't wait.
- A flaky test is a bug, never tolerated nor retried away: find the race and fix it (usually a wait on time, or work still running when the test ends: wait for it).
- A wait for something that can fail waits for the failure too and says it, never runs to the limit.

## On the FX thread
- `FxWait.fx(() -> …)` for work with a result, `FxWait.onFx(() -> …)` for work without one: never `fx(() -> { …; return null; })`.

## Watching a test fail
- Code is broken on purpose (a mutation, to see a test fail without the fix) only in a throwaway worktree: `git worktree add <session scratchpad>/<name> HEAD`, copy the change over, break it there, run, then `git worktree remove`. Never in the person's working tree: an `if (Boolean.TRUE) return at;` left there by an agent nearly got committed.

## Build rules
- `BuildRulesTest` reads `pom.xml` and fails when a check that fails the build is turned off: javac's `-Xlint:all -Werror` (a `-Xlint:-name` needs its reason in a comment just before it), the Enforcer's rules, Modernizer at the project's Java, Error Prone (on javac's processor path with its two policy flags; only `-Xep:Name:ERROR` or `:OFF`, each `:OFF` named with its reason in the comment before the compiler plugin; the off-by-default checks that catch defects stay on; NullAway beside it, pinned, `-Xep:NullAway:ERROR` with exactly the options `NULLAWAY_OPTIONS` lists (`OnlyNullMarked`, `JSpecifyMode`, `HandleTestAssertionLibraries`: none that leaves a class out), JSpecify a pinned main dependency, and `NullMarkedTest`: every package under one in `NULL_MARKED` with a `package-info.java` whose package declaration is `@NullMarked`, none other, no class marked by itself outside them, and no `NullUnmarked` anywhere in `src`), PMD (`check` with `pmd-rules.xml` in verify, failing on every priority, tests included, nothing left out by path; every `<exclude>` in the rule set with its reason in a comment just before it), SpotBugs (`check` in verify, effort Max, threshold Low, tests included, FindSecBugs pinned among its plugins, `spotbugs-exclude.xml` the only filter, nothing that leaves code, detectors or findings out: `onlyAnalyze`, `omitVisitors`, a baseline; every `<Match>` there by bug pattern alone, never class, package, method or field, with its reason in a comment just before it; its one skip is a repeat of a run that passed, `app.unichat.build.SpotBugsCache` (hashes what SpotBugs reads, writes `spotbugs.skip` for properties-maven-plugin in a file named after the run, so a run whose check was skipped stops instead of reading an earlier one, marks the hash only after a pass; `SpotBugsCacheTest`), wired exactly so, with no `skip` or `quiet` on those two plugins), Checkstyle (`check` in validate on main and test code, `violationSeverity` warning, failing on a finding, no file left out; `checkstyle.xml` runs exactly the modules `CHECKSTYLE_MODULES` lists with exactly their options (FileLength 800, MethodLength 100 and its tokens, HiddenField's ignores, the catch and empty-catch names; naming at Checkstyle's defaults), so a module taken out or loosened (a wider format, an ignore, fewer tokens) fails, each at severity error, with no suppression filter but `SuppressWarningsFilter`; a check left out has its reason in a comment there), JaCoCo (`prepare-agent` in initialize on surefire's `@{argLine}`, `report` in test, `check` in verify halting on failure, all on this run's own exec file named after `maven.build.timestamp`, so `-DskipTests` skips them and no earlier run is read; the agent takes only `app.unichat.*`, no `<excludes>`; one LINE COVEREDRATIO rule per package with main code, its minimum the property `jacoco.floor.<package>`; those properties are exactly `FLOORS_PLAIN` and headless-ui's exactly `FLOORS_HEADLESS`, each a multiple of 0.05, headless-ui's above the plain one, 0 only for the two in `ZERO_IN_THE_PLAIN_BUILD`; a profile sets nothing but properties, and of those only `argLine` and floors), and any other `<skip>`. A new tool that fails the build gets its case there.
- `SuppressionsHaveReasonsTest` reads `src/main/java` and `src/test/java`: every `// NOPMD` says `: why` after it, every `@SuppressWarnings(...)` (qualified too) has a `// why` on the line where it closes (one spread over lines: on its last), none names `"PMD"`, `"all"`, `"checkstyle"` or `"checkstyle:all"` (every rule at once), one naming a Checkstyle check never sits on the file's top-level type, none names `MethodLength` or `FileLength` (a size limit is met by splitting, never suppressed), and every `@SuppressFBWarnings` a non-blank `justification` and a place on one member (a method, constructor or field), never a type. Comments, strings and text blocks are told apart from code, so a word in them counts for nothing.
- A pattern's speed is measured by what it reads, never by a clock: `app.unichat.CountedReads` is text that counts its `charAt` calls (`perChar()`): a linear pattern reads each char a few times, one that backtracks reads it as many times as the text is long (`FixPromptTest`, `WebDavTest`, `LoginsParsingTest`).
- A check that depends on the computer's language runs under `app.unichat.WithLocale` (Turkish case folding, Persian digits), which puts the JVM's locale back.

## Flags
Off by default, only the person runs them: `-Dunichat.networkTests=true` (real downloads and CLIs), `-Dunichat.chromeTests=true` (real Chrome, off screen), `-Dunichat.perfTests=true` (`ScrollPerfUiTest`, `EmojiScrollPerfUiTest`: the real display), `-Dunichat.realInputTests=true` (`MenuDismissUiTest`: the real mouse). `MatrixLiveIT` needs `UNICHAT_IT_HOMESERVER`.

## UI tests (`*UiTest`, `-Pheadless-ui`)
- They run with no display or windows: JavaFX's own headless platform (`-Dglass.platform=Headless`, since JavaFX 25; Monocle was never published past JavaFX 21). All of them run there. It proves logic, not focus, tray or Dock.
- Its virtual screen is a fixed 1000×1000 and a window drawn outside it (moved off-screen, or taller than the rest) throws on every frame, on the UI thread, into whatever test comes next: keep test windows on it, hidden with opacity 0, and close them when done.
- CI runs them on Linux (`build.yml`, ui-headless): a test mustn't assume the Mac. The shortcut key is Ctrl there (press Ctrl and ⌘ together), the fonts are taller (leave room before a size cap), and there's no sound card (PulseAudio's null sink).
- How the message list scrolls is checked frame by frame: `ui/TimelineWindow` (the window with `service/ScriptedChatService`, a demo where the test plays the others: messages arriving, typing, history to load) and its `watch(probe)`, which fails with every frame drawn wrong. Add a case there for any scroll complaint.
- `KeyboardUiTest` checks F6 zones, timeline keys, zoom and screen-reader texts; `FilterUiTest` that the rail keeps the chosen chip when switching network.

## Lessons
- A line taken out because its test still passed without it (run alone) was needed: `SendQueueView`'s `setMaxHeight(USE_PREF_SIZE)` kept the queue's list from being stretched, which only happened with other windows in the run, and the full run failed. Breaking a line to see its test fail proves the test; a test that passes without the line proves nothing about the line until the full run says so.
- `FxWait.until`'s condition runs on the FX thread: `settled()` (or another `until`) inside it waited for itself, and a whole UI test class hung to JUnit's limit, three minutes a test, without a word. A condition only looks (`SendQueueUiTest.rowsNow`); `FxWait` now throws `OnFxThread` at once (`FxWaitUiTest`).
- `Node.isFocused()` needs the window to have OS focus: F6 into the timeline only selected a message via the focused listener, so it silently failed when the window wasn't frontmost. Select explicitly (`focusTimeline()`), and never test through focus listeners.
- A fixed "now" next to code that reads the real clock (`FirefoxCookiesTest`: cookies valid one day after 2026-10-26) starts failing days later. Give fixtures a margin of years.
- Matrix media messages keep the name in `fileName`, not `body` (body = caption): match on both.
- Measure, don't guess: a click simulation (visible→hidden events, cache misses) found the second avatar flash; peak heap with real files (`-Xmx256m` and a folder of them) found the WebP OOM.
- `FxWait.settled` knows only what counts in `Redraws.PENDING`: a `Platform.runLater` the code queues to change the layout later (`Composer`'s stacking after a width change, `MainView.catchUp` when the window shows again) must count there, or a test measures the half-moved screen. `NotificationOpenUiTest` failed one run in three (on `main` too) until both did.
- A window or context menu left showing broke a later test on Linux only (the run order differs there): `ProfileMediaUiTest` took "the first menu showing" and fired another test's. `MenuItem.fire()` doesn't close its menu as a click does (`getParentPopup().hide()`), and `ui/LeftoverWindows` (a JUnit extension every test runs under, `META-INF/services`) now closes any window or menu a test opened and left showing (and says so on stderr: most UI tests leave their main window, so failing them was 41 edits for nothing). Look a menu or viewer up by its owner, never "the one showing". Closing a test's last window would end JavaFX (implicit exit) for every later test, and after that `Platform.runLater` drops tasks silently: a wait on one never ends, and JUnit's timeout doesn't cover extensions. So the extension turns implicit exit off before closing and only waits when the FX thread is alive.
- The whole run died of "Java heap space" (in `ArchitectureTest` or `SendablePhotosTest`, the victims) once 80 scroll tests each opened a `MainView`, ~10 MB kept per test. Measured, not guessed (used heap after a GC, live views through weak references, and what JavaFX's timer still ran): the focused message box's caret kept blinking in the closed window (the headless platform never takes the focus away), with the whole view held; `Theme` and the app's animations held closed windows too (fixed in the app, `ui/CLAUDE.md`). A test that builds a `MainView` disposes it and takes it out of its scene when done (`TimelineWindow.close`).
- Tests left their temp files in the system's temp folder for good: hundreds of folders (`unichat-library…`, `moving…`, `emoji-menu…`, JUnit's own) after a few runs (a few MB, more with every run). Surefire points `java.io.tmpdir` at `target/test-tmp` (`pom.xml`'s `argLine`: the JDK reads it once, at start, so a system property set later does nothing), and `app.unichat.TestTemp` (a JUnit extension for all, `META-INF/services`) empties it when the run starts and ends (`TestTempTest`). A test still cleans up what it makes; this catches what it doesn't.
- `TimelineReadingUiTest.theTextGetsBigger` failed now and then on CI's Linux ("the message read moved -9 px", the list itself not moved): the test measured the list's top and bottom from the flow's bounds, which reach a row cut above or below the viewport, so it watched another message than the one the list holds (and saw a gap of -2 where the list measured 0). A test measures as the code it checks does (`TimelineWindow.readMessage`, `belowViewport`: the viewport's own top and height). When a failure only happens on CI, first make it say what moved and from where (`stays` gives the list's own move and position).
- `VaultPageUiTest` waited for a line the page shows only until it draws itself again ("accepted", then the redraw at once): it passed alone and timed out in the full run, where the redraw came first. Wait for the state the step ends in (what's gone as well as what's there), never for a passing line.
- `PasskeyProbeRowUiTest` hung the run for hours with nothing said: it built a `Button` on JUnit's thread while the FX thread was setting up JavaFX's CSS classes, and both waited on each other's class initialization (`jcmd <pid> Thread.print`: "waiting on the Class initialization monitor"). Every node is built inside `FxWait.fx`, even one only checked for being there.
- `SpotBugsCache` marked any run that reached it as passed: `verify -Dspotbugs.skip=true` (SpotBugs never ran) was taken as a pass, and the plain verifies after it skipped SpotBugs on code it never read. The mark now needs this run's own report: its decision was to analyse, `target/spotbugsXml.xml` newer than this run's check, no `BugInstance` and `errors='0'` (`SpotBugsCacheTest.aRunWithSpotBugsSkippedByHandIsNeverMarked`, `aRunThatFoundBugsWithoutFailingIsNeverMarked`, `aReportFromAnEarlierRunIsNotThisRunsPass`; real Maven: a skip by hand, then a plain verify, analysed). A cache marks what was checked, never that the step ran.
- `FxCoalescerUiTest` held the FX thread on a latch (`Platform.runLater(() -> release.await())`, so requests pile up) and asserted before `release.countDown()`: one failed assertion (the shared `Redraws.PENDING` moved by another test's redraw) left the FX thread held, and `LeftoverWindows.afterEach` waited on it for good, 23 minutes with nothing said. A test that holds the FX thread lets it go in a `finally`, and asserts on what's its own (`FxCoalescer.queued()`), never on a count every test shares (`>=` at most). No per-line pattern sees the block, so no `lessons.tsv` row.
