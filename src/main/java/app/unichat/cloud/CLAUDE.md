# cloud — notes for Claude

The person's own storage account (pCloud, Icedrive, Nextcloud…).

- `Storage` is the account however it's reached: `WebDav` (Icedrive, any other), or `PCloudApi`, pCloud's own API (stat, createfolderifnotexists, uploadfile with nopartial, getfilelink; token in a Bearer header, never in an address), because pCloud's WebDAV refuses a login with two-step verification on (it just never answers: every question to a server waits at most `WebDav.ANSWER`). `PCloudLogin` signs in in the browser (OAuth 2 token flow): pCloud's page, then `http://localhost:43117/pcloud` (fixed: the address registered with the app), whose page passes the "#" part on to `/pcloud/done`; `state` ties the answer to the request; only `*.pcloud.com` hosts are trusted with the token. The app's Client ID: `PCloudLogin.CLIENT_ID` once Unichat's app is registered, or `cloud.pcloudClientId` from Ajustes → Nube. Tests: `FakePCloud`. `DropboxApi` (API v2, app-folder access: paths start in Dropbox/Apps/<app>): `DropboxLogin` signs in with OAuth 2 + PKCE (no secret in the app; Dropbox sends a code to `http://localhost:43117/dropbox`, exchanged with this sign-in's own verifier for a lasting refresh token, kept as the account's secret); each call carries a short-lived token made from it again when Dropbox answers 401; names go in the `Dropbox-API-Arg` header as ASCII-escaped JSON (accents, emoji); files over 150 MB go up in an upload session. App key: `DropboxLogin.APP_KEY`, or `cloud.dropboxAppKey` from Ajustes. Both browser sign-ins share `Loopback` (127.0.0.1, port 43117, state). Tests: `FakeDropbox`.

- Every request to a service goes through `Http.send` (no answer in time → `cloud.error.noAnswer`; interrupted → `IOException` keeping the interrupt).
- `WebDav` (PROPFIND/MKCOL/PUT/GET; `stamp` = ETag or date, so a round downloads only what changed), `CloudAccount` (service, address, login and secret: `cloud.` keys stay on this machine; `Unichat/Settings`, `Unichat/Media`; disconnecting also forgets the vault held or seen here, `VaultParts.gone`: another account has another vault), `Cloud` (one round a minute and one after anything's saved, on its own thread; `Status` for Ajustes → Nube, `ui/settings/CloudPage`).
- `SyncedPart`: one thing kept the same on every computer, as one file: three versions (here, the account's, the last agreed `cloud.base.<name>`); only one side changed → it goes to the other; both → the newer; a computer new to the account takes what's there. After adopting, the agreed hash is what this computer holds (agreeing on the account's own sent it back up forever). Two parts: the settings (`Bundle`: portable settings minus `panel.`, and `preferences.json` minus what only follows the server) and what the AI learned (`writing-style.md`; pending corrections stay here).
- Applied live, never a restart: settings through `Settings.replacePortable`, then `ui/settings/SyncedSettings` (what Ajustes does for the few read once: theme, AI buttons, global shortcut, Dock, notifications label, update check, language last); preferences through `ChatPreferences.adoptPreferences`. `SyncedSettingsUiTest` has a proof for every setting key in the source, and fails for a new one without.
- Media (`MediaUpload`): each chat's saved folder goes up until all of it is there: a file that fails waits its own turn again (1, 2, 4… up to 60 minutes, forever, `Retry`) without holding the others back. Each upload is checked against the account's copy (`Storage.info`: size, and a checksum where the service gives one: pCloud's SHA-1, Dropbox's content hash; WebDAV only the size; computed here by `Checksums`). Once a day and on "Verificar ahora" everything uploaded is checked and repaired, the bigger copy winning (`Checksums.decide`: damage cuts files short, so a file damaged here is restored from there and never damages it; same size and other content: neither is touched, the person is told). Done files in `cloud-uploaded.txt`; nothing there is ever deleted; hidden and ".part" files wait. A round reports each step (`Cloud.Activity`: settings, what the AI learned, uploading or checking file n of m) for Ajustes → Nube. While nobody can see Unichat (`support/Seen`) media waits (`MediaTurn`, the round's media step): `MediaUpload.run`/`verify` ask `mayGoOn` before each file (the file going finishes: stopping mid-file throws away what was sent), a check that falls due or is cut short stays due (`cloud.lastVerify` not written) and goes on from where it stopped (`MediaUpload.checked`, emptied by a whole check), a "Verificar ahora" pressed during a check gets one of its own (`MediaTurn.asked`: cleared only if no press came since the check began), and the round says so when something waits (files or a check due: `Status.mediaPaused`, also when the round fails, `cloud.media.pausedUnseen` in the tray and Nube); the settings, the AI's part, the texts and the vault go on. Seen again, `start`'s `Seen` listener queues one round on the `cloud` thread, coalesced lock-free with the timer's (`Cloud.queueRound`, `roundQueued`: it runs under `Seen`'s lock), never more than one behind a running round, however long (`CloudUnseenTest`). A check that fails still counts what went up before it (`MediaTurn.sent`).
- Not in the demo (its chats would reach the person's account), except for a snapshot of the page. Tests use `FakeDav` (an in-memory WebDAV on 127.0.0.1).
- What a round is doing reaches the person three ways, in the same words (`ui/settings/CloudTexts`): Ajustes → Nube's line and bar, the tray (lines at the top of its menu: what, how fast, the file and how far, how many left; and the icon's ring while files go up and nothing is being saved, `Notifier.setCloud`), and a ring over the settings gear (`Rail.setCloud`, drawn over it, never in the layout: the chat never moves; its tooltip has the lines; a click while files go up opens Nube). Only names of ours (a machine's UUID, `<key> <yyyy-MM>.jsonl`) become paths here. In every round before media, and alone on its own thread (`Cloud.textsNow`: after something new is kept, and before a deleted message is looked at), since a round may be sending a video for minutes. `TextSyncTest`, `StorageListing` (each service's `list`).

No computer runs a Unichat from before them (the person's ruling, 2026-11-23): nothing is kept for one. `CloudNames` holds both sets (`renamed`/`old` for logical paths, `oldStored`/`newStored` under the vault) and moves the old ones once, in place, on the server (`Storage.move`: WebDAV `MOVE` with `Overwrite: F`, Dropbox `move_v2`, pCloud `renamefolder`/`renamefile`, never over what's there; `StorageMoving`), at the start of each round's vault part (`CloudRenames.plain`, the texts under TextSync's lock) until it's done (`cloud.names.done`), then never again. A whole folder moves when the new one isn't there; else (a move cut short) entry by entry: a text keeps the longer, an index the larger size of each file, a part the newer `Bundle.savedAt` (`CloudNames.winner`), media what the new folder lacks. Then each old folder (`Ajustes`, `Textos`, `Multimedia`) is deleted whole once every file left in it is confirmed under its new name: media the same size, and checksum where the service gives one (WebDAV gives only the size); anything else what wins there. One that isn't keeps its folder, said in the log; a media file kept so is remembered with both copies' stamps (`cloud.names.kept`), and the old folder isn't walked again until one changes. The media check still runs: nothing is missing under the new name. A plain move that fails with a settings part still under `Ajustes` (or unlisted) holds back the plain settings and the AI's part that round (`CloudRenames.settingsWait`): its own copy would go up over it and win. Disconnecting forgets `cloud.names.done` (another account may have the old names). While the move fails, the round's media check waits (`MediaTurn.run`'s `check`): a file not yet under the new name would go up again. pCloud's `move` asks whether the target is there, then renames: one request apart, a name written in between would be replaced (pCloud has no rename that refuses). `CloudNamesTest`.
- The vault's own move (`VaultNames`, by a computer where it's open, under `vaultPart`, `keyLock` and TextSync's lock; its `Registro` goes with it): every sealed file copied to its new path sealed again under its new logical path (each write first checking the old names are still the vault's), the slots copied as they are (sealed without their path), then `vault.json` written (its being there is the mark; only if no other computer did, read back with this round's id and generation) and `Bóveda/boveda.json` deleted at once; then the slots again (where the new names have none, or one was written after its copy) and each old file deleted once its new place, read again, holds it. Copies, not moves, before the switch, so a computer reading the old names meanwhile finds everything. Until `vault.json` is there, everything reads the vault through `OldVault` (`VaultNames.at`: paths under `Vault.ROOT` reach the old ones, listings come back with new names, and `OldVault.aad` gives `SealedStorage` and `VaultReseal` the old logical path): rounds, `textsNow` (which reads it inside `keyLock`, so never across a move), `vaultAfter` and every job. A round's move cut short reads the account again (`CloudRenames.vault`): the old names while they're still the vault's, the new ones while they hold this round's key, else the personal parts wait for the next round. A job that writes the vault's keys or files (`Cloud.onWorker(job, true)`, `CloudVault.writing`: a change of key, remove-and-change, turning it off, a password, a new recovery code, opening it, removing a computer, forgetting it here) first moves the vault where it is still under the old names and open here, or, once they are switched, finishes the slots left there (`CloudRenames.forJob`: they need no key; the files are the rounds' to finish, so one old file that never reads stops no job), or is refused (`cloud.error.vaultRenameFirst`); one that opened it through a way in moves it after (`afterJob`). So an old slot never comes back over a way in changed or taken away since: a round's finish copies an old slot only where the new names have none or where it was written again within that same call. Every other job (the page's view, `codeKept`, `acceptKey`…) sees the vault where it is and never runs the move. A file that doesn't open with the key stays under its old name, told once and remembered with its stamp (`cloud.names.vaultLeft`): while those are all that's left, unchanged, `VaultNames.left` asks only their stamps, never walks the folder. A computer on a Unichat from before the move finds no `boveda.json` and no old mark: `MISSING`, nothing sent. ## The vault (opt-in, `Unichat/Vault`)
In short: one random 256-bit vault key (VK) seals (AES-256-GCM, `VaultCrypto`; the path is the associated data) what the person's computers share, and each way in (recovery code, password, a computer's own X25519 key) holds a copy of it in its own slot; the service sees only sealed bytes. States per computer: `NONE` (no vault: today's plain round), `LOCKED` (a vault this computer has no key for), `DECLINED` ("Seguir sin la bóveda en este equipo"), `OPEN`, `REMOVED` (its slot is gone, or a change it can verify left it out), `UNRECOGNIZED` (a change of key nothing it holds vouches for: its key kept, nothing sent), `MISSING` (the vault it holds is gone with no mark that it was turned off: nothing sent until the person says). What Ajustes → Nube → Bóveda asks of the vault is `Cloud.vault()` (`CloudVault`), one job each on the vault's thread (`cloud-vault`), never alongside a round's vault part and never waiting for its media (`Cloud.vaultPart`: a round holds it from reading the vault's state through the move in, and lets it go before media; each job holds it, then `keyLock`; locks always in the order `vaultPart`, `keyLock`, `vaultLock`, `TextSync`'s). The account is read once the job holds the lock (disconnected meanwhile: none). A state a job read is told at once (`Cloud.toldAsRead`: in one step over `Cloud.status`, an `AtomicReference`, so a round's end told meanwhile is never written over with its middle; another state drops the notice, `Status.vault`), each progress tick says the state last read (`Cloud.vaultKnown`, never the one the round began with), and a job run during media has the round read the vault's state again before telling it (`Cloud.vaultAfter`; that failing, the state last read). `CloudVaultJobsTest`, `ui/settings/VaultPageUiTest.aVaultMadeWhileMediaGoesUpIsntReadAgainAtEachProgressTick`. What travels sealed: settings, what the AI learned, texts, and the vault's own parts (keys, pins, transcripts); media never (its own switch, `cloud.media`). The keys of the vault stay on the machine (`cloud.vault.*`, never in the synced settings). Details, one topic each:

- The vault (`Vault`): `Unichat/Vault/vault.json` (`Info`: id, created, generation) and one slot per way in at `keys/<id>.json` (`VaultSlot`), sealed under "slot:<vault>:<method>:<id>:<generation>" so a slot moved to another vault, method or id, or put back claiming another generation, opens nothing, and `Vault.slots` lists only the current vault's; a computer's slot id is its machine UUID and its params carry its X25519 public key, sealed with the vault key beside it (`VaultNext`: a key put in through the account is offered nothing); only UUID ids (`Ids.ours`) become paths. `VaultTest`.
- Changing the key (`Vault.rotate`, `CloudVault.rotateKey`, only with the vault open here): a new VK offered to every computer still listed as `next` in its slot (an ephemeral X25519 agreement with its public key, HKDF with info "unichat-vault rotate" + the ephemeral and the computer's public keys, sealed under "next:<vault>:<machine>:<generation>"; vouched for by `auth` = the old VK sealing, under "offer:<vault>:<machine>:<generation>", the ephemeral key and the SHA-256 of what it seals; an offer not yet taken stays behind the new one as `prior`, so a computer off through two changes follows the chain from the key it holds; `vault.json` carries `vouch`, its generation sealed with the VK it replaced), but only to one whose public key the old VK sealed and is the one this computer first saw (`VaultPeers`, `cloud.vault.peers`: machine → key, pinned each open round on first sight, best effort, or at the change for one never seen; a computer removed but holding the old VK can seal a key of its own into another's slot). A pin stays when its slot goes (it may come back with another key); only `Cloud.removeComputer` drops it (marked removed before its slot is deleted, so one that can't be deleted is kept out all the same), and a machine removed here is never pinned nor offered again; `Cloud.acceptKey` pins the key its slot shows now (the person says it was set up again). One refused (another key, or one no agreement works with: malformed, small order) is offered nothing and named (`KeyChanged.refused`: "the key of <computer> changed"). Each open round a computer puts its own public key (from `cloud.vault.private`) back in its slot if it isn't there. Then a new recovery code, `cloud.vault.codeUnconfirmed` set (before the rise: an answer lost after it never hides that a new code is to be kept; nothing reads the vault again before the code is returned), then `vault.json`'s generation rises; only after that the old recovery and password slots go (and any Google or passkey one: those methods exist in `VaultSlot.Method` but no screen offers them yet) (`Rotated.dropped`, added again by the person) and every file under the vault but `keys/` and `vault.json` is sealed again (`VaultReseal`: written only if its stamp is still the one read; one opening with neither key is left and named; one that can't be read or listed is noted, `resealFailed`, and the rest goes on). Cut short before the generation rises, its offers and new recovery slot are taken back while the account still says the old generation (`withdrawn`: a stale offer would become the key if someone raised the generation by hand), and `codeUnconfirmed` is put back as it was (`CloudVault.rotate`: no new code came of it); one whose answer was lost after it rose is done. Unichat quitting halfway leaves its offers and an unshown recovery slot behind (orphaned: the same risk, until the next change replaces the offers and drops every other recovery slot). A computer whose slot is older than the generation opens its old VK with its slot, then takes its `next` with `cloud.vault.private` only when that old VK vouches for it, directly or through `prior` (`VaultParts.taken`, `VaultNext.take`), seals again with the new key only what it sent itself and that still opens only with the old (a text of its own folder whose content is the start of its file here, `TextSync.sentHere`; one that isn't is sent again from here, its `sent` dropped; never its `index.json`, which goes anew after the pass, `TextSync.indexAgain`; a part whose content is what it agreed on, `SyncedPart.holds`/`MergedPart.holds`: anything else may be a removed computer's and is never promoted), then always rewrites its slot with its own key. No offer it can take → `REMOVED` when the change is vouched for with its old VK (`Vault.vouched`: `vault.json`'s `vouch`, or another computer's offer), else `UNRECOGNIZED` (a generation raised through the account: its key kept, nothing sent, until an offer it can follow comes or a way in opens it). Limit: a removed computer holds the old VK, so it can vouch for an offer of its own to a computer that was off during its removal, until that one is opened with a way in; for the same reason it can write a turn-off mark that such a computer believes (the mark's key is HKDF of the VK both held), and that one then goes plain. The one changing it does the same right after. `CloudVault.removeComputer` deletes another computer's slot; `CloudVault.forgetHere` this one's, then `cloud.vault.id`/`key`/`private`/`offKey`/`codeUnconfirmed`, the pins and the move's markers (not `declined`): locked here after. All three on the vault's thread, never alongside a round's vault part (`vaultPart`) nor `textsNow` (`keyLock`). `VaultRotateTest`.
- A file of the vault that doesn't open is `SealedStorage.Damaged`. While open, a part under `Settings` that doesn't open reads as none, so this computer's own copy goes up in its place, but only while `vault.json` still says this round's generation (one sealed with a newer key is never written over with an older); the round goes on and `Status.vaultNotice` (`Cloud.Notice`: `Cloud.Part`s, never file names) names it (`replaced`, only once this computer's copy actually went up; else `damaged`), in words by `ui/settings/CloudTexts.vaultLines`. The generation is checked at the read, not at the write: a change of key landing in between gets this copy sealed with the old key, which heals itself, since this computer's next round takes the new key and seals again what it agreed on. Another computer's text that doesn't open is never written: `TextSync` skips that file (its index read again next round), its later files still come, and the machine is named (`Notice.textsDamaged`: machine → its computer slot's label).
- `SealedStorage` (a `Storage` over the account): `Unichat/<rest>` is kept at `Vault.ROOT/<rest>`, sealed with the logical path as associated data, so `SyncedPart` and `TextSync` run over the vault unchanged (a re-seal changes the stamp but not the opened content, so nothing re-uploads). Media and the vault's own folder are refused (`IllegalArgumentException`); a file that doesn't open says the vault's copy is damaged (`cloud.error.vaultDamaged`). The key comes from a supplier on each call, never kept. `SealedStorageTest`.
- Each round (and `textsNow`) asks `VaultParts.open` for the vault's state here (`Cloud.VaultState`, in `Status.vault`): no `vault.json` → `NONE`, today's plain round (and a vault this computer held or declined is gone: `cloud.vault.id`/`key`/`private` and `declined` forgotten, `VaultParts.gone`), but for a computer holding an id only when `VaultOff.says` (the turn-off mark opens with its `cloud.vault.offKey`, kept each open round, `VaultOff.remember`): otherwise `MISSING` (also one off through a change of key and then the turn-off: its key is the older generation's, `VaultRotateTest.aComputerOffThroughAChangeOfKeyAndATurnOffAsksOnce`) (keys kept, nothing personal; `CloudVault.leaveMissingVault`, "Volver a sincronizar sin cifrar", asked twice, does `gone`); a computer holding no id is `MISSING` too when it saw a vault (`cloud.vault.seen`: the id of every valid `vault.json` read, any state, or made here; another id replaces it; `gone` clears it, `forgetHere` keeps it): one that declined or never opened it has no key to believe a mark with; a `vault.json` that doesn't read, another vault's id or no key here → `LOCKED`, or `DECLINED` with `cloud.vault.declined` ("Seguir sin la bóveda en este equipo"); its `COMPUTER` slot (id = machine) gone or not opening with `cloud.vault.key` → `REMOVED`; else `OPEN`, the vault key in memory for the round only (`VaultParts.Round`, cleared on close). `OPEN`: the same `SyncedPart`s, `TextSync` and the vault's own parts (`secrets`: `Settings.VAULT_SECRETS` + `gif.<id>.key`, `SyncedPart.merged`: `adoptVaultSecrets` merges, a key only this computer had stays and goes up next round, any other key and a Telegram key that isn't one (`settings/TelegramKeyFormat`) ignored; `pinned`: `PinnedMessages.json`/`adopt`, through its own writer; `transcripts`: a `MergedPart`, the union, nothing deleted, names listed each round and a file read only to go up, only `<sha256>.txt` names become files) over `SealedStorage`, whatever `cloud.media`/`cloud.settings` say: the vault is its own switch. `LOCKED`/`DECLINED`/`REMOVED`/`UNRECOGNIZED`/`MISSING`: nothing personal, plain or sealed. `cloud.media` gates media in every state, and the plain texts only in `NONE`. When the state changes (`Cloud.vault`, for a round and `textsNow` alike), every part forgets the stamps it saw (`unseen`): a plain file and its sealed copy can carry the same ETag (`CloudVaultTest.theVaultOpeningHere…`).
- Moving in (`VaultMove`, each round while `OPEN`, after the sealed parts and texts, in the round's vault part): the plain `Cloud.Part` files under `Settings` (no other name there) and every machine's texts under `Texts` (UUID folders, `TextIndex.FILE` names and `index.json` only) go into the vault, each plain copy deleted only once its sealed copy reads back whole (a text as long as the plain one: they only grow) and its stamp is still the one read (an older computer may have sent a longer one meanwhile). A settings file is copied only where the vault has none, never over it. Each computer with a `COMPUTER` slot is the only writer of its sealed texts (`TextSync`'s record says where what it sent went, `sentTo`: "plain" or "vault:<id>"; another one sends them all again, once, and a launch to the same one sends nothing): its plain ones only go once its sealed copy is as long, and the move is done (`cloud.vault.movedAt`) only once every such computer's plain texts went, so a computer of the vault that never runs again holds it (and no stray is named) until it's removed from the vault; a computer without a slot's texts come in under its name here (sealed index merged through `TextIndex`), only for the machines sending plain when the move first ran (`VaultMove.SENDERS`: one list sealed in the vault, `Unichat/Log/senders.json`, never under `Settings` (where a part that doesn't open reads as none and a plain file of ours is moved in), written once by the computer that made the vault, `cloud.vault.recordSenders` until then; every later computer adopts it and never writes its own; none there takes nothing in (the account can delete the list, never write one), and one that doesn't open, or gone once read here (`cloud.vault.sendersKnown`), is the round's error, `cloud.error.vaultSendersDamaged`, never written again), and only as new names: a plain text never replaces a sealed one (a longer one stays plain); any other folder is named as a stray, never taken nor deleted. - What Ajustes → Nube → Bóveda does (`VaultActions`, through `Cloud` on the vault's thread, under `vaultPart` and `keyLock`; the page never sees a key): `createVault` (open here at once; the code shown once and `cloud.vault.codeUnconfirmed` = the vault id until `codeKept`: the person typed two groups back, `RecoveryCheck`; `newRecoveryCode` and a change of key set it again), `openVault(Way, char[])` (the recovery code as typed, `RecoveryCode.parse(char[])`, or a password; only slots at the vault's current generation, but on a computer that holds this vault and is `UNRECOGNIZED` (the state of a fresh round, `CloudVault.openVault`), where one from before counts when it opens the key its own slot opens: a new computer never joins an old key through a way in put back with the vouch stripped; one that opens nothing is `cloud.error.vaultWrongSecret` and writes nothing; opened, this computer writes its `COMPUTER` slot and keeps `id`/`key`/`private`, `declined` cleared; the `char[]` is cleared once used), `declineVault`, `addPassword` (12+), `rotateKey(confirmed)` / `removeAndChangeKey(machine, confirmed)` (remove, then `rotate`, in one job: a removed computer still holds the key; only the computers the person saw listed are offered the key, any other is refused and named; a change that fails after the removal says the key was kept, `cloud.error.vaultRemovedKeyKept`, only when the account still shows the old generation; else `vaultRemovedKeyUnknown`), `deleteLockedVault` (`LOCKED` only, "Borrar esta bóveda y empezar de nuevo", asked twice: `Vault.ROOT` deleted with no mark, its key isn't here, so the computers that held it go `MISSING`), and "Olvidar la bóveda en este equipo" warns when this is the only computer and the code isn't kept. Every computer's name read from the account goes through `VaultView.label` (one line, no invisible marks, 64 characters cut between whole graphemes) where it's read (`Vault.computers`, `rotate`'s refused, the view): strays, damaged texts and the page all show it so. `vaultView` → `VaultView`: the state, the ways in by method (a slot's label is the account's to write, so never what names a way in), and, open, each computer with its label as one plain line (`Lines.one`, 64 characters), when first pinned here, `keyChanged` (removed here, or not the pinned key: it'd be refused), `unseen` (never pinned here) and `newSinceRemoval` (`VaultPeers` counts removals and keeps, per pin, the count when pinned: no clock to compare). `VaultActionsTest`; the screens' `ui/settings/VaultPageUiTest` over `VaultFixture` (public, for tests of other packages).
- Turning it off (`CloudVault.turnOffVault`, `VaultOut`, only open here, on the vault's thread under `vaultPart`, `keyLock` and `TextSync`'s lock): the settings and the AI's part go back to their plain files (the opened content, read back equal), and every machine's sealed texts (all of them: one that's off has no one else to send them) where the plain one is missing or shorter, the plain index merged and read back; a file that doesn't open is left (a text's writer sends its own plain once it finds the vault gone). Only once everything came back is the mark written (`VaultOff.write`: `Unichat/Settings/vault-off.json`, the vault and generation sealed with HKDF(VK, "unichat-vault off"), taken back with the rest on a failure, deleted when neither the folder nor `vault.json` would go, and by the next `Vault.create`) and `Vault.ROOT` deleted whole; any failure before takes back the plain files this run wrote (best effort: the vault holds them all) and leaves the vault as it was, told, to try again. Another computer's round still open meanwhile may let a plain copy go (`VaultMove.letGo`: its sealed one is as long), so after the delete every plain copy is looked at again and put back where missing (a text also where shorter: texts only grow; a part is a whole file, and another one there is newer), and read back. `VaultMove.deleteIfSame` also reads `vault.json` right before each plain delete and keeps the copy unless it's still the vault moved into; one request apart, a vault turned off in between still loses that copy (its writer sends its own again; an offline computer's is the one at risk). A failure before the delete says nothing changed (`cloud.error.vaultOffUndone`). A folder that won't go: `vault.json` alone is deleted (every computer goes `NONE`), told as `cloud.error.vaultLeftovers`, and `Vault.create` clears a `Vault` folder without `vault.json` first; neither deleted: `cloud.error.vaultPartlyGone` (never "as it was": everything is plain, the vault may be partly gone). The vault's own parts (secrets, pins, transcripts) never go plain. Then `VaultParts.gone` (the hold here and `declined`) and `TextSync.sentAt(PLAIN)` (what was sent was just copied: nothing goes again). Another computer finding no `vault.json` with an id held goes `gone` and back to `NONE` once the mark opens with its key; one that declined or never opened it is `MISSING` and asks once (`cloud.vault.seen`); its texts go plain once (`sentTo` changed). Media never. `VaultOutTest`.
- The passkey probe (phase 3's step 1, `docs/superpowers/specs/2026-11-19-passkey-probe.md`): `PasskeyPage` (+ `PasskeyHtml`) serves `http://localhost:43117/passkey` on `Loopback` (relying party `localhost`; nothing from outside, CSP `default-src 'none'`), whose script makes or uses a passkey asking for PRF with a fixed salt and posts back with `state` only what it found: PRF's length and fingerprint (8 bytes of SHA-256("unichat probe fp" ‖ PRF): the same value shows as the same), never its bytes; only Host `localhost`/`127.0.0.1:<port>` and its own Origin are answered (DNS rebinding); every field one line, cut short. `PasskeyProbe` runs it with `-Dunichat.passkeyProbe=true` or `--passkey-probe` (on start, and "Probar llave de acceso (prueba)" in Bóveda, `ui/settings/PasskeyProbeRow`), one at a time, and appends each finding to `<data>/logs/passkey-probe.txt`. `PasskeyPageTest`, `PasskeyProbeTest`.
- Creating a vault is detect-not-prevent (no service gives conditional writes): a vault overwritten after `create`'s second read-back leaves ours orphaned, so whoever holds a vault key compares `Vault.info(...).id()` with the vault id it holds before trusting it. A `vault.json` that isn't one is replaced only while `keys/` is empty.

## Lessons
- A round whose vault move failed after the switch went on with the old names' view, found its parts gone there and sent its own older copies, which then won. A move cut short reads the account again before anything is written (`VaultNamesTest.aRoundCutShortAfterTheSwitchGoesOnUnderTheNewNames`); likewise a job or `textsNow` chooses the vault's names under the lock the move holds (`aKeyChangeAcrossTheSwitchKeepsTheRemovedComputerOut`, `textsAskedAloneDuringTheSwitchGoUnderTheNewNames`), and only a job that writes the vault may run the move (opening the page ran all of it, or was refused: `openingTheVaultsPageNeverRunsTheMove`). A finish cut short left old slots that a later round copied back over a key changed or a way in taken away since (`REMOVED` here, a removed computer back): every writing job finishes the leftovers first (`aKeyChangedAfterAnInterruptedFinishKeepsThisComputerIn`, `aWayInTakenAwayAfterAnInterruptedFinishStaysGone`, `aComputerForgottenAfterAnInterruptedFinishStaysGone`).
- A vault under its old names read through the new ones was `MISSING` (no `vault.json`, no mark): a rename of anything a computer checks for its state needs a reader for both names until the move is done (`OldVault`, `VaultNamesTest`).
- Ajustes → Nube → Bóveda said "Leyendo la bóveda…" for hours: every vault job ran on the round's one `cloud` thread, queued behind a day's check of 636 uploaded files (`media.verify`, one `DropboxApi.info` each) or a long video. Vault jobs have their own thread and share only `Cloud.vaultPart` with the round's vault part, never its media (`CloudVaultJobsTest`). A job kept apart from a round by sharing its thread waits for all of it: share a lock over only the part that must not overlap.
- With vault jobs off the round's thread, a vault made during media was still told as `NONE` by every progress tick (`Status.doing` kept the state the round began with), and `VaultPage` reloads on any state it doesn't show: 30 reads of `vault.json` for 4 photos, hours of them in a day's check. Whatever publishes mid-round says the state last read (`Cloud.vaultKnown`); a status field another thread can change is never copied forward from the round's start.
- Once vault jobs told the status too, `UnichatApp`'s listener read `c.status()` on the telling thread and posted it (and `Notifier.setCloud` built its lines before going to AWT): an older status posted after a newer one stayed on the tray and the gear until the next. A listener posting to another thread reads the status in what it posts (`ui/CloudShown`).
- A computer took any `next` that opened with its private key, and anyone can encrypt to a public key: someone with only the account could offer it a key of their own and raise the generation. An offer counts only when the key the computer holds vouches for it (`VaultNext.take`, `VaultRotateTest.anOfferForgedThroughTheAccountIsNeverTaken`); a generation nothing vouches for is `UNRECOGNIZED`, never `REMOVED` (`aGenerationRaisedByHandLocksNobodyOut`).
- A way in from before a change of key opened the old key on any computer once `vault.json`'s vouch was stripped, and a slot's generation was the account's to say: someone holding the old key (a removed computer) could put the old password's slot back and have a new computer join that key. A slot's generation is sealed with it, and an older slot counts only on a computer already holding the vault, `UNRECOGNIZED`, for the key its own slot opens (`VaultActionsTest.aNewComputerNeverJoinsTheOldKeyThroughAWayInPutBackFromBeforeTheChange`, `aWayInPutBackClaimingTheCurrentGenerationOpensNothing`).
- A computer finding no `vault.json` went plain: deleting one file sent every computer's settings and texts unencrypted. Only the turn-off mark that opens with its key does that (`VaultOutTest.theVaultsFileDeletedByHandSendsNothingPlain`). Anything the account says that makes a computer send more, or send plain, needs proof only a key holder can write. A declined or never-opened computer still went plain on the file deleted (no key, so no mark to check): it remembers the vault it saw (`cloud.vault.seen`) and is `MISSING` (`VaultOutTest.aComputerThatDeclinedSendsNothingPlain…`).
- Each computer recorded its own list of the machines sending plain on its first move, so a folder put in through the account before a later computer opened the vault was sealed in by it. The list is the vault's, sealed, written only by the computer that made it (`CloudVaultTest.aFolderPutInAfterTheFirstMoveIsNeverTakenInByALaterComputer`).
- The vault's list of who sent plain lived at `Settings/unichat-senders.json`, a name the move takes in as a settings file and a place where a part that doesn't open reads as none: deleting or damaging the sealed list and planting a plain one had it sealed in, and the attacker's folder after it. The list is at `Log/senders.json`, the move takes only `Cloud.Part` files, and a list damaged or gone is told, never written again (`CloudVaultTest.theListDamagedInTheVaultAndAnotherPlantedPlain…`).
- `Vault.create` checked `vault.json` only right after writing it: a second computer overwriting it a moment later left two vault keys under one id, unnoticed. It reads it back again after writing its slots and takes back what it wrote (`undo`) when the id changed or anything failed, so neither a lost race nor a dropped network leaves a half-made vault in the way (`VaultTest.aVaultMadeElsewhereAfterOursWasReadBackStillWins`, `aFailureHalfwayLeavesNoVaultBehind`).
- `VaultMove` first copied every machine's plain texts into the vault, a second writer beside each computer's own `TextSync` (and `textsNow`, on its own thread): a shorter plain copy could land over a longer sealed one just sent, whose writer then never sent it again. A computer of the vault's sealed texts are only ever written by it; the move only lets their plain copies go (`VaultMoveTest.aComputerOfTheVaultIsTheOnlyWriterOfItsTexts…`).
- Clearing `TextSync`'s `sent` on every vault state change re-sent all of a computer's texts at each launch (`Cloud`'s last state starts unknown, so the first round is always a "change"). What was sent is kept with where it went (`sentTo`), and only another place clears it (`TextSyncTest.aRestartSendsNothingAgain…`, `CloudVaultTest.aLaunchSendsNoTextAgain…`).
- A check cut short by Unichat going unseen started again from the first file each round: with hundreds of files and short windows it never ended, hashing and asking about the first ones over and over. What a check has looked at is kept until it's whole (`MediaUpload.checked`, `MediaUploadTest.aCheckCutShortGoesOnFromWhereItStopped`); anything stopped on a condition resumes, never restarts.
- Repairing from the account read the whole file into memory (`Storage.get` → `byte[]`): a 3 GB video failed every day. Media comes down with `Storage.get(path, target)`, as it arrives, into a hidden ".part" renamed once whole (`Storage.save`); the `byte[]` one is for the settings only (`StorageDownloads`, used by each service's test; `MediaUploadTest`'s account refuses the `byte[]` one).
- A browser sign-in left unfinished kept 127.0.0.1:43117 for good, so the next "Connect" said the port was busy until a restart. `Loopback.until`: each sign-in ends at `Loopback.DEADLINE` (tests give `Duration.ZERO`), on cancel, and when Ajustes → Nube goes or its window closes (`CloudPage.cancelWhenGone`, `CloudSignInUiTest`); the port is freed before the failure is told. A test waits on such a future with `get()`, which JUnit's timeout can interrupt; `join()` can't, and hung the run for good.
- `state` is compared in constant time (`Loopback.ours`, `.claude/lessons.tsv` `oauth-state-equals`); pCloud's page takes the "#access_token" out of the address (`history.replaceState`) once read, so it doesn't stay in the browser's history.
- `WebDav`'s PROPFIND patterns (`<…href[^>]*>`) scanned past every tag to the next `>`: an answer full of tags that never close read the whole answer again from each one. A tag's class stops at `<` or `>` (`[^<>]*>`), so each char is read a few times (`WebDavTest.aServersAnswerIsReadInLinearTimeWhateverItHolds`, `app.unichat.CountedReads`). Found by the security reviewer.
- Dropbox's sign-in hung when its token server couldn't be reached: `DropboxLogin.back` put `e.getMessage()` on the browser's page, a `ConnectException` has none, `Loopback.page(null)` threw, the browser's connection was dropped and the sign-in waited for its deadline. A failure's message may be null or blank: show `Errors.message(e)` (the class name then), and say "couldn't reach" apart from a refusal (`cloud.dropbox.unreachable`; `DropboxTest.aTokenServerThatCantBeReachedFailsTheSignInAndTheBrowserSaysSo`, `aFailureWithABlankMessageStillSaysWhatFailed`); NullAway now refuses `e.getMessage()` where a value is needed.
