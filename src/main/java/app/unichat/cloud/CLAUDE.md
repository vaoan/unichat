# cloud — notes for Claude

The person's own storage account (pCloud, Icedrive, Nextcloud…).

- `Storage` is the account however it's reached: `WebDav` (Icedrive, any other), or `PCloudApi`, pCloud's own API (stat, createfolderifnotexists, uploadfile with nopartial, getfilelink; token in a Bearer header, never in an address), because pCloud's WebDAV refuses a login with two-step verification on (it just never answers: every question to a server waits at most `WebDav.ANSWER`). `PCloudLogin` signs in in the browser (OAuth 2 token flow): pCloud's page, then `http://localhost:43117/pcloud` (fixed: the address registered with the app), whose page passes the "#" part on to `/pcloud/done`; `state` ties the answer to the request; only `*.pcloud.com` hosts are trusted with the token. The app's Client ID: `PCloudLogin.CLIENT_ID` once Unichat's app is registered, or `cloud.pcloudClientId` from Ajustes → Nube. Tests: `FakePCloud`. `DropboxApi` (API v2, app-folder access: paths start in Dropbox/Apps/<app>): `DropboxLogin` signs in with OAuth 2 + PKCE (no secret in the app; Dropbox sends a code to `http://localhost:43117/dropbox`, exchanged with this sign-in's own verifier for a lasting refresh token, kept as the account's secret); each call carries a short-lived token made from it again when Dropbox answers 401; names go in the `Dropbox-API-Arg` header as ASCII-escaped JSON (accents, emoji); files over 150 MB go up in an upload session. App key: `DropboxLogin.APP_KEY`, or `cloud.dropboxAppKey` from Ajustes. Both browser sign-ins share `Loopback` (127.0.0.1, port 43117, state). Tests: `FakeDropbox`.

- Every request to a service goes through `Http.send` (no answer in time → `cloud.error.noAnswer`; interrupted → `IOException` keeping the interrupt).
- `WebDav` (PROPFIND/MKCOL/PUT/GET; `stamp` = ETag or date, so a round downloads only what changed), `CloudAccount` (service, address, login and secret: `cloud.` keys stay on this machine; `Unichat/Ajustes`, `Unichat/Multimedia`), `Cloud` (one round a minute and one after anything's saved, on its own thread; `Status` for Ajustes → Nube, `ui/settings/CloudPage`).
- `SyncedPart`: one thing kept the same on every computer, as one file: three versions (here, the account's, the last agreed `cloud.base.<name>`); only one side changed → it goes to the other; both → the newer; a computer new to the account takes what's there. After adopting, the agreed hash is what this computer holds (agreeing on the account's own sent it back up forever). Two parts: the settings (`Bundle`: portable settings minus `panel.`, and `preferences.json` minus what only follows the server) and what the AI learned (`writing-style.md`; pending corrections stay here).
- Applied live, never a restart: settings through `Settings.replacePortable`, then `ui/settings/SyncedSettings` (what Ajustes does for the few read once: theme, AI buttons, global shortcut, Dock, notifications label, update check, language last); preferences through `ChatPreferences.adoptPreferences`. `SyncedSettingsUiTest` has a proof for every setting key in the source, and fails for a new one without.
- Media (`MediaUpload`): each chat's saved folder goes up until all of it is there: a file that fails waits its own turn again (1, 2, 4… up to 60 minutes, forever, `Retry`) without holding the others back. Each upload is checked against the account's copy (`Storage.info`: size, and a checksum where the service gives one: pCloud's SHA-1, Dropbox's content hash; WebDAV only the size; computed here by `Checksums`). Once a day and on "Verificar ahora" everything uploaded is checked and repaired, the bigger copy winning (`Checksums.decide`: damage cuts files short, so a file damaged here is restored from there and never damages it; same size and other content: neither is touched, the person is told). Done files in `cloud-uploaded.txt`; nothing there is ever deleted; hidden and ".part" files wait. A round reports each step (`Cloud.Activity`: settings, what the AI learned, uploading or checking file n of m) for Ajustes → Nube.
- Not in the demo (its chats would reach the person's account), except for a snapshot of the page. Tests use `FakeDav` (an in-memory WebDAV on 127.0.0.1).
- What a round is doing reaches the person three ways, in the same words (`ui/settings/CloudTexts`): Ajustes → Nube's line and bar, the tray (lines at the top of its menu: what, how fast, the file and how far, how many left; and the icon's ring while files go up and nothing is being saved, `Notifier.setCloud`), and a ring over the settings gear (`Rail.setCloud`, drawn over it, never in the layout: the chat never moves; its tooltip has the lines; a click while files go up opens Nube). Speed comes from the bytes going out (`CountingBody`, `Storage.put(path, file, sent)`), over the time since the round's first byte.
- What chats say (`TextSync`): each computer sends only its own files (`<data>/texts/here`) to `Unichat/Textos/<machine>/` with an `index.json` of their sizes, and brings the others' into `texts/<machine>/` when an index's stamp changed (machines found with `Storage.list`); no file ever has two writers, so the cloud never replaces one computer's copy with another's (a shared file rewritten by each made conflicted copies and lost lines). Only names of ours (a machine's UUID, `<key> <yyyy-MM>.jsonl`) become paths here. In every round before media, and alone on its own thread (`Cloud.textsNow`: after something new is kept, and before a deleted message is looked at), since a round may be sending a video for minutes. `TextSyncTest`, `StorageListing` (each service's `list`).
- The vault (`Vault`): `Unichat/Bóveda/boveda.json` (`Info`: id, created, generation) and one slot per way in at `llaves/<id>.json` (`VaultSlot`), sealed under "slot:<vault>:<method>:<id>" so a slot moved to another vault, method or id opens nothing, and `Vault.slots` lists only the current vault's; a computer's slot id is its machine UUID and its params carry its X25519 public key (for a new key later); only UUID ids (`Ids.ours`) become paths. `VaultTest`.
- `SealedStorage` (a `Storage` over the account): `Unichat/<rest>` is kept at `Vault.ROOT/<rest>`, sealed with the logical path as associated data, so `SyncedPart` and `TextSync` run over the vault unchanged (a re-seal changes the stamp but not the opened content, so nothing re-uploads). Media and the vault's own folder are refused (`IllegalArgumentException`); a file that doesn't open says the vault's copy is damaged (`cloud.error.vaultDamaged`). The key comes from a supplier on each call, never kept. `SealedStorageTest`.
- Each round (and `textsNow`) asks `VaultParts.open` for the vault's state here (`Cloud.VaultState`, in `Status.vault`): no `boveda.json` → `NONE`, today's plain round (and a vault this computer held is gone: `cloud.vault.id`/`key`/`private` forgotten); a `boveda.json` that doesn't read, another vault's id or no key here → `LOCKED`, or `DECLINED` with `cloud.vault.declined` ("Seguir sin la bóveda en este equipo"); its `COMPUTER` slot (id = machine) gone or not opening with `cloud.vault.key` → `REMOVED`; else `OPEN`, the vault key in memory for the round only (`VaultParts.Round`, cleared on close). `OPEN`: the same `SyncedPart`s, `TextSync` and the vault's own parts (`secrets`: `Settings.VAULT_SECRETS` + `gif.<id>.key`, `SyncedPart.merged`: `adoptVaultSecrets` merges, a key only this computer had stays and goes up next round, any other key and a Telegram key that isn't one (`settings/TelegramKeyFormat`) ignored; `pinned`: `PinnedMessages.json`/`adopt`, through its own writer; `transcripts`: a `MergedPart`, the union, nothing deleted, names listed each round and a file read only to go up, only `<sha256>.txt` names become files) over `SealedStorage`, whatever `cloud.media`/`cloud.settings` say: the vault is its own switch. `LOCKED`/`DECLINED`/`REMOVED`: nothing personal, plain or sealed. `cloud.media` gates media in every state, and the plain texts only in `NONE`. When the state changes (`Cloud.vault`, for a round and `textsNow` alike), every part forgets the stamps it saw (`unseen`): a plain file and its sealed copy can carry the same ETag (`CloudVaultTest.theVaultOpeningHere…`).
- Moving in (`VaultMove`, each round while `OPEN`, after the sealed parts and texts, on the cloud worker): the plain `unichat-<part>.json` under `Ajustes` and every machine's texts under `Textos` (UUID folders, `TextIndex.FILE` names and `index.json` only) go into the vault, each plain copy deleted only once its sealed copy reads back whole (a text as long as the plain one: they only grow) and its stamp is still the one read (an older computer may have sent a longer one meanwhile). A settings file is copied only where the vault has none, never over it. Each computer with a `COMPUTER` slot is the only writer of its sealed texts (`TextSync`'s record says where what it sent went, `sentTo`: "plain" or "vault:<id>"; another one sends them all again, once, and a launch to the same one sends nothing): its plain ones only go once its sealed copy is as long, and the move is done (`cloud.vault.movedAt`) only once every such computer's plain texts went, so a computer of the vault that never runs again holds it (and no stray is named) until it's removed from the vault; a computer without a slot's texts come in under its name here (sealed index merged through `TextIndex`). It runs under `TextSync`'s lock, and the first file that fails is the round's error (media still goes). The markers are forgotten when the vault is gone or another one is there. Done once nothing is left (`cloud.vault.movedAt`); after that a plain file is a stray: a computer still on a Unichat without the vault, named by its `Bundle.machine` or its `Textos/<machine>` (`Status.moving().strays()`, with its computer slot's label or ""), its texts still taken in, its settings never, and its plain files deleted only once none changed for `VaultMove.QUIET` (`cloud.vault.strayQuietSince`, `cloud.vault.straySeen`: a hash of their stamps, so a restart doesn't make them new). Media never. `VaultMoveTest`, `CloudVaultTest`.
- Creating a vault is detect-not-prevent (no service gives conditional writes): a vault overwritten after `create`'s second read-back leaves ours orphaned, so whoever holds a vault key compares `Vault.info(...).id()` with the vault id it holds before trusting it. A `boveda.json` that isn't one is replaced only while `llaves/` is empty.

## Lessons
- `Vault.create` checked `boveda.json` only right after writing it: a second computer overwriting it a moment later left two vault keys under one id, unnoticed. It reads it back again after writing its slots and takes back what it wrote (`undo`) when the id changed or anything failed, so neither a lost race nor a dropped network leaves a half-made vault in the way (`VaultTest.aVaultMadeElsewhereAfterOursWasReadBackStillWins`, `aFailureHalfwayLeavesNoVaultBehind`).
- `VaultMove` first copied every machine's plain texts into the vault, a second writer beside each computer's own `TextSync` (and `textsNow`, on its own thread): a shorter plain copy could land over a longer sealed one just sent, whose writer then never sent it again. A computer of the vault's sealed texts are only ever written by it; the move only lets their plain copies go (`VaultMoveTest.aComputerOfTheVaultIsTheOnlyWriterOfItsTexts…`).
- Clearing `TextSync`'s `sent` on every vault state change re-sent all of a computer's texts at each launch (`Cloud`'s last state starts unknown, so the first round is always a "change"). What was sent is kept with where it went (`sentTo`), and only another place clears it (`TextSyncTest.aRestartSendsNothingAgain…`, `CloudVaultTest.aLaunchSendsNoTextAgain…`).
- Repairing from the account read the whole file into memory (`Storage.get` → `byte[]`): a 3 GB video failed every day. Media comes down with `Storage.get(path, target)`, as it arrives, into a hidden ".part" renamed once whole (`Storage.save`); the `byte[]` one is for the settings only (`StorageDownloads`, used by each service's test; `MediaUploadTest`'s account refuses the `byte[]` one).
- A browser sign-in left unfinished kept 127.0.0.1:43117 for good, so the next "Connect" said the port was busy until a restart. `Loopback.until`: each sign-in ends at `Loopback.DEADLINE` (tests give `Duration.ZERO`), on cancel, and when Ajustes → Nube goes or its window closes (`CloudPage.cancelWhenGone`, `CloudSignInUiTest`); the port is freed before the failure is told. A test waits on such a future with `get()`, which JUnit's timeout can interrupt; `join()` can't, and hung the run for good.
- `state` is compared in constant time (`Loopback.ours`, `.claude/lessons.tsv` `oauth-state-equals`); pCloud's page takes the "#access_token" out of the address (`history.replaceState`) once read, so it doesn't stay in the browser's history.
