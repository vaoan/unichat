# matrix — notes for Claude

`ChatService` over Matrix: sync, sending, bridges seen from the client. `MessageHtml` gives the message's HTML to `ui/timeline/HtmlView` and its bridge's link previews to `ui/timeline/LinkPreviewCard`: `ui/timeline/CLAUDE.md`.

- `matrix/` — `MatrixChatService` (facade: lifecycle, sync loop) over `MatrixCore` (shared), `MessageSender`, `ChatActions`,
  `BridgeAccounts`, `DiscordServers`, `ContactActions`, `MediaDownloader`, `SyncCache`, `MatrixLogin`, `Profiles`, `Invites`, `FetchedMessages`; `SyncProcessor`
  (pure /sync → model, unit tested) with `RoomFields`, `SystemMessages`, `SyncEvents`; `BridgeProtocol` (pure), `BotChat`, `MatrixClient` (HTTP). `MatrixLiveIT` = end-to-end test, needs `UNICHAT_IT_HOMESERVER`.
- Media cache: `matrix/MediaCache` caps `cache/media`
  (`cache.mediaMb`, LRU; files over 1 MB go first, saved stickers/GIFs are pinned, `MediaSource.keepCached`; one file per direct-media URL whatever the size). `model/MediaLibrary.same` says when two items are one sticker (bridge id, else format, dimensions and bytes), since direct media gives the same file a new URL in each message. A thumbnail the server made (`/thumbnail`, never an original or a bridge's direct media) is kept as the lightest file: an opaque PNG becomes a smaller JPEG (`support/LighterPictures`, `LighterThumbnailDownloadTest`).
- Read receipts (`Settings.readReceipts`, Ajustes → Privacidad): ALWAYS sends `m.read` on opening a chat; ON_REPLY and NEVER send `m.read.private`, which tuwunel never passes to appservices, so the bridge never tells the network; ON_REPLY then sends a public `m.read` for the newest message of someone else just before each message we send and each reaction we add (`MessageSender.readOnReply`; a reaction is an answer; `ReadOnReplyTest`). The person's phone app still marks read on its own.
- Formatting what's sent: WhatsApp's marks (`*bold*`, `_italic_`, `~strike~`, `` `code` ``, ```` ``` ```` blocks, `> ` quotes) plus Discord's `__underline__` and `||spoiler||` become `formatted_body` (`model/Markup`, pure; nothing inside a word, code or a link), which each bridge writes its network's way; with no marks the message is plain text as before. The box's right-click menu (`ui/timeline/FormatMenu`, ⌘B ⌘U ⌘⇧X) offers only what the chat's bridge lists in `formatting` (`RoomFeatures.formats`) and wraps or unwraps the selection (`model/TextFormat`).
- Bridges send `com.beeper.message_send_status` for each message (`BridgeConfig`: `message_status_events`, plus the error notice that says why); `SyncProcessor.applySendStatus` marks ours FAILED when the network refused it, so a message never looks sent when it wasn't.
- Staying current: `support/WakeWatch` notices the computer waking (macOS stops awake time while asleep, so a long poll left open would wait out its timeout on a dead connection); `MatrixChatService.wake` drops it and catches up at once. The top bar (`MainView.showConnection`) says "Conectando…" until the server answered and "Sincronizando <redes>…" while a network's bridge reconnects (`AccountAlerts.syncingLine`); bridges never report when their backfill ends, so that's as far as Unichat can tell.
- Sending files: pasting (⌘V in the box, or anywhere with a chat open, `WindowShortcuts`) sends copied files as they are and a copied picture (a browser's "Copy image") as a `PHOTO`, saved as a PNG in `cache/sending` (`ui/timeline/Pasting`: files win over text, text over a picture). The clip opens a menu (`Composer.attachMenu`: file, photos/videos, document = `m.file` whatever it is, many files, or many photos = a batch as `PHOTO`), each a `service/SendAs`. Photos (`PHOTO`) are made into what networks show as a photo: Telegram's bridge sends as a file any picture over ~16.7 MP (`image_as_file_pixels`), 10 MB or 10,000 px of width + height, i.e. every phone photo, and WebP/HEIC are photos nowhere; `matrix/OutgoingPhotos` + `video/SendablePhotos` make a JPEG of at most 2560 px with sips or ffmpeg (in `cache/sending`, kept a day), JPEG/PNG within those limits go as they are, GIFs and videos untouched, a failed conversion sends the original. A picture's size comes from its header (`support/ImageHeaders`), never by decoding it. Several files (or a drop of several) go through `service/UploadQueue`, one per service so it survives `relocalize`: one at a time, in order, a pause between them (bridges take bursts as spam). Reliable: a file that fails is tried again for as long as it takes (30 s doubling to 5 min; only a file gone from disk is given up), and the batch is kept in `uploads.json` (`uploads-demo.json` for the demo; this computer's paths, so it stays) and resumes after a restart. A file to a bridged chat is done when the bridge's `com.beeper.message_send_status` says the network has it (`matrix/SendStatuses`, 5 min patience), not when our server does: sending on before that piled hundreds of uploads in Telegram's bridge, all lost when its connection dropped; `ui/timeline/UploadBar` shows it on top like `AudioBar`. Upload progress comes from `matrix/UploadProgress` counting the request body. `-Dunichat.upload=<file>,<file>` (snapshot; `-Dunichat.uploadAs=PHOTO|DOCUMENT`) sends a batch to the open chat. A file in the chat shows a picture instead of its icon when it has one (`ui/media/FilePreview`: the attached `thumbnail_url`, else the file itself if it's a picture up to 15 MB).

- WhatsApp Business messages with buttons (orders to pay, links, template replies): the bridge marks them (`fi.mau.whatsapp.business_message_type`) and writes each button as a `<label>` line before "Use the WhatsApp app to click buttons"; `BusinessMessages` takes those out of the body and HTML into `Message.buttons` (labels as the bridge wrote them, often an internal name like `review_and_pay`) and names "Unsupported thumbnail message" (an order's picture) `business.order`. Only with the mark: someone's own `<text>` stays. The bridge can't pass a press on, so `ui/timeline/BusinessButtons` draws them as chips with a note.

- Stickers have a cache of their own (`MediaSource.sticker`, `cache/sticker-cache`): the newest seen `cache.stickerCount` (500) within `cache.stickerMb` (1 GB), the one seen longest ago first whatever its size (`MediaCache.trimOldest`), Ajustes → Privacidad; a sticker the media folder held moves in instead of downloading again (`StickerCacheTest`).

- Forwarding (`MessageSender.forward`, `ForwardedContent`): no mautrix bridge forwards natively from Matrix (bridgev2 has no forward event; "forward" in their code is backfill), so a forward is a copy sent as one's own, on the same network too: the text with its formatting and no one mentioned (person pills to plain names, `m.mentions: {}`: forwarded to Discord a mention would ping), a file at the same address unless it's a bridge's direct media, then a copy on our server (`needsCopy`), a sticker as stickers go (`sendSticker`, converted for the chat). Where it came from is the UI's optional line (`ui/timeline/ForwardNote`).

- Archived Discord rests out of the sync (`ArchiveRest`, `SyncFilter`): the person is in ~3 700 rooms, nearly all Discord channels, and each sync cost tuwunel ~0.4 s walking them (~0.03 s with them left out). Archived rooms inside a Discord server (`DiscordServers.serverSpaces`, the one "which server is this room in", through categories) go in `room.not_rooms`; never a DM or group DM (in no server, the bridge's folder included), another network, a chat that isn't archived, the chat open in the window (`setOpenChat`: opened from a search or a folder, its replies must come), nor anything while `notify.archived` is on or Archivados is open (`setArchiveOpen`, from `ui/chats/RestBar`; a hidden window doesn't leave it). A filter naming rooms is posted (`/user/{id}/filter`) once and named by id, kept by its content's hash here and in `matrix.syncFilters` (this computer's); an id the server answers 404/`M_NOT_FOUND` for is forgotten and posted again. A post that fails is tried again later (`Retry`), never every round: meanwhile what rests stays, unless rooms should wake, then nothing rests. The first sync and the cache refresh are always whole (`SyncFilter.forRequest(initial)`), so the cached token never skips what rested. Everything runs on the sync thread before a request (`beforeRequest`): the filter, then one part of the catch-up (100 rooms in their id order, so the same rooms are the same filters, no `since`, 20 events each), then the request with the `since` it had, which brings again whatever came after; a part under way finishes before what rests changes. Only the caught-up rooms count as seen (`caughtUp`). A catch-up that fails is tried again (`Retry`) and the bar says so; if its rooms rest again first, the retry and the bar go. `not_rooms` drops resting rooms' account data too, so their tags (unarchived elsewhere) come from a tags-only sync every `TAGS_EVERY` (5 min), of which only `account_data` is taken; rooms that start resting have their tags asked from the main sync's `next_batch`, or a change between the two is missed, after those already resting catch up on theirs from their own point (a forced tags sync), or theirs would be; if that forced sync fails, the next tags sync has no point and brings everything. A wake mid tags sync or mid filter post is no failure: the interrupt is left for the request after, and the next round asks again. Catch-up and tags syncs hold the sync thread, so they give up after 30 s (`sideTimeout`). Waking the computer mid catch-up is no failure: the next round goes on. A filter id forgotten (404) is posted again at once only once; refused again, it waits for the backoff. Opening a chat drops the long poll only when it, or the one before, is a room that rests (`ArchiveRestTest`, `DiscordRestSyncTest`).
- What each Discord server brings at the bridge is `ArchivedServers`', on a thread of its own: an archived server brings nothing, as before; opening Archivados sends no command (waking 123 servers one by one took minutes and flooded the bot chat, and the filter alone saves the sync). Only an archived server, or a channel in one, opened while in Archivados (`archivedChatOpened`) brings that one server back (`create-on-message`, "Reactivando <server>…"), until Archivados is left. `notify.archived` never changes the bridge: an archived server stays paused, so with it on only what the bridge still brings (channels of servers that aren't archived, single archived channels) can notify.
- "Load older chats" (`OlderChatSteps` decides each network's step, `OlderChatLoader` runs them one network at a time, `RoomArrivals` counts the rooms that come, behind `service/OlderChats` through `LoadsOlderChats`): only `load` runs anything. "Nothing more" (`olderChats.<net>.done`) belongs to an account: it goes when the network's login ids aren't those kept in `olderChats.<net>.login`, after a restart too (`BridgeAccounts.forgetOlderChatsOnNewLogin`). A command left unanswered, or a logout mid-step, writes no "nothing more", and a logout mid-restart puts the old limit back. Old chats arriving don't notify: `NotifyGate` lets through only what's under 5 minutes old and newer than anything seen in its chat, and history is older (`NotifyGateTest.aChatLoadedWithItsHistoryDoesntNotify`, `OlderChatsNotifyTest`). They arrive read: bridgev2 marks backfilled messages read only past `backfill.unread_hours_threshold` (720 h by default), so chats from the last 30 days would come unread; `OlderChatLoader` marks every room it counts read itself (`ChatActions.markReadHere`: counts to 0, `m.fully_read` and a private receipt, never a public `m.read` whatever `readReceipts` says: the person didn't open it), and again when its history comes, unless its newest message is newer than the step's start (news) (the person, 2026-11-24; `OlderChatsNotifyTest.aLoadLeavesTheUnreadBadgeAsItWas`).

## Lessons
- A catch-up of woken rooms (a sync without `since`, its timeline `limited`) ran on a thread of its own as first written: answered after a live sync had brought something newer, it reset the room (`resetTimeline`) and erased it, and its dispatch marked every chat seen, so a live message in another chat never notified. Found in review. Anything that syncs part of the rooms runs on the sync thread between two rounds (`ArchiveRest.beforeRequest`), and only its own rooms count as seen (`DiscordRestSyncTest.aCatchUpNeverErasesWhatCameAfterIt…`, `aLiveMessageInAnotherChatDuringAWakeStillNotifies`).
- An address a server suggests for itself (`.well-known`, the login's `well_known`) is a stranger's: taken as it came, a plain http one became the session's and the token went out in clear. `MatrixLogin.safeBase` (https, or http on this machine or its network) and `isHomeserver` both decide (`LoginWellKnownTest`).
- A message's addresses are its sender's to choose: a `file:` media URL from a message was opened as a local path (autosave copied `~/.ssh` keys to the cloud; on Windows a `file://host/share` leaks the login's hash). `MediaDownloader.media` opens a `file:` address only if `MessageSender` registered it as ours (`ownFile`, our local echo); `LocalFileUrlTest`.
- Networks only appeared after the first /sync: cached `list-logins` loaded after the sync and `accounts()` skipped networks without rooms; every start downloaded ~6 MB. Logins load at start, the last full sync is cached on disk and the network sync resumes from its token (`StartupBeforeSyncTest`, a fake homeserver with a 5 s /sync).
- 8 bot commands on virtual threads waiting on `synchronized (botLock)` used all 8 carriers and froze every background task (Java 21; JEP 491 removed that pinning in Java 24). `MatrixCore.io` stays a platform pool: don't fan work that takes `synchronized (proc)` onto virtual threads.
- Only an answer that says so means "start over": any error on the startup catch-up (a 429, a 502 while the server restarts) dropped the cached token and forced the whole multi-MB sync; `BotChat.addDirect` wrote `m.direct` from the cache after any failed GET, dropping the server's other direct chats. Fall back only on 400/404 (`sinceRejected`) and on 404/`M_NOT_FOUND`; busy and down answers go to the backoff or up (`CatchUpErrorTest`, `BotChatDirectTest`).
- `MatrixException` is unchecked: a `catch (IOException e)` lets it through. A failed reply lookup completed its future exceptionally, skipped the "forget a null" step and stayed cached for good; catch both (`ReplyLookupRetryTest`). Forget before completing, or the next asker races the cleanup.
- Whatever waits for something that may never come needs an end: `.part` files of a cut download (deleted on failure, and `MediaCache.trim` removes those over an hour old), `MediaDownloader.watching` keys (dropped with their last watcher), `MatrixRoom.pending` (the newest `SyncProcessor.MAX_PENDING` per room) (`DownloadLeftoversTest`, `MediaCacheTest`, `SyncProcessorTest`).
- The send's answer carries only `event_id`, so a confirmed echo kept the time sending started (before the upload), and an answer saved meanwhile moved autosave's mark past what I sent. When its event comes in the sync, `SyncProcessor.takeServerEvent` gives it `origin_server_ts` and tells `messagesChanged` (`SyncProcessorTest.aConfirmedEchoTakesTheServersTimeWhenItsEventComes`).
- A Discord server pause the bridge refused was logged as the exception's class name only ("failed: MatrixException") and never tried again, so an archived server kept bringing everything. Whatever goes to the server or a bridge on the person's behalf logs the reason and is retried (`Retry`: 1 min doubling to 1 h; `DiscordServers.retryGuildPauses` from `applyMutes`, `DiscordPauseRetryTest`).
- A media address is parsed once, with `model/Mxc` (server and id checked: no empty part, slash or control character); `startsWith("mxc://")` is only for "is it one".
- A Discord sticker (GIF) and a WhatsApp one (WebP) never reached Telegram: its bridge declares WebP "fully supported" yet passes everything but PNG/JPEG/WebM/Lottie through ffmpeg into WebP, and Homebrew's ffmpeg has no WebP encoder (`exit status 8` in the bridge's log). A bridge's room_features say what it takes, not what it can convert: read its `transferMediaToTelegram`-like code before trusting a type. Unichat now converts first (`StickerConverter.toTelegram`, `SendStickerTest.aStickerFromAnotherNetworkGoesToTelegram…`).
- A big group ("Furry Moonfest", 101 members) sat on top of the list with nothing to read: when every loaded event was a room change (joins, new names and pictures), `RoomFields` took the newest of those as the chat's activity. A `SYSTEM` line is still the preview but never moves the chat (`SyncProcessorTest.someoneJoiningOrChangingTheirPictureDoesntMoveTheChatUp`).
- A Discord sticker sent back to Discord failed ("Remote media not found … Federation is disabled"): `needsCopy` took for granted every bridge reads its own direct media, as Telegram's does, but the older mautrix-discord asks our server for it, which can't reach it. Now any direct media goes as a copy on our server, whatever the chat (`SendStickerTest.aBridgesDirectMediaAlwaysGoesAsACopy`); never hand a bridge a `media-<bridge>.localhost` address. Federation stays off on purpose.
- A Telegram video sticker (WebM) sent to Discord arrived as a video with a play button, not moving by itself: Unichat sent the WebM as it was. A WebM sticker now goes to every network but Telegram as an animated GIF (`StickerConverter.asGif`/`forChat`, `SendStickerTest.aTelegramVideoStickerGoesToDiscordAsAGifThatPlaysByItself`). How a network shows a format (play button or not) is part of "does it take it".
- A Telegram video sticker still reached Discord as a WebM that didn't load: Telegram's bridge converts WebM stickers (`convert_from_webm`) and still labels them video/webm, and ffmpeg, told to read a WebM, said "Invalid data found when processing input". A sticker goes as what its bytes are (`support/ImageHeaders.pictureMime`, `StickerConverter.forChat`; `SendStickerTest.aStickerLabelledWebmThatIsReallyAGifGoesAsTheGifItIs`), and a failed conversion logs what ffmpeg said: logging only the exception's class hid this for three tries.
- Forwarding, as first written, would have let a stranger run bridge admin commands as the person: bridges run any message of one's own that starts with their prefix (`!whatsapp …`, `BridgeConfig`) as a command, in any room (`bridgev2/queue.go`), and every message in a bot's chat. A stranger's text re-sent as one's own (forward, quote, AI draft) gets a zero-width space before a leading "!" (`ForwardedContent.notACommand`), never goes to a bridge's bot chat (`ChatFilter.writable(…, false)`), loses `app.unichat.original` (trusted on one's own messages), invisible marks in file names and the HTML the timeline never showed (`ForwardedContentTest`). Found by the security reviewer before it shipped.
- A friend's GIF from Telegram "arrived as an MP4" and went to Discord as a video with a play button: Telegram keeps every GIF as a silent MP4 (Telegram Desktop's `isGifv`: any silent H.264 video up to 10 MB, whatever its length), and its bridge sends `m.video` `video/mp4` marked `fi.mau.gif` (seen in the real events). Telegram's and WhatsApp's bridges pass the mark on; Discord's shows a video. Forwarded anywhere else it goes as an animated WebP made from the MP4 (`StickerConverter.gifVideoAsPicture`, `video/GifVideos.webpUnder`, `ForwardedContent.becomeWebp`): Discord plays it by itself, every colour, light; as the video when it has sound, is the size of a camera's (over 720 px on its longest side by default, Ajustes → Redes 320/480/640/720: Telegram marks any silent video up to 10 MB as a GIF, a phone's clip too; `GifVideos.camera`), lasts longer or weighs more than Ajustes → Redes allows (any length and 10 MB by default), ffmpeg or img2webp can't, or the forward sheet or Ajustes turned it off (`SendStickerTest.aGifThatCameAsAVideo…`, `GifVideosTest`). Look at the room's real events (`/messages` with the session's token) before guessing what a bridge sent.
- Made a GIF first, they weighed 50 times the video (a 3 s, 430 KB MP4 became 22.7 MB; a 26 s one 110 MB, so it always went as the video): GIF made at the video's own frame rate and size. An animated WebP from the MP4's frames as they come, size and rate (the person's choice; only past 900 frames fewer a second; ffmpeg writes them as PAM; `img2webp`, built with gif2webp, puts them together, run in their folder so hundreds of names fit Windows' command line) keeps every colour at a fraction of it. Measure a conversion on the person's real files before blaming the limit.
- Which format each network got for stickers and GIFs was decided by a check in each place (`forTelegram`, `asGif`, `gifVideoAsPicture`, `target`, flags threaded through `forChat`): changing a network meant finding them all. It's one table now (`NetworkFormats.of`: what its bridge sends on, what an animated and a still one become, whether a GIF that came as an MP4 goes as it is), the chat's room_features still narrowing it (`byFeatures`), and `StickerConverter` only converts from a format to another, each way falling back to the next best (`to`). A network, or a change of mind about one, is a line in the table (`StickerConverterTest`).
- A Telegram video sticker forwarded to Discord still went as a GIF, not the animated WebP: the bridge made every WebM sticker a GIF before Unichat got it (`convert_from_webm: true`, set when Unichat couldn't show WebM; still labelled video/webm), so there was no WebM left to make one from. Now `false` (`server/BridgeConfig`): video stickers come as the WebM they are, shown converted (`video/WebmStickers.animated`, `ui/media/MessageMedia.loadMedia`) and forwarded as WebP with their transparency; Lottie comes as it is too now, drawn by Unichat (`video/LottieStickers`) (`BridgeConfigTest`). Stickers that came before stay GIFs.
- A WebP or GIF someone pastes as a link in Discord (not uploaded) comes through the bridge as the link's preview: one still frame Discord's proxy made (`m.image`, body the link). The link itself can't be fetched to animate it: Discord answers 404 to an attachment link without its signature (`?ex=…&is=…&hm=…`), which only a logged-in client (the bridge) gets.
- A sticker sent as Unichat restarted (memory) reached Discord's bridge while it was still connecting: "user is not logged in and portal doesn't have webhook", FAIL_PERMANENT, three seconds before it was connected; the message stayed failed. That refusal is the bridge not ready, not the network (`SyncProcessor.bridgeNotReady`): `MessageSender` remembers the last 200 events it sent and sends one again after 15, 30 and 60 s (`sendAgainWhenReady`), then redacts the failed one, which leaves the chat instead of showing as deleted (`SendStatusTest`, `SendStickerTest.aMessageTheBridgeWasntReadyFor…`).
- A Telegram sticker still went to Discord as a GIF: the GIF was the sticker's own (a set cached a week from before the bridge kept WebM, or a Lottie one: Telegram's .tgs is gzipped Lottie JSON that nobody else reads, Discord's and WhatsApp's own Lottie stickers aside, so the bridge makes it a GIF). Discord and the rest now get an animated GIF as the lighter animated WebP (gif2webp), as the GIF when that can't be made (`NetworkFormats.Rule.ifUnmade`) (`SendStickerTest.anAnimatedGifStickerGoesToDiscordAsAnAnimatedWebp`).
- The sync thread ended for good on an `OutOfMemoryError` after waking (it caught `Exception` only), and the top bar kept "Conectando…" (set on waking, cleared only by a sync): nothing ends the sync but stopping, any error is a pause and another round from `nextBatch` (`MatrixChatService.syncLoop`/`survived`, `WakeSyncTest.anErrorInsideTheSyncDoesNotEndIt`). A loop the app can't live without catches `Throwable`.
- A Telegram animated sticker (Lottie) went to Discord and WhatsApp as the .tgs it was, which only Telegram reads. `StickerConverter.forChat` tells Lottie by its bytes (it comes labelled application/x-tgsticker, or video/lottie+json), makes it an animated WebP (`video/LottieStickers`; a still PNG where a chat takes only that) and sends Telegram its JSON, which its bridge gzips itself: a .tgs would be gzipped twice (`StickerConverterTest.aLottieStickerGoesAsAnAnimatedWebp…`). A sticker labelled video/lottie+json is drawn, never played as a video (`Message.playsInline`).
- A frames folder (`….frames.part`, a whole picture a frame, `video/AnimatedWebp`) left by a run that ended mid-way stayed in the cache for good: `MediaCache` deleted leftovers as files, which a full folder refuses in silence. Folders go whole (`MediaCacheTest.aFramesFolderLeftByARunCutShortGoesWithWhatsInIt`).
- A Telegram voice note forwarded to Telegram (Jecht's chat, 2026-11-17) came back "Your message was not bridged: unsupported media type (audio/ogg in m.audio)": the forward kept only `info`, so it went as a plain audio file, and Telegram's room_features take Ogg only under `org.matrix.msc3245.voice`. A voice note keeps what makes it one (`Message.voiceWaveform`, from `SyncEvents`) and a forward marks it again where the chat has voice notes (`MessageSender.keepVoice`, `SendStickerTest.aForwardedVoiceNoteGoesAsAVoiceNoteWithItsWaveform`). A forward carries every mark a bridge reads, not just the file.
- A voice note or file I sent had no "Reenviar" (Telegram, 2026-11-23): its echo shows it from disk (`file:`), `confirmLocalEcho` kept that address and its event, already known by id, only gave the time, so `MessageActions` (only a media address goes on) never offered it. A known message of mine takes its event's media fields too (`SyncEvents.takesServerMedia`/`applyMedia`, `SyncProcessorTest.aConfirmedEchoOfMyVoiceNoteTakesItsServerAddressAndWaveform`), and `MediaDownloader.uploaded` maps the address to the file on disk, while its size and time are as sent, so playing it doesn't download it back (`SendVoiceTest.whatISentPlaysFromDiskAtItsServerAddressToo`, `aFileChangedAfterSendingIsDownloadedNotShownAsWhatWasSent`). An echo's stand-in field (`file:` address, temporary id, start time) is replaced by the server's when its event comes, every one of them.
- `BridgeProtocol.LOGIN_LINE` began `(?m)^\s*`, and `\s` crosses line ends: each blank line of a bot's answer began a scan over every blank line after it. A line's start is `^[ \t]*` (`LoginsParsingTest.aBotAnswerIsReadInLinearTimeWhateverItsBlankLines`, `app.unichat.CountedReads`). Found by the security reviewer.
- `ArchiveRestTest`'s two waking tests (and `aChatOpenedOutsideTheArchiveBringsNoServerBack`) read the interrupt count, or the log, as soon as a future of `ArchiveRest` completed, but it completes inside `beforeRequest`, and the loop takes the interrupt and logs its request just after, on its own thread: under load they read first (failures in 1 run of 7, three in six of the class). Those tests wait for the loop's round to end (`settled`, `rounds`, `server.changes`). A future that completes mid-step says nothing about what comes after the step: wait for the step's own end.
- `ArchiveRestTest.openingTheArchiveWakesTheFilterAtOnceAndSendsNoBridgeCommand` was left out of that fix and failed on CI's Linux: it read the log as soon as `setArchiveOpen(true)` completed, before the loop logged the request with the filter (none in the log), and its count before it was taken after `archivedChanged()`'s future, so that round's request could land among the waking's. Both wait with `settled` now (a 50 ms pause in the test's loop after `beforeRequest` showed both; the other 28 tests held). A test reading what the loop logs after a future waits for the round, before every count it takes too.
- Forwarding a stranger's sticker whose event named no type threw from `forward` itself (`NetworkFormats.sticker`'s `Set.of(…).contains(null)`), so the echo stayed "sending". A sticker with no type is one its bridge doesn't send on: it's read for what its bytes are and converted (`SendStickerTest.aForwardedStickerThatSaysNoTypeGoesAsWhatItsBytesAre`). NullAway found it once `matrix` was marked; look up a nullable only after its null check.
- `MatrixRoom.prevBatch == null` meant both "never had a token" and "the start is loaded", and the next sync's `prev_batch` refilled it: after the start, a new message brought "Cargar mensajes anteriores" back and each click paged through what was already loaded (found in review).
