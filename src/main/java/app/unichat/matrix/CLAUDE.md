# matrix — notes for Claude

`ChatService` over Matrix: sync, sending, bridges seen from the client. `MessageHtml` writes link previews as HTML that `ui/timeline/HtmlView` draws: `ui/timeline/CLAUDE.md`.

- `matrix/` — `MatrixChatService` (facade: lifecycle, sync loop) over `MatrixCore` (shared), `MessageSender`, `ChatActions`,
  `BridgeAccounts`, `DiscordServers`, `ContactActions`, `MediaDownloader`, `SyncCache`, `MatrixLogin`, `Profiles`, `Invites`, `FetchedMessages`; `SyncProcessor`
  (pure /sync → model, unit tested) with `RoomFields`, `SystemMessages`, `SyncEvents`; `BridgeProtocol` (pure), `BotChat`, `MatrixClient` (HTTP). `MatrixLiveIT` = end-to-end test, needs `UNICHAT_IT_HOMESERVER`.
- Media cache: `matrix/MediaCache` caps `cache/media`
  (`cache.mediaMb`, LRU; files over 1 MB go first, saved stickers/GIFs are pinned, `MediaSource.keepCached`; one file per direct-media URL whatever the size). `model/MediaLibrary.same` says when two items are one sticker (bridge id, else format, dimensions and bytes), since direct media gives the same file a new URL in each message.
- Read receipts (`Settings.readReceipts`, Ajustes → Privacidad): ALWAYS sends `m.read` on opening a chat; ON_REPLY and NEVER send `m.read.private`, which tuwunel never passes to appservices, so the bridge never tells the network; ON_REPLY then sends a public `m.read` for the newest message of someone else just before each message we send (`MessageSender.readOnReply`). The person's phone app still marks read on its own.
- Formatting what's sent: WhatsApp's marks (`*bold*`, `_italic_`, `~strike~`, `` `code` ``, ```` ``` ```` blocks, `> ` quotes) plus Discord's `__underline__` and `||spoiler||` become `formatted_body` (`model/Markup`, pure; nothing inside a word, code or a link), which each bridge writes its network's way; with no marks the message is plain text as before. The box's right-click menu (`ui/timeline/FormatMenu`, ⌘B ⌘U ⌘⇧X) offers only what the chat's bridge lists in `formatting` (`RoomFeatures.formats`) and wraps or unwraps the selection (`model/TextFormat`).
- Bridges send `com.beeper.message_send_status` for each message (`BridgeConfig`: `message_status_events`, plus the error notice that says why); `SyncProcessor.applySendStatus` marks ours FAILED when the network refused it, so a message never looks sent when it wasn't.
- Staying current: `support/WakeWatch` notices the computer waking (macOS stops awake time while asleep, so a long poll left open would wait out its timeout on a dead connection); `MatrixChatService.wake` drops it and catches up at once. The top bar (`MainView.showConnection`) says "Conectando…" until the server answered and "Sincronizando <redes>…" while a network's bridge reconnects (`AccountAlerts.syncingLine`); bridges never report when their backfill ends, so that's as far as Unichat can tell.
- Sending files: pasting (⌘V in the box, or anywhere with a chat open, `WindowShortcuts`) sends copied files as they are and a copied picture (a browser's "Copy image") as a `PHOTO`, saved as a PNG in `cache/sending` (`ui/timeline/Pasting`: files win over text, text over a picture). The clip opens a menu (`Composer.attachMenu`: file, photos/videos, document = `m.file` whatever it is, many files, or many photos = a batch as `PHOTO`), each a `service/SendAs`. Photos (`PHOTO`) are made into what networks show as a photo: Telegram's bridge sends as a file any picture over ~16.7 MP (`image_as_file_pixels`), 10 MB or 10,000 px of width + height, i.e. every phone photo, and WebP/HEIC are photos nowhere; `matrix/OutgoingPhotos` + `video/SendablePhotos` make a JPEG of at most 2560 px with sips or ffmpeg (in `cache/sending`, kept a day), JPEG/PNG within those limits go as they are, GIFs and videos untouched, a failed conversion sends the original. A picture's size comes from its header (`support/ImageHeaders`), never by decoding it. Several files (or a drop of several) go through `service/UploadQueue`, one per service so it survives `relocalize`: one at a time, in order, a pause between them (bridges take bursts as spam). Reliable: a file that fails is tried again for as long as it takes (30 s doubling to 5 min; only a file gone from disk is given up), and the batch is kept in `uploads.json` (`uploads-demo.json` for the demo; this computer's paths, so it stays) and resumes after a restart. A file to a bridged chat is done when the bridge's `com.beeper.message_send_status` says the network has it (`matrix/SendStatuses`, 5 min patience), not when our server does: sending on before that piled hundreds of uploads in Telegram's bridge, all lost when its connection dropped; `ui/timeline/UploadBar` shows it on top like `AudioBar`. Upload progress comes from `matrix/UploadProgress` counting the request body. `-Dunichat.upload=<file>,<file>` (snapshot; `-Dunichat.uploadAs=PHOTO|DOCUMENT`) sends a batch to the open chat. A file in the chat shows a picture instead of its icon when it has one (`ui/media/FilePreview`: the attached `thumbnail_url`, else the file itself if it's a picture up to 15 MB).

- WhatsApp Business messages with buttons (orders to pay, links, template replies): the bridge marks them (`fi.mau.whatsapp.business_message_type`) and writes each button as a `<label>` line before "Use the WhatsApp app to click buttons"; `BusinessMessages` takes those out of the body and HTML into `Message.buttons` (labels as the bridge wrote them, often an internal name like `review_and_pay`) and names "Unsupported thumbnail message" (an order's picture) `business.order`. Only with the mark: someone's own `<text>` stays. The bridge can't pass a press on, so `ui/timeline/BusinessButtons` draws them as chips with a note.

- Stickers have a cache of their own (`MediaSource.sticker`, `cache/sticker-cache`): the newest seen `cache.stickerCount` (500) within `cache.stickerMb` (1 GB), the one seen longest ago first whatever its size (`MediaCache.trimOldest`), Ajustes → Privacidad; a sticker the media folder held moves in instead of downloading again (`StickerCacheTest`).

- Forwarding (`MessageSender.forward`, `ForwardedContent`): no mautrix bridge forwards natively from Matrix (bridgev2 has no forward event; "forward" in their code is backfill), so a forward is a copy sent as one's own, on the same network too: the text with its formatting and no one mentioned (person pills to plain names, `m.mentions: {}`: forwarded to Discord a mention would ping), a file at the same address unless it's a bridge's direct media, then a copy on our server (`needsCopy`), a sticker as stickers go (`sendSticker`, converted for the chat). Where it came from is the UI's optional line (`ui/timeline/ForwardNote`).

## Lessons
- An address a server suggests for itself (`.well-known`, the login's `well_known`) is a stranger's: taken as it came, a plain http one became the session's and the token went out in clear. `MatrixLogin.safeBase` (https, or http on this machine or its network) and `isHomeserver` both decide (`LoginWellKnownTest`).
- A message's addresses are its sender's to choose: a `file:` media URL from a message was opened as a local path (autosave copied `~/.ssh` keys to the cloud; on Windows a `file://host/share` leaks the login's hash). `MediaDownloader.media` opens a `file:` address only if `MessageSender` registered it as ours (`ownFile`, our local echo); `LocalFileUrlTest`.
- Networks only appeared after the first /sync: cached `list-logins` loaded after the sync and `accounts()` skipped networks without rooms; every start downloaded ~6 MB. Logins load at start, the last full sync is cached on disk and the network sync resumes from its token (`StartupBeforeSyncTest`, a fake homeserver with a 5 s /sync).
- 8 bot commands on virtual threads waiting on `synchronized (botLock)` used all 8 carriers and froze every background task (Java 21; JEP 491 removed that pinning in Java 24). `MatrixCore.io` stays a platform pool: don't fan work that takes `synchronized (proc)` onto virtual threads.
- Only an answer that says so means "start over": any error on the startup catch-up (a 429, a 502 while the server restarts) dropped the cached token and forced the whole multi-MB sync; `BotChat.addDirect` wrote `m.direct` from the cache after any failed GET, dropping the server's other direct chats. Fall back only on 400/404 (`sinceRejected`) and on 404/`M_NOT_FOUND`; busy and down answers go to the backoff or up (`CatchUpErrorTest`, `BotChatDirectTest`).
- `MatrixException` is unchecked: a `catch (IOException e)` lets it through. A failed reply lookup completed its future exceptionally, skipped the "forget a null" step and stayed cached for good; catch both (`ReplyLookupRetryTest`). Forget before completing, or the next asker races the cleanup.
- Whatever waits for something that may never come needs an end: `.part` files of a cut download (deleted on failure, and `MediaCache.trim` removes those over an hour old), `MediaDownloader.watching` keys (dropped with their last watcher), `MatrixRoom.pending` (the newest `SyncProcessor.MAX_PENDING` per room) (`DownloadLeftoversTest`, `MediaCacheTest`, `SyncProcessorTest`).
- The send's answer carries only `event_id`, so a confirmed echo kept the time sending started (before the upload), and an answer saved meanwhile moved autosave's mark past what I sent. When its event comes in the sync, `SyncProcessor.takeServerTime` gives it `origin_server_ts` and tells `messagesChanged` (`SyncProcessorTest.aConfirmedEchoTakesTheServersTimeWhenItsEventComes`).
- A Discord server pause the bridge refused was logged as the exception's class name only ("failed: MatrixException") and never tried again, so an archived server kept bringing everything. Whatever goes to the server or a bridge on the person's behalf logs the reason and is retried (`Retry`: 1 min doubling to 1 h; `DiscordServers.retryGuildPauses` from `applyMutes`, `DiscordPauseRetryTest`).
- A media address is parsed once, with `model/Mxc` (server and id checked: no empty part, slash or control character); `startsWith("mxc://")` is only for "is it one".
- A Discord sticker (GIF) and a WhatsApp one (WebP) never reached Telegram: its bridge declares WebP "fully supported" yet passes everything but PNG/JPEG/WebM/Lottie through ffmpeg into WebP, and Homebrew's ffmpeg has no WebP encoder (`exit status 8` in the bridge's log). A bridge's room_features say what it takes, not what it can convert: read its `transferMediaToTelegram`-like code before trusting a type. Unichat now converts first (`StickerConverter.toTelegram`, `SendStickerTest.aStickerFromAnotherNetworkGoesToTelegram…`).
- A big group ("Furry Moonfest", 101 members) sat on top of the list with nothing to read: when every loaded event was a room change (joins, new names and pictures), `RoomFields` took the newest of those as the chat's activity. A `SYSTEM` line is still the preview but never moves the chat (`SyncProcessorTest.someoneJoiningOrChangingTheirPictureDoesntMoveTheChatUp`).
- A Discord sticker sent back to Discord failed ("Remote media not found … Federation is disabled"): `needsCopy` took for granted every bridge reads its own direct media, as Telegram's does, but the older mautrix-discord asks our server for it, which can't reach it. Now any direct media goes as a copy on our server, whatever the chat (`SendStickerTest.aBridgesDirectMediaAlwaysGoesAsACopy`); never hand a bridge a `media-<bridge>.localhost` address. Federation stays off on purpose.
- A Telegram video sticker (WebM) sent to Discord arrived as a video with a play button, not moving by itself: Unichat sent the WebM as it was. A WebM sticker now goes to every network but Telegram as an animated GIF (`StickerConverter.asGif`/`forChat`, `SendStickerTest.aTelegramVideoStickerGoesToDiscordAsAGifThatPlaysByItself`). How a network shows a format (play button or not) is part of "does it take it".
- A Telegram video sticker still reached Discord as a WebM that didn't load: Telegram's bridge converts WebM stickers (`convert_from_webm`) and still labels them video/webm, and ffmpeg, told to read a WebM, said "Invalid data found when processing input". A sticker goes as what its bytes are (`support/ImageHeaders.pictureMime`, `StickerConverter.forChat`; `SendStickerTest.aStickerLabelledWebmThatIsReallyAGifGoesAsTheGifItIs`), and a failed conversion logs what ffmpeg said: logging only the exception's class hid this for three tries.
- Forwarding, as first written, would have let a stranger run bridge admin commands as the person: bridges run any message of one's own that starts with their prefix (`!whatsapp …`, `BridgeConfig`) as a command, in any room (`bridgev2/queue.go`), and every message in a bot's chat. A stranger's text re-sent as one's own (forward, quote, AI draft) gets a zero-width space before a leading "!" (`ForwardedContent.notACommand`), never goes to a bridge's bot chat (`ChatFilter.writable(…, false)`), loses `app.unichat.original` (trusted on one's own messages), invisible marks in file names and the HTML the timeline never showed (`ForwardedContentTest`). Found by the security reviewer before it shipped.
- A friend's GIF from Telegram "arrived as an MP4" and went to Discord as a video with a play button: Telegram keeps every GIF as a silent MP4, and its bridge sends `m.video` `video/mp4` marked `fi.mau.gif` (seen in the real events). Telegram's and WhatsApp's bridges pass the mark on; Discord's shows a video. Forwarded anywhere but those two, it goes as a real GIF (`StickerConverter.gifAsGif`, `video/GifVideos`, `ForwardedContent.becomeGif`; the video if ffmpeg can't), and it's saved as a `.gif` too (`ui/media/MediaSaver`, `autosave/SavedFile`) (`SendStickerTest.aGifThatCameAsAVideo…`, `SavedFileTest`). Look at the room's real events (`/messages` with the session's token) before guessing what a bridge sent.
