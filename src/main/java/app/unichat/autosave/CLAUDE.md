# autosave — notes for Claude

Saving what others send in a chat, by kind, as it arrives and back through its past.

`AutoSave` is the facade everything outside the package uses (`of`, `explore`, `setBase`, `Progress`, `Exploring`…), with the one saving thread; behind it, one job each: `LiveSaving` (saving as messages arrive, the round's count for the menu-bar ring, the failure notices), `Holds` (a chat held by a failure for now: the timed retry, its count, what was told already), `PastExplorer` (exploring the past: pages, what it's doing, stopping), `SavedFile` (a message's file written into a folder, for both), `SavedMove` (a folder changed and what was saved moved along).

- Saving what a chat receives (`autosave/AutoSave`): the gear among the chat's profile actions opens its options (`ui/chats/ChatOptions`), where it's turned on and each kind chosen apart (`model/SaveKind`: photos, videos, audio, documents, GIFs, link videos; never stickers), in preferences.json (`Flag.AUTO_SAVE` plus one "left out" flag per kind, so what was on before kinds existed stays all; `ChatPreferences.setAutoSave/autoSaves`). It saves as soon as messages are there, chat opened or not: every `messagesChanged` (live or catching up after sleep or a restart) saves what others sent after the last one saved (`autosave/SavedUpTo`, `autosave.json`, exact instants; turning it on starts now: never the history). Started with the service (`UnichatApp.showMain`), not the window. Media through `FileNames` (as "Guardar como…", never overwriting), links (`support/Urls.in`) with `video/YtDlp` (pinned, downloaded on first use; one video, never the playlist, up to 1080p, the link after `--`; its own error line is the reason). Folders (`autosave/SaveFolders`, `autosave.` keys stay on this machine): a base in Ajustes → Redes (`~/Downloads/Unichat` unless chosen; `-Dunichat.autosaveDir`, which surefire points into target/), one folder per chat under it or a chat's own from its options. `AutoSave.Progress` feeds the menu-bar icon (`Notifier.setDownloadProgress`: a ring that fills, spinning until the first is done; the helper's `progress` command, the AWT tray draws it too) and the notices: done (how many, from which chat) and, always, what failed with why (no space, measured where it was going; no permission; yt-dlp's reason). Ajustes → Notificaciones turns the ring and the done notice off (`downloads.trayProgress`, `downloads.notifyDone`). The options' "Lo anterior" explores the past (`AutoSave.explore`): page by page back to the beginning (`ChatReader.loadOlder`), each page a job of its own so what arrives isn't kept waiting, only the kinds chosen, older than what was saved live, continuing where it stopped (`SavedUpTo.Back`); what's gone is counted and told once, no space stops it. The saved files are an archive: a message deleted, seen once or expired never deletes its copy.
- Changing a folder (the base in Ajustes → Redes, or a chat's own) takes along what was saved (`AutoSave.setBase` / `setOwn` on the saving thread, `autosave/SavedMove.toBase` / `toOwn`: file by file, merged, nothing overwritten, the old folder removed once empty) and says how many moved (`ui/chats/FolderMoves`); from the base only each chat's own folder moves, never the base whole: it may hold the person's own things. Without it the new folder started empty and the saved files looked lost.
- Exploring the past says what it's doing as it goes (`AutoSave.Exploring.now`: going through a day's messages, downloading a file of it, asking the server for older ones; and how many looked at, saved, gone), shown live with a moving bar in the chat's options (`ChatOptions.pastState`): "Buscando…" alone for minutes said nothing.
- Saved files are named as sent plus the message's Matrix id (`FileNames.forSaving`: "IMG_3944 [id].MOV"; yt-dlp's too, `YtDlp.command`): never overwritten, still recognizable, and known again (`FileNames.savedIn`), so nothing is saved twice. Written under a hidden ".part" name and renamed once whole (`autosave/SavedFile.copyInto`, shared by both): nothing takes a half-written file.
- Stopping exploring (`AutoSave.stopExploring`) interrupts the download going on (yt-dlp is killed with it, `Processes`), isn't counted, shows "Deteniendo…" at once, and leaves the thread clean for saving as it arrives; it used to wait for the file to end, silently. Exploring a chat that got to its beginning starts over from the newest (`SavedUpTo.forgetBack`), finding what's saved already: pressing it used to do nothing.
- What I send can be saved too, with its own kinds ("Guardar lo que yo envíe", `Flag.AUTO_SAVE_MINE*`, `ChatPreferences.autoSaves(chatId, mine)`); `autosave/Wanted` picks the kinds by who sent the message, for arrivals and exploring alike. What I send counts only once the server has it (not `SENDING` nor `FAILED`): its local echo has a temporary id (`local:uc…`), and saving it then saved the same file twice.
- A downloading file reports how much arrived (`MediaSource.media(…, progress)` from `MatrixClient.copyTelling`, yt-dlp's "[download] 45%" lines via `Processes.capture(…, eachLine)`), shown in the options and in `ui/chats/ExploreBar`, on top of the window while a chat's past is explored (closing the options doesn't hide it; "Detener" there too).
- A video that came with its page (Instagram reels) isn't downloaded again from the page (`AutoSave.links`): it saved the same reel twice, the second in VP9. What yt-dlp saves is H.264/AAC whatever the site gave (`-S vcodec:h264`, then `VideoTranscoder.makePlayable` on anything else, in place, whole or not at all): a Mac doesn't open VP9.
- `LinkVideo` uses the same engine for a reel the bridge gave only as its picture: its video fetched once into `cache/media` (`reel-<hash>.<ext>`, the engine's folder hidden and named ".part" so the cache trims it if cut short) for the player (`ui/media/MediaOpening.reel`).
- What a link leads to is saved by InstaTray's engine (`instatray.core`, the user's own library, JitPack `com.github.vaoan:InstaTray:core-1.0.1`, 0BSD) through `autosave/LinkSaver`: its sites and catch-all for anything yt-dlp knows, gallery-dl for the ones yt-dlp doesn't (if the person has it, `video/GalleryDl`), each site's cookies from `*cookie*.txt` in Downloads, permanent vs retryable failures. Unichat keeps its own: the chat's folder, the message's id (`Fetch.Request.nameTag`), the progress, H.264 for anything else (`VideoTranscoder.makePlayable`), and only `http(s)://` text ever reaches a tool (the engine also ends options with "--"). Improving downloads is done in InstaTray's `core/` and released with a new tag. `YtDlp` only keeps yt-dlp's pinned binary ready.
- A link can be saved on demand, auto-save on or off for its chat: a message's menu (right click, Enter) has "Guardar enlace: …" for each of `AutoSave.links(m)` (up to five; `ui/timeline/MessageActions.Action.SAVE_LINK`), which runs `AutoSave.saveLink(m, url)` on the saving thread (`LiveSaving.saveAsked`): the same engine, the chat's folder (`SaveFolders.of`), the message's id in the name (so saving later knows it), H.264, counted on the menu-bar ring and told through `Progress` like any round; its failure is told every time (with its message), never held. Files a link saves are marked with Mark-of-the-Web too (`LinkSaver.save`), as received files are.

- A GIF that came as a video (Telegram's and WhatsApp's are silent MP4s marked `fi.mau.gif`) is saved as the MP4 it is: the person chose that over a GIF (heavy, 256 colours) or a WebP (not every program animates it). Only forwarding changes it (`matrix/CLAUDE.md`).

## Lessons
- A file from a stranger is named and marked as a browser would: `FileNames.safe` drops invisible format characters (`\p{Cf}`: a right-to-left override, U+202E, made an `.exe` read as a `.pdf`) and leading dots (hidden files were skipped by `savedIn` and `SavedMove`, so saved again on every explore), and `SavedFile.copyInto` writes Windows' Mark-of-the-Web (`support/MarkOfTheWeb`, ZoneId=3) so SmartScreen asks before a received `.exe` runs.
- A failed live save was marked done (`SavedUpTo.saved` ran anyway): no space, a dropped network or a failed yt-dlp lost those files for good. Each failure is a `Failure`, for good (`AutoSave.Gone`: `MediaSource.gone`, a 404/410; InstaTray's `FAILED_PERMANENT`, plus a timeout or a missing tool, which would hold the chat for hours or forever) or for now; for now stops the chat's round at that message (`LiveSaving`, the hold kept by `Holds`), so the next `messagesChanged` tries it again, and it's told once until the chat gets past it (`AutoSaveTest`).
- Explorer acts on a `.url`, `.lnk`, `.scf`, `.library-ms`, `.searchConnector-ms`… just by listing the folder (a `\\host\share` icon sends the NTLM hash): `FileNames.forSaving` adds ".txt" to them on every system (the folder may be synced to Windows), after the id tag, so `savedIn` still knows them.
- A failure for now that never cleared (a full disk, an error yt-dlp's words don't place) held the chat for good, and a quiet chat tried again only at its next message. A held chat also tries again by itself every `AutoSave.RETRY_AFTER` (30 min; tests pass zero), and after `MAX_TIMED_TRIES` (48: a day) of those it's let go as for good, told once (only at the first failure), so what came after is saved. The chat's own changes don't count as tries: a busy group would give up in minutes (`AutoSaveTest.aFailureThatNeverClearsIsTriedAgainByItselfThenLetGo`).
- A chat's folder under the base followed its title, which anyone in a group can change: its files split into a new folder and exploring saved them all again. `SaveFolders.name` keeps the first name per chat id (`autosave.folder.name.<id>`, on this machine) (`SaveFoldersTest`).
- A Linktree profile (yt-dlp's `[generic]`, HTTP 403 each time) was a failure "for now", so it held every later file of its chat and was tried again at each change (five times in a day). A page no site knows that answers 4xx has nothing to save: for good (`LinkSaver.NOTHING_THERE`); a known site's 403 (rate limiting) and any 5xx are still tried again (`LinkSaverTest.aPageNoSiteKnowsThatRefusesHasNothingToSave`).
- A failure's notice led nowhere: `Progress.failed` carries the message it came in, and the notice's click goes to it (`ui/desktop/NotificationTarget`, `<chat>#<message>`; `MainView.showMessage`).
- Every reel sent to Pablo BM was saved twice: the bridge gives one's own reel back as its video with its link written in the text ("[https://…/reel/X/](https://…/reel/X/?igsh=…)"), and `links` only skipped `external_url`. A video's text links to its own page are skipped too (`Urls.samePage`), and an address ends where a Markdown link's text does (`Urls.ADDRESS`: that one was a single address of both, handed to yt-dlp) (`AutoSaveTest.aReelsLinkInItsOwnTextIsntDownloadedAgain`, `UrlsTest`).
