# autosave — notes for Claude

Saving what others send in a chat, by kind, as it arrives and back through its past. The rules, commands and map are in the root `CLAUDE.md`.

- Saving what a chat receives (`autosave/AutoSave`): the gear among the chat's profile actions opens its options (`ui/ChatOptions`), where it's turned on and each kind chosen apart (`model/SaveKind`: photos, videos, audio, documents, GIFs, link videos; never stickers), in preferences.json (`Flag.AUTO_SAVE` plus one "left out" flag per kind, so what was on before kinds existed stays all; `ChatPreferences.setAutoSave/autoSaves`). It saves as soon as messages are there, chat opened or not: every `messagesChanged` (live or catching up after sleep or a restart) saves what others sent after the last one saved (`autosave/SavedUpTo`, `autosave.json`, exact instants; turning it on starts now: never the history). Started with the service (`UnichatApp.showMain`), not the window. Media through `FileNames` (as "Guardar como…", never overwriting), links (`support/Urls.in`) with `video/YtDlp` (pinned, downloaded on first use; one video, never the playlist, up to 1080p, the link after `--`; its own error line is the reason). Folders (`autosave/SaveFolders`, `autosave.` keys stay on this machine): a base in Ajustes → Redes (`~/Downloads/Unichat` unless chosen; `-Dunichat.autosaveDir`, which surefire points into target/), one folder per chat under it or a chat's own from its options. `AutoSave.Progress` feeds the menu-bar icon (`Notifier.setDownloadProgress`: a ring that fills, spinning until the first is done; the helper's `progress` command, the AWT tray draws it too) and the notices: done (how many, from which chat) and, always, what failed with why (no space, measured where it was going; no permission; yt-dlp's reason). Ajustes → Notificaciones turns the ring and the done notice off (`downloads.trayProgress`, `downloads.notifyDone`). The options' "Lo anterior" explores the past (`AutoSave.explore`): page by page back to the beginning (`ChatReader.loadOlder`), each page a job of its own so what arrives isn't kept waiting, only the kinds chosen, older than what was saved live, continuing where it stopped (`SavedUpTo.Back`); what's gone is counted and told once, no space stops it. The saved files are an archive: a message deleted, seen once or expired never deletes its copy.
- Changing a folder (the base in Ajustes → Redes, or a chat's own) takes along what was saved (`AutoSave.setBase` / `setOwn` on the saving thread, `autosave/SavedMove`: file by file, merged, nothing overwritten, the old folder removed once empty) and says how many moved (`ui/FolderMoves`); from the base only each chat's own folder moves, never the base whole: it may hold the person's own things. Without it the new folder started empty and the saved files looked lost.
- Exploring the past says what it's doing as it goes (`AutoSave.Exploring.now`: going through a day's messages, downloading a file of it, asking the server for older ones; and how many looked at, saved, gone), shown live with a moving bar in the chat's options (`ChatOptions.pastState`): "Buscando…" alone for minutes said nothing.
- Saved files are named as sent plus the message's Matrix id (`FileNames.forSaving`: "IMG_3944 [id].MOV"; yt-dlp's too, `YtDlp.command`): never overwritten, still recognizable, and known again (`FileNames.savedIn`), so nothing is saved twice. Written under a hidden ".part" name and renamed once whole (`AutoSave.copyInto`): nothing takes a half-written file.
- Stopping exploring (`AutoSave.stopExploring`) interrupts the download going on (yt-dlp is killed with it, `Processes`), isn't counted, shows "Deteniendo…" at once, and leaves the thread clean for saving as it arrives; it used to wait for the file to end, silently. Exploring a chat that got to its beginning starts over from the newest (`SavedUpTo.forgetBack`), finding what's saved already: pressing it used to do nothing.
- What I send can be saved too, with its own kinds ("Guardar lo que yo envíe", `Flag.AUTO_SAVE_MINE*`, `ChatPreferences.autoSaves(chatId, mine)`); `autosave/Wanted` picks the kinds by who sent the message, for arrivals and exploring alike.
- A downloading file reports how much arrived (`MediaSource.media(…, progress)` from `MatrixClient.copyTelling`, yt-dlp's "[download] 45%" lines via `Processes.capture(…, eachLine)`), shown in the options and in `ui/ExploreBar`, on top of the window while a chat's past is explored (closing the options doesn't hide it; "Detener" there too).
- A video that came with its page (Instagram reels) isn't downloaded again from the page (`AutoSave.links`): it saved the same reel twice, the second in VP9. What yt-dlp saves is H.264/AAC whatever the site gave (`-S vcodec:h264`, then `VideoTranscoder.makePlayable` on anything else, in place, whole or not at all): a Mac doesn't open VP9.
- What a link leads to is saved by InstaTray's engine (`instatray.core`, the user's own library, JitPack `com.github.vaoan:InstaTray:core-1.0.1`, 0BSD) through `autosave/LinkSaver`: its sites and catch-all for anything yt-dlp knows, gallery-dl for the ones yt-dlp doesn't (if the person has it, `video/GalleryDl`), each site's cookies from `*cookie*.txt` in Downloads, permanent vs retryable failures. Unichat keeps its own: the chat's folder, the message's id (`Fetch.Request.nameTag`), the progress, H.264 for anything else (`VideoTranscoder.makePlayable`), and only `http(s)://` text ever reaches a tool (the engine also ends options with "--"). Improving downloads is done in InstaTray's `core/` and released with a new tag. `YtDlp` only keeps yt-dlp's pinned binary ready.
