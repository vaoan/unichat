# server — notes for Claude

The local server: installs, starts and watches tuwunel and the bridges.

- `server/` — Synapse + Postgres + bridges docker-compose, `setup.sh` / `setup.ps1`. `docs/BRIDGES.md`.
- `server/BinaryStore` downloads bridges (and tuwunel when the package has none) only if they match the SHA-256 pinned in `resources/app/unichat/server/sha256sums.txt` (`Manifest.sha256`, keyed `<owner/repo>@<tag>/<asset>`), never the release's own sums. **Bump `versions.env` → run `native/pin-hashes.sh`** (`ManifestTest` fails until you do). A bridge in `NATIVES_ALL` comes from Unichat's `NATIVES` release on every platform (patched or at a commit, `docs/NATIVE-SERVER.md`); what's installed is recorded as `Manifest.version` (`<tag>+<natives tag>` for Unichat's builds), so a new build of the same tag is installed again.
- `server/LocalServer` runs the processes; `server/BridgeInstaller` leaves a bridge ready (download, config, setup processes; tests with a temp dir and `FakeService`), `server/ServerSecrets` holds the secrets file.
- `server/StatusEndpoint` + `BridgeStates` (bridges POST their account states, mautrix `status_endpoint`) feed
  `MatrixChatService.accounts()` and `ui/chats/AccountAlerts` + `AccountAlertBar` (foot of the chat list, so chats don't jump); `server/Watchdog` restarts hung,
  stuck or flapping processes (awake time, backoff), and all but Meta's bridges when the internet returns; `server/MetaSessions` keeps Meta cookies safe from the bridge erasing them over a redirect (see docs/NATIVE-SERVER.md). Demo: `-Dunichat.demoAccounts=WHATSAPP:NEEDS_LOGIN,...`.

- A bridge with no account doesn't run. `BridgeLauncher` decides every start, restart and stop of a bridge (tested on fakes, `BridgeLauncherTest`); `LocalServer` only hands it the supervisor. `BridgeDemand` keeps which bridges are meant to run:
  - At launch only those with an account start (`AccountCheck`: a login in `LoginsCache`, else in the bridge's own database; when nothing tells, it starts, since an account gone silent is worse than the battery).
  - `ensureBridge` (opening a sign-in) starts one and waits for its probe (at most 60 s, and not at all once it stopped running); it then runs for the session.
  - Logging out of the last account stops it, only when the bridge itself answers that no login is left (`BridgeAccounts.afterLogout` → `BridgeProvisioner.loggedOut`), never on a refresh alone.
  - The watchdog watches only `BridgeLauncher.watched()`.
- "Does it answer?" is `HttpProbe` (`/_matrix/client/versions`): `READY` (a 200: `LocalServer` waiting for tuwunel) or `ALIVE` (any answer: `Watchdog`); an interrupted probe throws, so stopping never counts as down.
- What each chat allows (edit, delete for everyone) is what its bridge published in the room (`com.beeper.room_features`); X's bridge publishes it again at each start (`BridgeCapabilities`, before it runs: the capabilities' half of `kv_store.bridge_info_version` marked stale, so only chats whose answer changed are sent).

## Lessons
- Telegram with an account would never have started once its keys were saved: `restartBridge` skipped any bridge not meant to run, and Telegram without keys was never asked at launch whether it had an account. A gate on "meant to run" asks again (`BridgeDemand.withAccounts`) for a bridge that couldn't run before (`BridgeLauncherTest.telegramWithAnAccountStartsWhenItsKeysAreSaved`).
- X's chats never offered "Editar" though X and its bridge allowed it: mautrix-twitter decides edit/delete by whether it has a chat's XChat keys, publishes that when the chat is made, and doesn't publish again when the keys come later (the room said `+no-edit+no-delete` days after). The bridge checks edits live, so only the published state was stale. `BridgeCapabilities` has it publish them again at each start (`BridgeCapabilitiesTest`). When a network allows what Unichat doesn't offer, read the room's `com.beeper.room_features` before Unichat's code.
- A thread reading a child process's output must never stop reading: when `Supervisor.pump` died (OOM) the pipe stayed full and the Discord bridge sat in write() for a day, alive but deaf. Use `support/Processes`.
- `tuwunel.toml` (registration token), `doublepuppet.yaml` (`as_token`) and each bridge's `config.yaml` and registration were 0644 while `secrets.properties` was 0600, and `config.yaml` was rewritten in place (a crash left it empty). Every file with a token is written with `settings/SyncedFile.replace(…, true)` (whole, owner-only), and what a bridge writes itself is re-written that way after it runs (`HomeserverConfigTest`, `BridgeInstallerTest`, `BridgeConfigTest`).
- The two homeserver probes disagreed on an interrupt: `LocalServer` took it as down, `Watchdog` as up, and the watchdog went on probing the other processes with the interrupt set (each failing at once). An interrupted probe is neither: `HttpProbe` throws and the watchdog's round stops (`HttpProbeTest`).
- `tuwunel.toml` (registration token), `doublepuppet.yaml` (`as_token`) and each bridge's `config.yaml` and registration were 0644 while `secrets.properties` was 0600, and `config.yaml` was rewritten in place (a crash left it empty). Every file with a token is written with `support/SafeFile.replace(…, true)` (whole, owner-only), and what a bridge writes itself is re-written that way after it runs (`HomeserverConfigTest`, `BridgeInstallerTest`, `BridgeConfigTest`).
- The disk filled (2026-11-12): tuwunel and the bridges couldn't write, so nothing new reached the chats for hours while every process still answered and every bridge said "connected"; the top bar said nothing (it only knew "the server doesn't answer" and "a bridge is reconnecting"), and freeing space didn't help until Unichat itself started over. `support/Storage` measures the data folder's disk every 30 s (low under 1 GB) and hears from `Supervisor.pump` when a process's error line says a write didn't fit (`Storage.writeFailed`: by the line's level, as message text reaches the logs); the top bar says so in red (`AccountAlerts.storageLine`), and `Watchdog` restarts only hung processes while it's low, then every one, the server too, once there's room, and one that couldn't write as soon as there is (`WatchdogDiskTest`, `StorageTest`, `SupervisorTest.aProcessSayingItCouldntWriteIsNoted`). "Nothing arrived" alone is no signal (a quiet chat is fine): look for what the processes themselves say.
- Google Messages' bridge never started (installed 2026-11-09, never logged in): `BridgeConfig` turned direct media on for every bridgev2 bridge, and mautrix-gmessages' connector has none, so the bridge stopped at every start ("direct media is enabled in config, but the network connector does not support it"), 9000 times, and nothing said so. It's off for `gmessages` (`BridgeConfigTest.googleMessagesKeepsItsMediaOnTheServer`). A key set for all bridges is checked against each one's log once it runs: look for `"level":"fatal"` in its `bridge.log`.
- Bridge logs cost battery all the time: every line was written, flushed and the file's size asked, at `info` level, though nothing reads info lines. Bridges log at `warn` (`-Dunichat.bridgeLogs=info` brings it back), and `LogPump` keeps the byte count in memory (from the file's size when opened) and flushes only warn/error/fatal or non-JSON lines at once, the rest when a later line comes a second after the last flush (`LogPumpTest`, `BridgeConfigTest`). The file stream is unbuffered by itself: a "flush" saves nothing without the `BufferedOutputStream`.
