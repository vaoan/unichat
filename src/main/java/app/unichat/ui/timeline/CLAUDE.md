# ui.timeline — notes for Claude

The open chat (timeline) and message HTML: `ThreadPane` (+ `TimelineScroll`, `ThreadRows`, `MessageRowView`, `MessageLine`), `HtmlView` and `RichText`, `MessageActions` / `MessageActionsUi` (a message's menu), `Composer` (+ `ComposerAi`, `AiReplyButton`, `FormatMenu`, `Pasting`, `VoiceRecording` + `VoiceBar`), `UploadBar`, `CloakSend` + `CloakBar`. A message's pictures, video and audio are `media/MessageMedia` (`ui/media/CLAUDE.md`). What it touches outside: `matrix/MessageHtml` (link previews as HTML) and `links/` (`links/CLAUDE.md`), whose notes point here.

- Where the list looks (`TimelineScroll`), decided after every layout and before the frame is drawn (`afterLayout`, a post-layout pulse listener that lays the list out again itself): following the newest message, its end on the bottom edge (also when it's taller than the window); or reading older ones, the message whose top is nearest above the middle of the view held on the same pixel (`anchorId`), whatever grows or shrinks around it (the box, someone typing, messages arriving, history loading above, edits, reactions, pictures, the window, the text size). Only the person moves it: the wheel or trackpad, keys on the list, the scrollbar pressed, a jump to a quoted message (`moved`). Going towards older messages stops following at once; the newest wholly in view, by any means, follows again, and nothing else does: the person's rule is that writing, Enter or sending one's own message while reading older ones leaves the list where it is (it used to jump down on sending). `FollowIndicator` says which: a green dot in the chat's header beside the star while following (tooltip and screen reader say "Al día"; it was a badge over the messages and took the chat's room, and it stays managed when hidden so the header's buttons don't move), else the way down at the list's bottom right with how many messages arrived below (theirs and yours). No time windows nor "near the bottom" fractions: 0.2 % of a long chat is hundreds of pixels and pulled the person back down. Tests watch every frame (`ui/TimelineWindow.Frames`): `TimelineFollowUiTest` (at the newest), `TimelineReadingUiTest` (reading older, and every way back down), `AutoScrollUiTest`.
- Updates: `ThreadRows.update` touches only rows that differ (`MessageRow.revision`, from `Message.revision()`: a new drawn field must go in there), since replacing the whole list redraws all that's on screen; `ThreadPane.redraw` is for changes of appearance; a width change rebuilds the rows only when it changes the bubbles' width (`MessageRowView.bubbleWidth`, within 200–560 px), and a rebuilt row shows a photo decoded before at once (`media/Stills`): opening the side panel used to rebuild every row and every photo blinked (`TimelineWidthUiTest`); `MainView` updates the open chat at most every 250 ms. `ScrollPerfUiTest` (`-Dunichat.perfTests=true`, the real display: only the person runs it; ffmpeg) prints before/after numbers for a giant chat; compare with the Mac under similar load, which moves them a lot.
- Message HTML is written by strangers. `HtmlView` draws `formatted_body` tag by tag, as a browser would (jsoup, so badly nested HTML reads the same), with no cases per network or bridge: Discord embeds are just HTML, and `matrix/MessageHtml` writes `com.beeper.linkpreviews` as HTML too. Pictures only from `mxc://`, links only http(s), no scripts or frames. `Message.body` stays plain text for lists, replies and editing (`withoutEmbedText` drops the "> " lines the bridge repeats an embed in).
- Discord's bridge drops the video of a rich embed, so `links/LinkInspector` opens each link when its message shows (`MediaSource.linkMedia`; at most 5 per message) and asks the server what it is, or the page's `og:video`; `MessageMedia.linkPlayers` shows it. Those links come from anyone: no cookies, and every hop refuses this machine and its network; `MediaDownloader` fetches all web addresses through it too. A browser's User-Agent gets redirected by FixupX, hence "compatible". Ajustes → Privacidad → Conexiones can turn it off (`privacy.linkPreviews`, checked in `MediaDownloader.linkMedia`).

- A WhatsApp Business message's buttons (`Message.buttons`, `matrix/BusinessMessages`) are chips under it that can't be pressed (`BusinessButtons`: internal names in words through `business.button.<name>`, unknown ones with spaces for underscores) and a note to use the phone's WhatsApp. The demo's "Tienda Aromas" (`!tienda:demo`) has two.

- Shift+↑ / Shift+↓ in the message box (`LineSelection`): first to the start / end of the cursor's line as drawn, then a line at a time to where ↑ / ↓ alone would go, in the column the run started from; any other move starts a new run. Measured from `getCharacterBounds`, never the drawn caret, which exists only while the window has the system's focus (headless never has it) (`ComposerSelectionUiTest`).

## Lessons
- Anything that recurses over a stranger's structure needs a depth cap: `<b>`×10000 fits in a Matrix event and overflowed the FX thread's stack in `HtmlView.walk`. Past `HtmlView.MAX_DEPTH` (64) the rest is drawn as plain text (`HtmlViewUiTest.aDeeplyNestedMessageIsDrawnAsPlainTextPastTheLimit`).
- Sending several lines made the list go down and then jump up a little: the box shrank back to one line in the same pulse the message arrived, and `keepBottom` only asked for a scroll, so one frame showed the newest message cut off (12 px) and the next moved everything. Corrections happen before the frame is drawn (`list.layout()` in the post-layout listener, measured again until it holds: a row whose content changed only takes its real height then). The same rewrite fixed scrolling back down with the wheel never following again, a long message showing its top, and someone typing or the box growing moving what was being read. A scroll test checks every frame, not where the list ends up (`TimelineWindow.watch`).
- History loading above the message being read threw it out of view: `keepAnchor` jumped to its row (`scrollToTop`) and moved by pixels before a layout, which undid the jump. Lay out between the two. And on Linux (a 416 px list) a file arriving was never drawn: `list.scrollTo` goes by the list's estimate of row heights, which said it already ended above it; when the newest still isn't drawn, `keepBottom` moves by pixels, measuring real rows. Scroll tests run in a short window too (`TimelineWindow.SHORT`), as Linux's taller fonts leave.
- A sticker answering a longer message, sent by oneself, sat under the quote's text at the left of a bubble on the right: a bubble's `VBox` lines up what's narrower than it (stickers, photos) at its left by default. Outgoing bubbles align to the right (`MessageRowView.bubble`), so their content stays on the chat's side; text still fills the width (`ReplyAlignUiTest`).
