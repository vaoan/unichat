# ui.timeline — notes for Claude

The open chat (timeline) and message HTML: `ThreadPane` (+ `TimelineScroll`, `ThreadRows`, `MessageRowView`, `MessageLine`), `HtmlView` and `RichText`, `MessageActions` / `MessageActionsUi` (a message's menu), `Composer` (+ `ComposerAi`, `AiReplyButton`, `FormatMenu`, `Pasting`, `VoiceRecording` + `VoiceBar`), `UploadBar`, `CloakSend` + `CloakBar`. A message's pictures, video and audio are `media/MessageMedia` (`ui/media/CLAUDE.md`). What it touches outside: `matrix/MessageHtml` (the bridge's link previews, as `model/LinkPreview`) and `links/` (`links/CLAUDE.md`), whose notes point here.

- Where the list looks (`TimelineScroll`), decided after every layout and before the frame is drawn (`afterLayout`, a post-layout pulse listener that lays the list out again itself): following the newest message, its end on the bottom edge (also when it's taller than the window); or reading older ones, the message whose top is nearest above the middle of the view held on the same pixel (`anchorId`), whatever grows or shrinks around it (the box, someone typing, messages arriving, history loading above, edits, reactions, pictures, the window, the text size). Only the person moves it: the wheel or trackpad, keys on the list, the scrollbar pressed, a jump to a quoted message (`moved`). Going towards older messages stops following at once; the newest wholly in view, by any means, follows again, and nothing else does: the person's rule is that writing, Enter or sending one's own message while reading older ones leaves the list where it is (it used to jump down on sending). `FollowIndicator` says which: a quiet chevron on a line in the chat's header beside the star while following (a green dot read as "online", which Unichat can't know) (tooltip and screen reader say "Al día"; it was a badge over the messages and took the chat's room, and it stays managed when hidden so the header's buttons don't move), else the way down at the list's bottom right with how many messages arrived below (theirs and yours). No time windows nor "near the bottom" fractions: 0.2 % of a long chat is hundreds of pixels and pulled the person back down. Tests watch every frame (`ui/TimelineWindow.Frames`): `TimelineFollowUiTest` (at the newest), `TimelineReadingUiTest` (reading older, and every way back down), `AutoScrollUiTest`.
- Updates: `ThreadRows.update` touches only rows that differ (`MessageRow.revision`, from `Message.revision()`: a new drawn field must go in there), since replacing the whole list redraws all that's on screen; `ThreadPane.redraw` is for changes of appearance; a width change rebuilds the rows only when it changes the bubbles' width (`MessageRowView.bubbleWidth`, within 200–560 px), and a rebuilt row shows a photo decoded before at once (`media/Stills`): opening the side panel used to rebuild every row and every photo blinked (`TimelineWidthUiTest`); `MainView` updates the open chat at most every 250 ms. `ScrollPerfUiTest` (`-Dunichat.perfTests=true`, the real display: only the person runs it; ffmpeg) prints before/after numbers for a giant chat; compare with the Mac under similar load, which moves them a lot.
- Message HTML is written by strangers. `HtmlView` draws `formatted_body` tag by tag, as a browser would (jsoup, so badly nested HTML reads the same), with no cases per network or bridge: Discord embeds are just HTML. Pictures only from `mxc://`, links only http(s), no scripts or frames. `Message.body` stays plain text for lists, replies and editing (`withoutEmbedText` drops the "> " lines the bridge repeats an embed in).
- Link previews are cards drawn as Telegram Desktop draws a web page (`LinkPreviewCard`: the accent's bar, the site, the title as the link, a few lines of text, the picture or video below, or a small picture beside the text; a GIF plays by itself). A bridge's (`com.beeper.linkpreviews` → `Message.linkPreviews`, pictures only from `mxc://`) gets the video its link leads to in place of its picture once found; a message with links and none from a bridge gets one card for its first link, read by Unichat (`MediaSource.linkPreview` → `links/LinkInspector.preview`), as Telegram's server does for its apps: one's own messages never get the preview the network made. A message with an embed (Discord's, `htmlText`) keeps `MessageMedia.linkPlayers` under it for the video the bridge drops (at most 5 links). Those links come from anyone: no cookies, every hop refuses this machine and its network; `MediaDownloader` fetches all web addresses through it too. Ajustes → Privacidad → Conexiones can turn it off (`privacy.linkPreviews`, checked in `MediaDownloader.linkMedia`/`linkPreview`). `LinkPreviewUiTest`; the demo's Andrés has one.

- A WhatsApp Business message's buttons (`Message.buttons`, `matrix/BusinessMessages`) are chips under it that can't be pressed (`BusinessButtons`: internal names in words through `business.button.<name>`, unknown ones with spaces for underscores) and a note to use the phone's WhatsApp. The demo's "Tienda Aromas" (`!tienda:demo`) has two.

- Shift+↑ / Shift+↓ in the message box (`LineSelection`): first to the start / end of the cursor's line as drawn, then a line at a time to where ↑ / ↓ alone would go, in the column the run started from; any other move starts a new run. Measured from `getCharacterBounds`, never the drawn caret, which exists only while the window has the system's focus (headless never has it) (`ComposerSelectionUiTest`).

- Forwarding: "Reenviar…" in a message's menu starts picking with it, as WhatsApp does (`MessageSelection`: click, Shift+click for the ones between, Space/Enter, Esc; "N seleccionados · Cancelar · Reenviar" takes the header's buttons' place, the message box stays, the message buttons hide and a click only picks; "Reenviar" there opens the sheet). `ForwardSheet` (the window's overlay) chooses one or more chats of any network (`chats/ChatFilter.writable`, the ⌘K's search) and what the copies say: who, which chat, when (`ForwardNote`, each off by default, Ajustes → Apariencia → Escritura sets where each forward starts), with the line shown as it will go. `service/Forwarding` sends them in the chat's order, a line only before each run it describes. Only what the server has can go (`MessageActions.FORWARD`: no echo still sending, no join, a file only at an `mxc://` address). Snapshots: `-Dunichat.overlay=forward|select`. `ForwardUiTest`.
- Deleting for everyone (only one's own messages the network still lets go, `MessageActions.DELETE_FOR_EVERYONE`): "Eliminar para todos…" asks about that one; "Eliminar varios…" starts picking with it (`MessageSelection.Purpose`: the same picking as forwarding, its button red and only those messages pickable). Either way `DeleteSheet` asks twice ("¿Eliminar N mensajes para todos?" quoting the first, then "¿Seguro?"), Cancelar focused both times; after the second yes they go one at a time and a notice says how it went (`ThreadPane.delete`). Snapshot: `-Dunichat.overlay=delete`. `DeleteMessagesUiTest`.

- Pinned messages are Unichat's own (no bridge carries pins to its network; Telegram's only sets who may): "Fijar mensaje" / "Desfijar mensaje" in a message's menu (`MessageActions.PIN`, anything the server has but a system line), kept in `service/PinnedMessages` (`pinned-messages.json`, this computer's: ids are the local server's), each with who sent it and what it said, so `PinnedBar`, under the chat's header, shows it however far back it is, loaded or not ("1 de 3" with several; a click goes to the one shown and the bar moves on to the next; its ✕ unpins that one). Going to one not loaded loads the chat's history page by page until it's there (`ThreadPane.reveal`, `loadOlder(then)`), and says so when the chat's start comes first (deleted). `PinnedMessagesUiTest`, `PinnedMessagesTest`.

- A message's menu and its keys follow `MessageActions` as data: `MessageActionsUi.MENU_ORDER` + `itemsFor(action)` build the menu, `ThreadPane.KEY_ACTIONS` + `MessageActionsUi.run` the keys, so both obey the same rule. A new action is a value in the enum, a case in `itemsFor` and, if a key does it, one in `run`; never another `if (a.contains(…))`. A new kind of message is a branch in `MessageRowView.content`, not in `bubble`.
- "Ver lo que decía…" (`MessageActions.SAVED_TEXT`): all a deleted message's menu has (Enter, right click, the "⋯"), and in an edited one's: `SavedTextSheet` (the window's overlay) shows every version the person's computers kept of it, when and who, each to copy, or that there's no copy (`autosave/CLAUDE.md`). Snapshot: `-Dunichat.overlay=savedText` or `savedText:none`. `SavedTextUiTest`.
- "Corregir con IA" (`MessageActions.FIX`, where `EDIT` is: one's own text the network still lets edit; only with the AI on): `MessageFixer` corrects a message already sent with ⌘O's prompt (`assist/FixPrompt`) on a thread of its own and edits it by itself (`svc.editMessage`); nothing waits for it (the box, sending and ⌘O go on), several at once, each row saying "Corrigiendo con IA…" with a wheel (`MessageRowView.fixingNote`, redrawn through `ThreadPane`'s coalescer). It edits only if the message is still what was corrected (not deleted, not changed meanwhile) and still editable; what came of it is a notice. Ajustes → Escribir con IA → "Corregir lo que envío" (`ai.fixMode`: OFF, AFTER, BEFORE; `Composer.setSending` decides before each text goes). Before sending: `SendQueue` holds each text in its chat's queue while it's corrected (`Correction`, shared with `MessageFixer`: ⌘O's prompt and `FixPrompt.addsWhatWasntThere`), all at once, and sends them in the order written; `SendQueueView` above the box shows the open chat's, a row each (a wheel, the text, send-as-written and cancel icons, named in full for screen readers; past ~3 rows it scrolls, sized in the text's em). Cancel stops its correction and nothing goes; a failed correction goes as written, said. If others wrote while it waited, it answers what was last said when it was written (`ai.keepThread`, on; the person's own "Responder" wins; not where the network has no replies). What was written before the correction is handed to auto-save as that message's first version (`SendQueue.onCorrected` → `AutoSave.wroteBefore`, matched to a message of mine new since it went, never by text alone). One queue per service (`SendQueue.of`): a window rebuilt shows the same; quitting and logging out send what's waiting as written first (`UnichatApp.sendWhatsWaiting`). Files and voice notes go in their chat's turn behind it (`Composer.setInTurn`, `SendQueue.inOrder`). Sending happens outside the queue's lock, one at a time from an outbox (the service tells its listeners as it sends). Commands (`!…`, `/…`) are never corrected. Each row says what it would answer (`Pending.wouldAnswer`); rows are kept while they wait (rebuilt ones lost the keyboard's focus). `SendQueueTest`, `SendQueueUiTest`; snapshot `-Dunichat.overlay=queue`. After sending: each text sent from this computer's box (`Composer.setOnSent`, told just before it goes, without "/me", `MessageFixer.expect`) is corrected the same way once the server has it (not while `SENDING`; forgotten if `FAILED`), quietly but for failures; never what's sent from another device (two computers would correct it twice), nor an older message of mine saying the same (`expect` keeps the ids there before it went; matching by text alone edited yesterday's "ok" from the phone). Only once the server has it (`FIX` needs `onServer`): a temporary id changes mid-correction. The corrected text is marked written by AI for style learning. Snapshot: `-Dunichat.overlay=fixing`. `MessageFixerTest`, `MessageFixUiTest`, `AutoFixSettingUiTest`.
- "Capturar conversación…" (`MessageActions.CAPTURE`, any message): picking a stretch (`MessageSelection.Purpose` with `range`, `MessageRange`): two markers on their rows ("Desde aquí" above the first, "Hasta aquí" under the last, `RangeMarkers`, each with a ✕; the list's click filter lets the ✕ through), the rows between as one band, and under the header a strip saying each end with its ✕ (the keyboard's way). The first click is both ends; outside moves the end on its side, inside the nearer end; an end taken away is put back by the next click; nothing between the ends can be left out. "Capturar…" makes `ConversationShot`: the chat's header (picture, name, what's under it) and the stretch's rows drawn off screen in a scene with the window's look, 420 pt wide (a phone's), at 2×, after its pictures load (`.media-loading` gone, 15 s at most), with an optional footer. `CaptureSheet` shows it as one long picture or pieces a phone's screen tall (`ShotPieces.cut`: between messages, inside one only when taller than a piece; the footer never alone; the last filled with the background) and sends it to chats (`ChatChooser`, shared with forwarding; photos in order), copies it (the picture and its files) or saves it (`FileNames.free`). Snapshots: `-Dunichat.overlay=capture` / `capture:sheet`. `MessageRangeTest`, `ShotPiecesTest`, `CaptureUiTest`.

## Lessons
- A capture measured itself before its layout: `layout()` on a node inside a `Group` doesn't size it, so the height checked against the limit and the places to cut were stale (one piece for a dozen messages, a stretch past the limit drawn anyway). Off screen, lay out through the scene's root (`ConversationShot.laidOut`). And what reaches others shows nothing of the person's own: its header says the network and how many, never the account (a phone number) nor "silenciado" (`ThreadPane.captureSubtitle`).
- A double click on a message reacted to it with ❤️ (`MessageRowView`'s bubble handler): opening a photo or picking a word with two clicks hearted messages without the person meaning it. And a digit pressed with the focus on the messages (after a click on one, meaning to write) reacted with a quick reaction. Reacting is meant, never a side effect of another gesture or key: only the reaction popup, a reaction under the message and the menu's "Reaccionar …" react; no key does, and a digit typed on the messages goes to the box (`NoAccidentalReactionUiTest`).
- ⇧⌘↑ / ⇧⌘↓ in the message box "selected backwards": JavaFX's Mac keys use `extendSelection`, which extends from the selection's nearer end, so a second ⇧⌘↑ collapsed it and ⇧⌘↓ after ⇧⌘↑ moved where it started. `Composer.onKey` handles them on the Mac: `selectRange(anchor, 0 | length)` (`ComposerSelectionUiTest.shiftCommandUpAndDown…`). A selection key keeps the anchor.
- The whole test run died of "Java heap space" once every `ThreadPane` asked for `SendQueue.of(svc)` and `AutoSave.of(svc)`: a static per-service registry whose value holds listeners (the windows) and they the service never lets either go, and `AutoSave` runs threads of its own. `SendQueue.of` holds its queues weakly (one with something waiting is held by the threads correcting it), and the window asks `AutoSave` only when it uses it (`SendQueueTest.aQueueNeverKeepsItsServiceAlive`).
- Anything that recurses over a stranger's structure needs a depth cap: `<b>`×10000 fits in a Matrix event and overflowed the FX thread's stack in `HtmlView.walk`. Past `HtmlView.MAX_DEPTH` (64) the rest is drawn as plain text (`HtmlViewUiTest.aDeeplyNestedMessageIsDrawnAsPlainTextPastTheLimit`).
- Sending several lines made the list go down and then jump up a little: the box shrank back to one line in the same pulse the message arrived, and `keepBottom` only asked for a scroll, so one frame showed the newest message cut off (12 px) and the next moved everything. Corrections happen before the frame is drawn (`list.layout()` in the post-layout listener, measured again until it holds: a row whose content changed only takes its real height then). The same rewrite fixed scrolling back down with the wheel never following again, a long message showing its top, and someone typing or the box growing moving what was being read. A scroll test checks every frame, not where the list ends up (`TimelineWindow.watch`).
- History loading above the message being read threw it out of view: `keepAnchor` jumped to its row (`scrollToTop`) and moved by pixels before a layout, which undid the jump. Lay out between the two. And on Linux (a 416 px list) a file arriving was never drawn: `list.scrollTo` goes by the list's estimate of row heights, which said it already ended above it; when the newest still isn't drawn, `keepBottom` moves by pixels, measuring real rows. Scroll tests run in a short window too (`TimelineWindow.SHORT`), as Linux's taller fonts leave.
- A sticker answering a longer message, sent by oneself, sat under the quote's text at the left of a bubble on the right: a bubble's `VBox` lines up what's narrower than it (stickers, photos) at its left by default. Outgoing bubbles align to the right (`MessageRowView.bubble`), so their content stays on the chat's side; text still fills the width (`ReplyAlignUiTest`).
- "Eliminar para todos" deleted at the first click, with no question: one stray click on a menu item took a message from everyone, for good. Whatever can't be undone and reaches others asks twice, the safe answer focused (`DeleteSheet`, `DeleteMessagesUiTest`).
- Leaving the bottom with the wheel, the first turn moved 12 px instead of 3 wherever the list's estimate of its rows was wrong (text at 110 %; Linux's fonts on CI, where `tinyTrackpadMovesUpThenBackDown` failed every run for days): `VirtualFlow`, past its end, laid the rows out again 9 px further. Coming back the same way left the newest 7 px cut, and it never followed again. The first turn up lands by the turn (`TimelineScroll.leavingTo`, `landLeaving`) (`TimelineReadingUiTest.tinyTrackpadMovesUpThenBackDownWhereTheListGuessesItsLengthWrong`). A test that only fails on CI: make the Mac look like it (a text size, a font) before guessing.
- Reading older messages, the message read moved 3 px (9 with Linux's fonts, failing on CI now and then) when the text grew: it was held on its pixel in the list, and the header, growing with the text, moved the list. It's held on its pixel in the window (`TimelineScroll.anchorY`, `sceneY`), so a header or the pinned bar appearing moves nothing either. And dragged to the end with rows the flow's estimate gets wrong, the list ended with the newest a few px cut (position 0.9958 on CI's Linux) and never followed again: its end counts as the newest reached, and letting the scrollbar go at its very end goes to the newest and follows it (`hookScrollBar`). Tested at 108 % and 115 % (`TimelineReadingUiTest.*WhereTheListGuessesItsLengthWrong`).
