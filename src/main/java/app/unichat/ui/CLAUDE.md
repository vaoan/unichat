# ui — notes for Claude

JavaFX screens: the only package (with the root) that uses JavaFX. The rules, commands and map are in the root `CLAUDE.md`.

- `ui/` — `MainView` (rail | `ChatListPane` | `ThreadPane` + `InfoPane`, overlays; keys, F6 and zoom in `WindowShortcuts`), `ChatListPane` (+ `ChatRowCell`, `SpaceChannelsView`), `ThreadPane` (+ `TimelineScroll`, `MessageRowView`, `MessageLine`), `Composer`,
  `CommandBar`, `AccountsPane` (+ `DiscordServersPage`, `LoadingView`), `SettingsWindow` (pages built with `SettingsForm`: `AppearancePages`, `PrivacyPage`, `NetworksPage`, `SpeechPage`, `AiReplyPage`), `Notifier` (AWT tray), `Theme`. Pure logic with tests: `A11yText` (what a screen reader and the voice say),
  `ChatFilter`, `ThreadRows`, `RichText`, `Formats`, `MediaSizes`, `LoginTexts`. Shared bits: `Nodes` (show, style), `Labels.help`, `Chips.sticky`, `Icons.iconButton`, `MediaTile`.
- Lists never `setAll` the same rows nor call `ListView.refresh()` on a data change (`ui/ListRows`): both pile every cell and hand them out again in another order, so each row draws another chat and the whole list repaints; rows redraw in place (`ListRows.Redrawable`). Redraws touch only what changed: each change redraws the visible rows (opening a chat marks it read), so a row (`ChatRowCell`) keeps its nodes and only toggles them (flag icons, account tag), `Avatar` keeps one network icon per network, `Rail` keeps its unread badges, the favorites row is rebuilt only when its chats change, and `Nodes.style` leaves classes alone when already so. `ListRepaintUiTest` checks it.
- `ui/InfoPane` is built again only when what it shows changes (`InfoPane.shown`): the window refreshes it on every message, and rebuilding blanked its photos (a flash). Its "Multimedia" is `ui/ProfileMedia`: photos, videos, links and files in tabs (`ProfileMedia.Contents`, pure, newest first), photos whole in their square (never stretched: `MediaTile` keeps the ratio), hidden per chat from its options (`ChatPreferences.setMediaHidden`, `Flag.MEDIA_HIDDEN`).
- Following the newest message (`ui/TimelineScroll`): the person going towards older messages (wheel/trackpad up, ↑ PgUp Home, dragging the thumb up) stops it at once; it follows again only when the newest message is wholly in view, in pixels; a growing photo decides nothing. No time windows nor "near the bottom" fractions: 0.2 % of a long chat is hundreds of pixels and pulled the person back down (`AutoScrollUiTest.aSmallScrollUpInALongChatIsNotUndone`).
- Timeline updates: `ThreadRows.update` touches only rows that differ (`MessageRow.revision`, from `Message.revision()`: a new drawn field must go in there), since replacing the whole list redraws all that's on screen; `ThreadPane.redraw` is for changes of appearance; `MainView` updates the open chat at most every 250 ms. `ScrollPerfUiTest` (`-Dunichat.perfTests=true`, the real display: only the person runs it; ffmpeg) prints before/after numbers for a giant chat; compare with the Mac under similar load, which moves them a lot.
- `css/app.css` — single stylesheet; light palette on `.root`, dark on `.root.dark`; `-accent` and font size
  set inline by `Theme`.
- macOS Dock: the package declares `LSUIElement` (package.sh), so by default there's no Dock icon, ⌘Tab or app menu; Ajustes → Notificaciones `app.showInDock` adds one while the window is open (`ui/DockIcon`), also forced if the menu bar icon is missing. ⌘Tab only lists apps with a Dock icon (macOS has no way around it), so any window besides the main one (photo, video, settings) also brings the Dock icon while open (`DockIcon.regular`), and ⌘` / ⌘⇧` (also ⌘< on a Spanish keyboard) moves between Unichat's windows (`ui/AppWindows`; macOS gives that only to apps with a Window menu); a menu that opens activates Unichat and focuses its window (`ui/MenuDismiss`): a right-click on a window of a background app shows the menu without activating it, and then neither a click outside nor Esc reached JavaFX (`MenuDismissUiTest`, the real mouse and keyboard); so `native/UnichatBar.swift` registers a global ⌃⌥U (`app.globalShortcut`, Carbon: no Accessibility permission) that brings the window back. `UnichatApp` handles ⌘Q itself, and activation with no window brings it back (`TrayReopen`). Don't build nodes while the window is hidden: nothing is drawn, so JavaFX never empties `Scene.dirtyNodes` and everything built stays in memory (`MainView.catchUp` brings it up to date on opening; only the menu bar count updates meanwhile).
- Message HTML: `ui/HtmlView` draws `formatted_body` tag by tag, as a browser would (jsoup, so badly nested HTML reads the same), with no cases per network or bridge: Discord embeds are just HTML, and `matrix/MessageHtml` writes `com.beeper.linkpreviews` as HTML too. Pictures only from `mxc://`, links only http(s), no scripts or frames. `Message.body` stays plain text for lists, replies and editing (`withoutEmbedText` drops the "> " lines the bridge repeats an embed in). Discord's bridge drops the video of a rich embed, so `links/LinkInspector` opens each link when its message shows (`MediaSource.linkMedia`; at most 5 per message) and asks the server what it is, or the page's `og:video`; `MessageMedia.linkPlayers` shows it. Those links come from anyone: no cookies, and every hop refuses this machine and its network; `MediaDownloader` fetches all web addresses through it too. A browser's User-Agent gets redirected by FixupX, hence "compatible". Ajustes → Privacidad → Conexiones can turn it off (`privacy.linkPreviews`, checked in `MediaDownloader.linkMedia`).
- Video: `Message.playsInline` decides by what the bridge reports (GIF flag, video stickers, or up to 2 MB and 15 s); `ui/InlineVideo` (muted loop in the timeline, a native player only while on screen, none with reduced motion), `ui/VideoViewer` (window; downloads on opening) with `ui/VideoControls` (±10 s, volume, speed, repeat, watch again, full screen with controls that hide while playing, always on top, save the video or the frame; YouTube's keys: K J L, ←→ ↑↓, M, F, < >, , ., Home/End, digits). javafx-media comes with javafx-web; WebM it can't play goes through `video/WebmStickers` (ffmpeg to animated WebP or, if that ffmpeg lacks the encoder like Homebrew's, GIF; cached in `cache/media`; `video/Ffmpeg` uses the person's own or downloads a pinned build on first use, `video.ffmpegAuto`, Ajustes → Redes), `VideoViewer` converts other unreadable videos to H.264 (`video/VideoTranscoder`), and what still can't play falls back to a file chip and the system player. Trust the file, not its label: a sticker labelled `video/webm` may be delivered as a GIF; `.mov` is cached as `.mp4` because JavaFX refuses that name. Reels that arrive as a picture + `external_url` open their page (`Message.isReelLink`).
- Photos: `ui/MediaViewer` (window and controls; steps through the chat's pictures with ← → / Page Up/Down and the side buttons, `ui/Gallery`: photos and pictures sent as documents, which open there too; the arrows pan while zoomed in; F full screen, Esc leaves it then closes) over `ui/PhotoPane` (mouse) and `ui/PhotoZoom` (pure: scale, turn, position). Animated GIF/WebP stay decoded at up to 1600 px, so real size there is the decoded one. A still WebP over 3 MP (a phone's photo) is never decoded in Java: TwelveMonkeys takes ~25 bytes/pixel, 600 MB+ for 24 MP; `video/BigPictures` makes a 1600 px PNG with `sips` (Mac) or ffmpeg, cached (`AnimatedImage.isBigWebp`, read from the header).
- Audio: `ui/AudioPlayback` (one per window: starting another stops it; survives changing chats), shown by `AudioControls` in the message and in `AudioBar` on top. JavaFX refuses Ogg/Opus: `stt/PlayableAudio` makes a 48 kHz WAV once (`OggOpus.toPlayableWav`; 16 kHz is only for Whisper).
- Animations: An animation over `AnimatedImage.MAX_ANIMATION_BYTES` first loses resolution, down to its size on screen (`shrinkToKeep`), and only then frames: dropping them halved a sticker's frame rate. Media grids keep their tiles (`ui/TileCache`) and `MessageMedia.loadMedia` shows what `AnimatedImage` already decoded at once.
- Emoji picker (`ui/EmojiPicker`, side panel `ui/EmojiGrid`): Unicode's Emoji 15.0 list (`resources/app/unichat/emoji/emoji.txt`, made by `native/emoji-list.py` from the pinned emoji-test.txt; 1870 without skin-tone variants; 15.0 because macOS 13.3 draws no newer). JavaFX lays out flags, keycaps and ZWJ sequences in pieces (490 of them on a Mac), so `ui/EmojiArt` measures which and draws those with Java2D (which joins them) as pictures, off the FX thread; one Java2D can't join either stays hidden. The list is virtual (`ui/EmojiGrid`, a `ListView` of rows from `ui/EmojiRows`, pure): 1870 buttons at once scrolled at 110 ms a step, the virtual one at 35 (`EmojiScrollPerfUiTest`, `-Dunichat.perfTests=true`); columns follow the width of a real button (`probe`), every emoji button in it has one size in em so text and pictures line up, and the arrow keys move between emoji since those off screen have no button. The side panel's tab starts with Favoritos (a hint while empty: right-click → Agregar a favoritos) and Recientes (updated when the tab is shown, so nothing moves under the pointer); the reaction picker (`EmojiGrid.Mode.REACTIONS`) is the same list starting with the ones reacted with most. Both have a search box: Unicode's names and keywords in the language in use (`ui/EmojiSearch`, `emoji/names_<lang>.txt` from CLDR by the same script, English for a language without; every word typed begins a word of the name, accents and case aside), ↓ goes to the emoji, Enter takes the first. The quick reactions (popup, message menu, keys 1–6) are the six the person reacts with most (`MediaLibrary.reacted` / `mostReacted`, in media-library.json, so they travel; the usual six fill in until there's history; taking a reaction away isn't a use; `QuickReactionsUiTest`). In messages, emoji JavaFX draws in pieces (flags, joined ones, skin tones: any cluster of more than one character, measured once) are pictures inside the text (`ui/EmojiInline` from `EmojiArt.segments`, `EmojiInlineUiTest`); the text box (a TextArea, plain text only) still shows them in pieces. `EmojiPickerUiTest` (Mac: its emoji font; the headless platform uses the system's fonts too). Messages and the text box still draw those emoji with JavaFX, in pieces.

## Checking UI changes
`-Dunichat.snapshot=out.png` (`SnapshotRun`) writes the window to a PNG and exits; combine with `-Dunichat.dataDir=<dir>` (put
`session.backend=demo` and optionally `ui.theme=LIGHT` in `<dir>/settings.properties`),
`-Dunichat.openChat=<id>` (demo ids like `!familia:demo`), `-Dunichat.openSpace=<id>` (a server's channels, e.g. `!servidor:demo`), `-Dunichat.info=true`, `-Dunichat.panel=EMOJIS|STICKERS|GIFS`,
`-Dunichat.overlay=command|newchat|add|folderNew|folderDelete|settings:<Página>`, `-Dunichat.openFolders=true` (folder list), `-Dunichat.openFolder=<name>` (inside one), `-Dunichat.network=<protocolo>` (settings snapshots the settings window).
Run via `JAVA_OPTS=... ./run-dev.sh`, then read the PNG. Do this after every visual change. A snapshot run is headless by itself (`UnichatApp.main`: JavaFX's Headless platform, AWT headless): no window, menu-bar icon nor notification appears.

## Accessibility (user requirement — keep it working)
Settings → Accesibilidad (`a11y.*` keys); `Theme` adds `contrast`, `strong-focus`, `wide-spacing` root classes and
follows OS high contrast / reduced motion. Every new control needs an accessible text (icon buttons get it from
`Icons.iconButton`), keyboard reachability, and must survive 160 % text + high contrast. Icons grow with the text (`Icons.SCALE`, set by `Theme`): give paddings that make room for one in `em`, and check alignment with `-Dunichat.snapshotScale=2` and `ui.fontScale=1.6`. The message box is as tall as the text it draws (its own Text node, measured after each layout and when the text re-wraps: guessing from the font size cut lines), up to 40 % of the window, then scrolls (`ComposerHeightUiTest`). Notices (`MainView.toast`) sit just above the message box, never over it (`ToastPlacementUiTest`). The composer puts the text on its own line above the buttons when they'd leave it under 14 em (`Composer.stack`, decided in a runLater after the layout that changed the width: moved mid-layout, the frame kept the stacked height; `NotificationOpenUiTest`); the info panel's four actions go two by two rather than cut. The composer has one media button (the face): it opens the side panel on the media tab used last (`SidePanel.lastMediaTab`, `panel.mediaTab`, default Emojis); a sticker or GIF's right-click menu has "Ver en grande" (`LibraryMenu.enlarge`). A plain key pressed outside a text box with a chat open writes in the composer (`WindowShortcuts.typeIntoComposer`, a handler so the timeline's own keys win). ⌘L (Ctrl+L) goes to the message box from anywhere. Every search box has a ✕ (`ui/SearchFields`, out of the Tab order) and Esc empties it before closing what it's in. A message's menu (Enter on it) has what only the mouse could do: view its photo/video, go to the message it answers, open its links (`MessageActionsUi`). `KeyboardUiTest`
(in `-Pheadless-ui`) checks F6 zones, timeline keys, zoom and screen-reader texts;
`FilterUiTest` (same flag) checks that the rail keeps the chosen chip when switching network. `./mvnw verify -Pheadless-ui` runs them with no display or windows (JavaFX's own headless platform, `-Dglass.platform=Headless`, since JavaFX 25; Monocle was never published past JavaFX 21); All of them run there (Audio, ReactionEmoji and NetworkSettings, which stopped under Monocle, too). Its virtual screen is a fixed 1000×1000 and a window drawn outside it (moved off-screen, or taller than the rest) throws on every frame, on the UI thread, into whatever test comes next: keep test windows on it, hidden with opacity 0, and close them when done. It proves logic, not focus, tray or Dock.
