# ui — notes for Claude

JavaFX screens: the only package (with the root) that uses JavaFX. This package holds the window (`MainView`) and what every screen shares; each area is a subpackage with its own `CLAUDE.md`, loaded with its files:
- `ui.chats` — the chat column, rail, spaces, folders, favorites, new chat, the info panel and side panel, avatars.
- `ui.timeline` — the open chat: rows, message HTML, the composer and its parts, message actions, upload/cloak bars.
- `ui.media` — photos, video, audio, animations, viewers, galleries, caches, the profile's media.
- `ui.emoji` — emoji picker, grid, search and inline pictures, reactions, sticker/GIF grids, the media library.
- `ui.settings` — the settings window, its form and pages, settings that travel.
- `ui.desktop` — Dock, tray, menu bar, notifications, window switching, quitting (macOS and Windows).
- `ui.login` — signing in, bridge logins, accounts, Telegram keys, Discord servers.

Topics across folders stay in `.claude/rules/`: `css-icons.md` (app.css, `Theme`, `Icons`), `i18n.md`. A screen of a feature package (cloud, autosave, assist, cloak, voice, login) follows that package's `CLAUDE.md` too. To look at a change: the `snapshot` skill.

Subpackages depend on this one (`Nodes`, `Icons`, `Labels`…) and `MainView` on all of them; a member is `public` only when another package uses it. Tests live in the package of what they test; a test that drives the whole window stays here. `FxWait` (test helper) is public here for all of them.

## Map
- `MainView` (rail | `chats.ChatListPane` | `timeline.ThreadPane` + `chats.InfoPane`, overlays; keys, F6 and zoom in `WindowShortcuts`), `chats.ChatListPane` (+ `ChatRowCell`, `SpaceChannelsView`), `timeline.ThreadPane` (+ `TimelineScroll`, `MessageRowView`, `MessageLine`), `timeline.Composer` (+ `ComposerAi`: drafts, fixes, style learning; `VoiceRecording`: the mic and its bar), `chats.CommandBar`, `login.AccountsPane` (+ `DiscordServersPage`, `LoadingView`), `settings.SettingsWindow`, `desktop.Notifier` (AWT tray), `Theme`.
- Pure logic with tests: `A11yText` (what a screen reader and the voice say), `chats.ChatFilter`, `timeline.ThreadRows`, `timeline.RichText`, `Formats`, `media.MediaSizes`, `login.LoginTexts`.
- Shared bits, use them instead of writing another: `Nodes` (show, style), `Labels.help`, `Chips.sticky`, `Icons.iconButton`, `media.MediaTile`, `SearchFields`, `WorkingLine`, `ListRows`, `FxCoalescer` (one redraw on the FX thread for many requests), `media.MediaOpening` (a message's file with the system's app, a video in the player), `Formats.clock`.
- Listeners from `ChatService` come on any thread: marshal with `Platform.runLater`, coalesced in `MainView` by `Throttle`; elsewhere progress from another thread or a width that changes redraws through `FxCoalescer`, which counts in `Redraws.PENDING` so `FxWait.settled` waits for it.

## Lists and redraws
- Lists never `setAll` the same rows nor call `ListView.refresh()` on a data change (`ListRows`): both pile every cell and hand them out again in another order, so each row draws another chat and the whole list repaints; rows redraw in place (`ListRows.Redrawable`). Redraws touch only what changed: each change redraws the visible rows (opening a chat marks it read), so a row (`ChatRowCell`) keeps its nodes and only toggles them (flag icons, account tag), `Avatar` keeps one network icon per network, `Rail` keeps its unread badges, the favorites row is rebuilt only when its chats change, and `Nodes.style` leaves classes alone when already so. `ListRepaintUiTest` checks it.
- Don't build nodes while the window is hidden: nothing is drawn, so JavaFX never empties `Scene.dirtyNodes` and everything built stays in memory (`MainView.catchUp` brings it up to date on opening; only the menu bar count updates meanwhile).
- Opening a file with the system's app goes through `Browser.openFile` only (AWT's own thread; `open`/`start`/`xdg-open` where AWT's Desktop can't; a message when there's no way): called from the thread a download finished on, it did nothing at all on macOS (`FileOpenUiTest`).

## Accessibility (user requirement — keep it working)
- Settings → Accesibilidad (`a11y.*` keys); `Theme` adds `contrast`, `strong-focus`, `wide-spacing` root classes and follows OS high contrast / reduced motion. Every new control needs an accessible text (icon buttons get it from `Icons.iconButton`), keyboard reachability, and must survive 160 % text + high contrast. Icons grow with the text (`Icons.SCALE`, set by `Theme`): give paddings that make room for one in `em`, and check alignment with the `snapshot` skill at scale 2 and `ui.fontScale=1.6`.
- The message box is as tall as the text it draws (its own Text node, measured after each layout and when the text re-wraps: guessing from the font size cut lines), up to 40 % of the window, then scrolls (`ComposerHeightUiTest`). Notices (`MainView.toast`) sit just above the message box, never over it (`ToastPlacementUiTest`). The composer puts the text on its own line above the buttons when they'd leave it under 14 em (`Composer.stack`, decided in a runLater after the layout that changed the width: moved mid-layout, the frame kept the stacked height; `NotificationOpenUiTest`).
- The info panel's six actions are round icons (names in tooltips and for screen readers: mute, favorite, pin, archive, low priority and the chat's options), all in a row or three and three, never five and one (`ActionGrid` decides from the width it gets and says its height depends on it; a TilePane's insets and rounding gave 2-2-2 and 5-1; `InfoActionsLayoutUiTest`, `InfoActionsUiTest`); leaving the group or deleting the chat is in the options, on their own "Peligroso" tab ("General" has the everyday ones; both stay built, only one shows) and behind a second "yes", never at hand (`ChatOptionsUiTest`).
- The composer has one media button (the face): it opens the side panel on the media tab used last (`SidePanel.lastMediaTab`, `panel.mediaTab`, default Emojis); a sticker or GIF's right-click menu has "Ver en grande" (`LibraryMenu.enlarge`), in the side panel and, for a sticker, in the chat too (`MessageActionsUi`; the chat's "Ver" is only photos and videos). A plain key pressed outside a text box with a chat open writes in the composer (`WindowShortcuts.typeIntoComposer`, a handler so the timeline's own keys win). ⌘L (Ctrl+L) goes to the message box from anywhere. Every search box has a ✕ (`SearchFields`, out of the Tab order) and Esc empties it before closing what it's in. A message's menu (Enter on it) has what only the mouse could do: view its photo/video, go to the message it answers, open its links (`MessageActionsUi`).

## Lessons
- A reused empty `ListCell` kept the `:current` pseudo-class → a grey "selected" bar under the list. Reset pseudo-classes in the empty branch of `updateItem`.
- List cells must use `setPrefWidth(0)` so they size to the viewport instead of content: the timeline's `RowCell` missed it and, with the side panel open, one wide row stretched every cell and cut outgoing bubbles at the right edge.
- The stage and the app's singletons (`Transcripts`, the service) outlive a `MainView`: a language change or logout builds another on the same stage. Anything a view or pane registers on them is removed in its `dispose()` (keep the listener in a field): the old view kept marking its chat read on each focus and stayed in memory (`RelocalizeUiTest`, which waits for the old view to be collected).
- Links from messages opened through `HostServices.showDocument` with no check of the scheme: a `file:`, `smb:` or `ms-msdt:` link went to whatever handles it (a program run, the Windows password's hash sent). Every external link goes through `Browser.open`, which opens only `http`/`https` with a host (`BrowserTest`); never `showDocument` or `Desktop.browse` elsewhere.
- A coalesced redraw was written by hand four times (`AtomicBoolean` + `runLater`: `UploadBar`, `ExploreBar`, `CloakBar`, `ThreadPane`) and none counted in `Redraws.PENDING`, so `FxWait.settled` returned before it ran and a test measured the screen half-drawn (a flaky test). All go through `FxCoalescer` (`FxCoalescerUiTest`; lesson `fx-coalesce-by-hand`).
- A closed window keeps its scene (its window property never goes back to null), so anything that ends "when the node leaves its scene" never ended for a closed window: `Theme` kept every scene it styled (each photo viewer, video, toast and settings window ever opened, with all it drew), and animations (`AnimatedImage`, typing dots, the voice bar, inline video) ran on for good, held by JavaFX's timer and holding the animation budget. Work that should stop when nothing can see it goes through `Showing.whileShowing` (scene, window and its showing, followed together); `Theme` drops a scene when its window hides (`ThemeSceneUiTest`, `media/AnimationShowingUiTest`).
