# ui.emoji — notes for Claude

Emoji, reactions and the media library's palettes: `EmojiPicker`, `EmojiGrid` (+ `EmojiRows`, `EmojiSearch`), `EmojiArt`, `EmojiInline`, `ReactionEmoji`, `StickerGrid`, `GifGrid`, `FavoritesPane`, `LibraryMenu`, `MediaItems` (messages ↔ library items), `TileCache`. The list and names come from `src/main/resources/app/unichat/emoji/` and `native/emoji-list.py`.

- Picker (`EmojiPicker`, side panel `EmojiGrid`): Unicode's Emoji 15.0 list (`resources/app/unichat/emoji/emoji.txt`, made by `native/emoji-list.py` from the pinned emoji-test.txt; 1870 without skin-tone variants; 15.0 because macOS 13.3 draws no newer).
- JavaFX lays out flags, keycaps and ZWJ sequences in pieces (490 of them on a Mac), so `EmojiArt` measures which and draws those with Java2D (which joins them) as pictures, off the FX thread; one Java2D can't join either stays hidden. In messages, emoji JavaFX draws in pieces (any cluster of more than one character, measured once) are pictures inside the text (`EmojiInline` from `EmojiArt.segments`, `EmojiInlineUiTest`); the text box (a TextArea, plain text only) still shows them in pieces.
- The list is virtual (`EmojiGrid`, a `ListView` of rows from `EmojiRows`, pure): 1870 buttons at once scrolled at 110 ms a step, the virtual one at 35 (`EmojiScrollPerfUiTest`, `-Dunichat.perfTests=true`); columns follow the width of a real button (`probe`), every emoji button has one size in em so text and pictures line up, and the arrow keys move between emoji since those off screen have no button.
- The side panel's tab starts with Favoritos (a hint while empty: right-click → Agregar a favoritos) and Recientes (updated when the tab is shown, so nothing moves under the pointer); the reaction picker (`EmojiGrid.Mode.REACTIONS`) is the same list starting with the ones reacted with most. Both have a search box: Unicode's names and keywords in the language in use (`EmojiSearch`, `emoji/names_<lang>.txt` from CLDR by the same script, English for a language without; every word typed begins a word of the name, accents and case aside), ↓ goes to the emoji, Enter takes the first.
- Quick reactions (popup, message menu, keys 1–6) are the six the person reacts with most (`MediaLibrary.reacted` / `mostReacted`, in media-library.json, so they travel; the usual six fill in until there's history; taking a reaction away isn't a use; `QuickReactionsUiTest`). `EmojiPickerUiTest` (Mac: its emoji font; the headless platform uses the system's fonts too).
- Sticker and GIF grids keep their tiles (`TileCache`); their pictures and animations follow `ui/media/CLAUDE.md`.
- Telegram's sticker sets (`StickerSetSection` in `StickerGrid`): the person's sets (the bridge's `/v3/image_pack/list`) and any opened from a sticker's menu ("Ver el set de este sticker", from `fi.mau.bridged_sticker.pack_url`, `model/StickerPack.urlOf`). A set is fetched when first opened (`/v3/image_pack/import` with GET: a preview; POST would import it into the bridge's space) and kept a week in `cache/sticker-packs/` (`matrix/StickerPackCache`); its stickers keep the bridge's mark, so Telegram gets its own sticker and other networks a converted one, as with favourites. The demo has one set (`service/DemoStickers`; snapshot `-Dunichat.stickerSet=<link>`). `StickerSetsUiTest`, `StickerSetMenuUiTest`.

## Lessons
- JavaFX 21 rendered emoji monochrome → JavaFX 23+, with emoji font families forced on emoji-only controls.
- A set's name showed "otro_set" as "otroset": a Button parses `_` as its shortcut mark. Text that comes from a network (names, titles) goes in a control with `setMnemonicParsing(false)`.
- Telegram's sticker sets "didn't load": its bridge turns each animated sticker (Lottie or WebM) into a GIF as it's asked, 2–3 s and 5–9 MB each, with no thumbnail; a set of 50 was hundreds of MB, and the media cache (1 GB, files over 1 MB first) threw them out again and again. Stickers got their own cache (`matrix/CLAUDE.md`), and every tile shows its real progress and a way to try again (`ui/media/MediaLoading`). Measure a bridge's answer (size, time, `Content-Length`) before guessing why media is slow.
- Recents filled with copies of the same sticker: one sent as a converted copy (a GIF for Discord, a copy on our server) has another address, format and size and no bridge mark, so seen back in the chat (`rememberSeen`) it was a new recent, and the panel pushed the copy over the original. The copy's info names the item it came from (`MediaLibrary.ORIGINAL`, written by `matrix/MessageSender`), and `MediaItems.of` takes that original for one's own messages only (a stranger's can't name another sticker; `MediaItemsTest`).
- Favourite stickers kept what each was when saved: Telegram's video stickers as the GIF its bridge made then (before `convert_from_webm: false`), some without a size, so improvements to how stickers come never reached them. `service/FavoriteRefresh` rebuilds each from its set as the bridge gives it now (asked afresh, `StickerSets.freshStickerPack`, not the week's copy), in the same place (`MediaLibrary.replace`); one gone from its set or whose set can't be brought stays. The button beside "Favoritos" does it, and once by itself when a Telegram account is connected (`StickerGrid.rebuildOnce`, `library.favoritesRebuilt`, this computer's marker; done only when every set came) (`FavoriteRefreshTest`, `FavoritesRebuildUiTest`). What's saved from a network goes stale: keep a way to bring it again.
- At start Telegram's bridge isn't ready, so the first rebuild's sets all failed, and each change of an account tried them all again at once (11 failures in a minute; the log only said "CompletionException"). By itself a failed rebuild waits 10 minutes (`StickerGrid.RETRY_MS`), and the log gives the cause (`FavoritesRebuildUiTest.byItselfAFailedRebuildWaitsBeforeTryingAgain`). Something run "when an account changes" runs many times: give it its own pace.
- Only a GIF that came as a picture (`image/gif`) could be a favourite, and most don't: Telegram's and WhatsApp's come as an MP4 marked `fi.mau.gif`, Discord's gifv as a WebP so marked (180 MP4s against 17 GIFs in the real cache). Any GIF is one now (`MessageActions.isStickerOrGif` → `Message.isGif`, `MessageActionsTest`), its tile plays an MP4 as it does a WebM (`ImageHeaders.isVideo`, `VideoFrames` reads it as `Source.MP4`; `WebmStickerTileUiTest.aFavouriteGifThatIsAnMp4…`), and sent where the bridge would show a video (Discord) it goes as the animated WebP a forward makes (`MessageSender.sendGif`, `SendStickerTest.aSavedGifThatIsAnMp4…`). Count how a network really sends a thing before deciding what "a GIF" is.
