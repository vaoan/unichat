# Unichat — notes for Claude

Java 21 + JavaFX 23 desktop unified inbox over Matrix + mautrix bridges, inspired by Beeper (no code or assets of theirs). Maven via wrapper
(`./mvnw`); use `JAVA_HOME=/opt/homebrew/opt/openjdk@21` on this Mac. User-facing text through `support/I18n` (`I18n.t("key")`, `I18n.n` for counts): `src/main/resources/app/unichat/i18n/messages.properties` (English, the fallback) and
`messages_es.properties`; a new language is one more `messages_<code>.properties` (found by `I18n.available`, offered in Ajustes → Apariencia; `I18nTest` demands the same keys and placeholders in every file).
The language changes live (`UnichatApp.relocalize` rebuilds the window), so never keep a text in a `static final` or anything built once. Tests run in Spanish (`unichat.language=es` in the pom).
Everything in the repo is in **English** (README, docs, scripts, code, commits); `README.es.md` and `docs/PRIVACIDAD.md` are the Spanish translations of the README and `docs/PRIVACY.md` (SignPath's application links the latter), keep them in step. The app itself is bilingual. Must keep working on **Windows** (user's target).

## Layout
Package rules: `docs/ARCHITECTURE.md`, enforced by `ArchitectureTest` (no cycles, JavaFX only in `ui`, `ui` talks to `service`). Read it before adding a dependency between packages.
- `model/` — mutable `Chat`, `Message`, records `Member`, `Account`; `Network` maps each network to its bridge
  bot localpart / puppet prefix / protocol id (must match `server/setup.*`).
- `support/` — leaf utilities (`Os`, `Hashes`, `Redactor`, `BundledTools`, `Processes`, `Folders`, `Urls`, `Errors`). Use them instead of writing another: process timeouts, folder deletion and URL encoding had each drifted apart.
- `bridge/` — what `matrix` and `server` share about bridges (`BridgeStates`, `BridgePorts`).
- `service/ChatService` — the only API the UI uses (made of small role interfaces; take the narrowest one). Live model objects, listeners on any thread (UI marshals with
  `Platform.runLater`, coalesced in `MainView` by `ui/Throttle`). `MockChatService` = demo mode. `BridgeAccess` = what only bridge-backed services add.
- Data dir files: `preferences.json` (per-chat archived/muted/favorite/lowPriority/pinned + folders; `service/PreferencesFile`), `settings.properties`,
  `media-library.json` and `media-library/` (a copy of each favourite sticker/GIF, `matrix/SavedMedia`) and `writing-style.md` (how the person writes, for AI drafts) travel with the person (copy them to a new machine); `session.properties` (token, `matrix.*`, `server.*`, `window.*`; `Settings.staysOnThisMachine`
  decides, older keys migrate out of settings.properties) and `server-seen.json` stay. An older version will ask you to log in again, because the session moved to session.properties; nothing is lost. `preferences.json.bak` is the version before the last save, tried when the main file is damaged. Saves happen on a coalescing daemon thread (never on the caller's, which may be the UI or hold `proc`), so a test reading the file calls `flush()` first; `ChatSession.stop()` flushes, and quit, logout and a shutdown hook in `UnichatApp` all reach it. Preference rules (`matrix/RoomPreferences`): the file wins; a field the
  person never touched follows the server; a server false counts only if the same server (identity `homeserver|deviceId`) said true, so a fresh server doesn't
  erase copied choices. Only the mute rule still goes to the server (unread counts come from it). Chat identity across servers: `service/ChatKeys`,
  `<protocol>:<channel.id>`. `service/ChatFolders` is the role for folders (`FolderActions`, `FolderForwarding`); a folder can be a favorite (`Folder.favorite`, in preferences.json; its menu), shown at the end of the favorites row with a folder tile that opens it. Favorite tiles are one width in em, names centered and cut with "…" (`Formats.favoriteName`: the first word unless it's under 4 letters; `FavoritesRowUiTest`); `ui/FolderView` (+ `FolderRows`, `FolderDialogs`) shows them, each folder a row as tall as a chat's (tile, name, time and last message of its most recent chat).
- `matrix/` — `MatrixChatService` (facade: lifecycle, sync loop) over `MatrixCore` (shared), `MessageSender`, `ChatActions`,
  `BridgeAccounts`, `DiscordServers`, `ContactActions`, `MediaDownloader`, `SyncCache`, `MatrixLogin`; `SyncProcessor`
  (pure /sync → model, unit tested) with `RoomFields`, `SystemMessages`, `SyncEvents`; `BridgeProtocol` (pure), `BotChat`, `MatrixClient` (HTTP). `MatrixLiveIT` = end-to-end test, needs `UNICHAT_IT_HOMESERVER`.
- `ui/` — `MainView` (rail | `ChatListPane` | `ThreadPane` + `InfoPane`, overlays; keys, F6 and zoom in `WindowShortcuts`), `ChatListPane` (+ `ChatRowCell`, `SpaceChannelsView`), `ThreadPane` (+ `TimelineScroll`, `MessageRowView`, `MessageLine`), `Composer`,
  `CommandBar`, `AccountsPane` (+ `DiscordServersPage`, `LoadingView`), `SettingsWindow` (pages built with `SettingsForm`: `AppearancePages`, `PrivacyPage`, `NetworksPage`, `SpeechPage`, `AiReplyPage`), `Notifier` (AWT tray), `Theme`. Pure logic with tests: `A11yText` (what a screen reader and the voice say),
  `ChatFilter`, `ThreadRows`, `RichText`, `Formats`, `MediaSizes`, `LoginTexts`. Shared bits: `Nodes` (show, style), `Labels.help`, `Chips.sticky`, `Icons.iconButton`, `MediaTile`.
- Lists never `setAll` the same rows nor call `ListView.refresh()` on a data change (`ui/ListRows`): both pile every cell and hand them out again in another order, so each row draws another chat and the whole list repaints; rows redraw in place (`ListRows.Redrawable`). Redraws touch only what changed: each change redraws the visible rows (opening a chat marks it read), so a row (`ChatRowCell`) keeps its nodes and only toggles them (flag icons, account tag), `Avatar` keeps one network icon per network, `Rail` keeps its unread badges, the favorites row is rebuilt only when its chats change, and `Nodes.style` leaves classes alone when already so. `ListRepaintUiTest` checks it.
- `ui/InfoPane` is built again only when what it shows changes (`InfoPane.shown`): the window refreshes it on every message, and rebuilding blanked its photos (a flash).
- Timeline updates: `ThreadRows.update` touches only rows that differ (`MessageRow.revision`, from `Message.revision()`: a new drawn field must go in there), since replacing the whole list redraws all that's on screen; `ThreadPane.redraw` is for changes of appearance; `MainView` updates the open chat at most every 250 ms. `ScrollPerfUiTest` (`-Dunichat.perfTests=true`, real display, ffmpeg) prints before/after numbers for a giant chat; compare with the Mac under similar load, which moves them a lot.
- `css/app.css` — single stylesheet; light palette on `.root`, dark on `.root.dark`; `-accent` and font size
  set inline by `Theme`.
- `server/` — Synapse + Postgres + bridges docker-compose, `setup.sh` / `setup.ps1`. `docs/BRIDGES.md`.
- `native/` — no-Docker stack (tuwunel + mautrix bridge binaries + SQLite): `versions.env` pins every component,
  `setup-mac.sh` / `run-mac.sh` are the reference for the installer Unichat will run at startup (install whatever
  is missing, start and supervise). Read `docs/NATIVE-SERVER.md` before touching it.
  Bridges run with `direct_media` (`mxc://media-<bridge>.localhost/…`, nothing copied to the server); Unichat
  downloads those from the bridge's port (`LocalServer.directMediaBase`), and `matrix/MediaCache` caps `cache/media`
  (`cache.mediaMb`, LRU; files over 1 MB go first, saved stickers/GIFs are pinned, `MediaSource.keepCached`; one file per direct-media URL whatever the size). `model/MediaLibrary.same` says when two items are one sticker (bridge id, else format, dimensions and bytes), since direct media gives the same file a new URL in each message. Media grids keep their tiles (`ui/TileCache`) and `MessageMedia.loadMedia` shows what `AnimatedImage` already decoded at once. `server/MediaPrune` deletes Discord attachments older than `discord.mediaDays` (default 30, 0 = never; Ajustes →
  Redes) on each server start; avatars/emoji kept.
- Read receipts (`Settings.readReceipts`, Ajustes → Privacidad): ALWAYS sends `m.read` on opening a chat; ON_REPLY and NEVER send `m.read.private`, which tuwunel never passes to appservices, so the bridge never tells the network; ON_REPLY then sends a public `m.read` for the newest message of someone else just before each message we send (`MessageSender.readOnReply`). The person's phone app still marks read on its own.
- Bridges send `com.beeper.message_send_status` for each message (`BridgeConfig`: `message_status_events`, plus the error notice that says why); `SyncProcessor.applySendStatus` marks ours FAILED when the network refused it, so a message never looks sent when it wasn't.
- `server/LocalServer` runs the processes; `server/BridgeInstaller` leaves a bridge ready (download, config, setup processes; tests with a temp dir and `FakeService`), `server/ServerSecrets` holds the secrets file.
- Staying current: `support/WakeWatch` notices the computer waking (macOS stops awake time while asleep, so a long poll left open would wait out its timeout on a dead connection); `MatrixChatService.wake` drops it and catches up at once. The top bar (`MainView.showConnection`) says "Conectando…" until the server answered and "Sincronizando <redes>…" while a network's bridge reconnects (`AccountAlerts.syncingLine`); bridges never report when their backfill ends, so that's as far as Unichat can tell.
- `server/StatusEndpoint` + `BridgeStates` (bridges POST their account states, mautrix `status_endpoint`) feed
  `MatrixChatService.accounts()` and `ui/AccountAlerts` + `AccountAlertBar` (foot of the chat list, so chats don't jump); `server/Watchdog` restarts hung,
  stuck or flapping processes (awake time, backoff), and all but Meta's bridges when the internet returns; `server/MetaSessions` keeps Meta cookies safe from the bridge erasing them over a redirect (see docs/NATIVE-SERVER.md). Demo: `-Dunichat.demoAccounts=WHATSAPP:NEEDS_LOGIN,...`.
- macOS Dock: the package declares `LSUIElement` (package.sh), so by default there's no Dock icon, ⌘Tab or app menu; Ajustes → Notificaciones `app.showInDock` adds one while the window is open (`ui/DockIcon`), also forced if the menu bar icon is missing. ⌘Tab only lists apps with a Dock icon (macOS has no way around it), so `native/UnichatBar.swift` registers a global ⌃⌥U (`app.globalShortcut`, Carbon: no Accessibility permission) that brings the window back. `UnichatApp` handles ⌘Q itself, and activation with no window brings it back (`TrayReopen`). Don't build nodes while the window is hidden: nothing is drawn, so JavaFX never empties `Scene.dirtyNodes` and everything built stays in memory (`MainView.catchUp` brings it up to date on opening; only the menu bar count updates meanwhile).
- `native/UnichatBar.swift` (`native/build-bar.sh`) — macOS helper, built as `UnichatBar.app` (bundle id
  `app.unichat.helper`, shown as "Unichat"): the menu-bar item (narrower than Java's TrayIcon, real NSMenu; its icon is a template drawn there, `Bar.glyph`, so macOS colours it like its own; as in Telegram, a left click brings the window when it is put away or behind other apps (`Notifier.setWindowFocused`: no Unichat window has the focus) and opens the menu while it is open and focused, a right click or Control-click always opens it: minimize to tray or open, notifications off/on, quit) and
  **system notifications** (UNUserNotificationCenter needs a bundle; clicks come back as `open <chat id>`). Driven by
  `ui/NativeBar` over stdin (the unread count, `ChatFilter.inboxUnread` like the inbox badge, shows beside the icon, with a red dot on the icon's corner, a view of its own since the template icon can't keep a colour; the AWT tray draws it on the icon, `Notifier.withCount`); `Notifier` uses it when macOS allows notifications, else `DesktopToast` (own card, must
  never take keyboard focus), and the AWT TrayIcon if the helper is missing or dies. package.sh ships it as
  `Contents/app/native/UnichatBar.app`.
- Message HTML: `ui/HtmlView` draws `formatted_body` tag by tag, as a browser would (jsoup, so badly nested HTML reads the same), with no cases per network or bridge: Discord embeds are just HTML, and `matrix/MessageHtml` writes `com.beeper.linkpreviews` as HTML too. Pictures only from `mxc://`, links only http(s), no scripts or frames. `Message.body` stays plain text for lists, replies and editing (`withoutEmbedText` drops the "> " lines the bridge repeats an embed in). Discord's bridge drops the video of a rich embed, so `links/LinkInspector` opens each link when its message shows (`MediaSource.linkMedia`; at most 5 per message) and asks the server what it is, or the page's `og:video`; `MessageMedia.linkPlayers` shows it. Those links come from anyone: no cookies, and every hop refuses this machine and its network; `MediaDownloader` fetches all web addresses through it too. A browser's User-Agent gets redirected by FixupX, hence "compatible". Ajustes → Privacidad → Conexiones can turn it off (`privacy.linkPreviews`, checked in `MediaDownloader.linkMedia`).
- Video: `Message.playsInline` decides by what the bridge reports (GIF flag, video stickers, or up to 2 MB and 15 s); `ui/InlineVideo` (muted loop in the timeline, a native player only while on screen, none with reduced motion), `ui/VideoViewer` (window; downloads on opening) with `ui/VideoControls` (±10 s, volume, speed, repeat, watch again, full screen with controls that hide while playing, always on top, save the video or the frame; YouTube's keys: K J L, ←→ ↑↓, M, F, < >, , ., Home/End, digits). javafx-media comes with javafx-web; WebM it can't play goes through `video/WebmStickers` (ffmpeg to animated WebP or, if that ffmpeg lacks the encoder like Homebrew's, GIF; cached in `cache/media`; `video/Ffmpeg` uses the person's own or downloads a pinned build on first use, `video.ffmpegAuto`, Ajustes → Redes), `VideoViewer` converts other unreadable videos to H.264 (`video/VideoTranscoder`), and what still can't play falls back to a file chip and the system player. Trust the file, not its label: a sticker labelled `video/webm` may be delivered as a GIF; `.mov` is cached as `.mp4` because JavaFX refuses that name. Reels that arrive as a picture + `external_url` open their page (`Message.isReelLink`).
- Photos: `ui/MediaViewer` (window and controls; steps through the chat's pictures with ← → / Page Up/Down and the side buttons, `ui/Gallery`: photos and pictures sent as documents, which open there too; the arrows pan while zoomed in; F full screen, Esc leaves it then closes) over `ui/PhotoPane` (mouse) and `ui/PhotoZoom` (pure: scale, turn, position). Animated GIF/WebP stay decoded at up to 1600 px, so real size there is the decoded one. A still WebP over 3 MP (a phone's photo) is never decoded in Java: TwelveMonkeys takes ~25 bytes/pixel, 600 MB+ for 24 MP; `video/BigPictures` makes a 1600 px PNG with `sips` (Mac) or ffmpeg, cached (`AnimatedImage.isBigWebp`, read from the header).
- Audio: `ui/AudioPlayback` (one per window: starting another stops it; survives changing chats), shown by `AudioControls` in the message and in `AudioBar` on top. JavaFX refuses Ogg/Opus: `stt/PlayableAudio` makes a 48 kHz WAV once (`OggOpus.toPlayableWav`; 16 kHz is only for Whisper).
- Sending files: the clip opens a menu (`Composer.attachMenu`: file, photos/videos, document = `m.file` whatever it is, many files, or many photos = a batch as `PHOTO`), each a `service/SendAs`. Photos (`PHOTO`) are made into what networks show as a photo: Telegram's bridge sends as a file any picture over ~16.7 MP (`image_as_file_pixels`), 10 MB or 10,000 px of width + height, i.e. every phone photo, and WebP/HEIC are photos nowhere; `matrix/OutgoingPhotos` + `video/SendablePhotos` make a JPEG of at most 2560 px with sips or ffmpeg (in `cache/sending`, kept a day), JPEG/PNG within those limits go as they are, GIFs and videos untouched, a failed conversion sends the original. A picture's size comes from its header (`support/ImageHeaders`), never by decoding it. Several files (or a drop of several) go through `service/UploadQueue`, one per service so it survives `relocalize`: one at a time, in order, a pause between them (bridges take bursts as spam). Reliable: a file that fails is tried again for as long as it takes (30 s doubling to 5 min; only a file gone from disk is given up), and the batch is kept in `uploads.json` (`uploads-demo.json` for the demo; this computer's paths, so it stays) and resumes after a restart. A file to a bridged chat is done when the bridge's `com.beeper.message_send_status` says the network has it (`matrix/SendStatuses`, 5 min patience), not when our server does: sending on before that piled hundreds of uploads in Telegram's bridge, all lost when its connection dropped; `ui/UploadBar` shows it on top like `AudioBar`. Upload progress comes from `matrix/UploadProgress` counting the request body. `-Dunichat.upload=<file>,<file>` (snapshot; `-Dunichat.uploadAs=PHOTO|DOCUMENT`) sends a batch to the open chat. A file in the chat shows a picture instead of its icon when it has one (`ui/FilePreview`: the attached `thumbnail_url`, else the file itself if it's a picture up to 15 MB).
- Sending voice notes: `voice/` records from `Microphone` (Java Sound) and encodes Ogg/Opus in pure Java (`VoiceEncoder`, Concentus; `OggOpusWriter`); `ui/VoiceBar` replaces the composer row while recording. `voice/VoiceEnhancer` (`voice.enhance`) cleans the raw recording before sending with ffmpeg (highpass, RNNoise `arnndn`, speechnorm), downloading ffmpeg and the pinned model on first use; any failure sends it as recorded. Measure changes to the filter with speech (`say`), not tones: RNNoise leaves a tone alone. `VoiceEnhancerTest` does with `-Dunichat.networkTests=true`. `RoomFeatures.voiceSend` says, per chat, the MIME (WhatsApp needs `audio/ogg; codecs=opus`) or null (no mic). A Mac without permission hands over pure silence, not an error: `VoiceBar` detects it.
- Login steps asking for request headers (LinkedIn): `LoginWebView.openCapturing` watches the page's own XHR/fetch headers through a script and builds the Cookie header from the cookie store (`BridgeCookies.captured`); LinkedIn cancels a session used under another browser's identity within seconds (mautrix/linkedin#61: its bridge always says Chrome 141/Linux), so cookies from the person's own browser don't work, and Google refuses embedded windows. So `login/ChromeLogin` opens their real Chrome on a throwaway profile (on a Mac through `open`: a child process would have its permissions charged to Unichat, and passkeys on the phone need Bluetooth), uses a chosen debugging port (port 0 makes `navigator.webdriver` true and Google refuses), gives only the site's tab the bridge's identity over the debugging port (`Emulation.setUserAgentOverride`, client hints included; Google's popup is another tab, unattached, because Google rejects a browser that contradicts itself), reads the cookies once the feed loads and deletes the profile (`-Dunichat.chromeTests=true` runs it for real, off screen); the window remains for email and password, and stops waiting for headers after 8 s (`BridgeCookies.headerFallbacks`).
- `assist/` + `ui/AiReplyButton`, `AiReplyPage` — AI reply drafts, and correcting what's written (`FixPrompt`: only that text goes, no chat, instructions or folder; undoable with ⌘Z), through the person's own `claude` or `codex` (`AiEngine`, prompt on stdin, `ai.*` settings, off by default). Only ever text in the composer, never sent by itself. A draft is one call to the program, so it's fast (~5 s; ~17 s when it searches the web): the voice notes it answers (`ReplyPrompt.voiceNotesToHear`: the chosen one and the newest since my last message, at most 6; `ai.voiceNotes`, on by default) are transcribed ahead, when the chat opens or one arrives (`Composer.hearAhead`, `Transcripts.requestAhead`, which never retries a failure), and `AiReplyButton.heard` only waits for what's left (3 minutes in all); they go in the prompt as their text, so `AiReplyButton.Request` carries a supplier, run off the UI thread. The draft uses how the person writes as learned so far; learning (`ai.learnStyle`, on by default) comes after each draft, in the background (`Composer.learnAfter`, one at a time, ~10 s): when there's something new (corrections or newer messages of mine in the chat), `assist/StyleLearner` has the same program update `writing-style.md` (`StylePrompt`: at most 40 bullets / 3 000 characters, told to it with the file's current size, style only, nobody else's data; an answer only too long is sent back once to be shortened (`StylePrompt.shorten`), any other failure keeps the old file and the log says why (`StylePrompt.problem`); 2 minutes), from my last 30 messages and the pending corrections (`WritingStyle`: `writing-style-corrections.json`, last 20, from `DraftCorrections`, the draft put in a chat's box against what was sent there). While it searches the web the working line says so (`aiButton.searchingWeb`). Drafts and fixes (⌘O) carry the file; Ajustes → Escribir con IA shows and edits it. A finished draft or fix plays a short sound (`assist/ReadySound`, synthesized in Java so Windows sounds the same; `ai.readySound` CHIME|SOFT|BELL|OFF, `ai.readyVolume` 0–100; never on a failure or cancel; surefire sets `unichat.silent`). From anywhere in the window ⌘I writes and ⌘O corrects (`Composer.aiKeyPressed`), leaving the focus in the text box; the info panel is ⌘⇧I. Chats are written by others and can carry instructions: keep the CLI's tools minimal (`AiEngine.command`: Claude reads only the chosen folder, tested by `ReplyWriterTest` with `-Dunichat.networkTests=true`) and never log the prompt.
- `stt/` — voice notes to text: `Transcriber` runs whisper.cpp's `whisper-cli` (`native/build-whisper.sh` on Mac,
  pinned official zip in package.ps1; shipped in `app/server/whisper/`) or the user's own command (`CommandLine`);
  `OggOpus` decodes Opus at 48 kHz then low-passes to 16 kHz (Concentus returns silence for the first CELT frames
  at 16 kHz); `WhisperModel` downloads the pinned model on first use; `Transcripts` caches per media URL.
  Claude Code / Codex CLIs can't take audio (tested), so they aren't engines.
- `native/build-gif2webp.sh` — libwebp's `gif2webp` built from pinned sources (with GIFLib; Google's Mac binary needs macOS 15) and shipped in `app/server/` (Windows: Google's build, pinned in package.ps1);
  `matrix/StickerConverter` uses it when a chat's room_features refuse a sticker's MIME (GIF → WebP on WhatsApp), keeping `fi.mau.bridged_sticker` when the sticker is the chat's own network's (`MessageSender.ownSticker`): Telegram's bridge first rejects a type the chat doesn't take (image/gif), then sends the original from its pack; without the mark it passes the file through its ffmpeg, which fails without a WebP encoder (Homebrew's).
  Ajustes → Redes (`<network>.animatedStickers` = STICKER|GIF|VIDEO) can send them as mp4 instead (`GifFrames` +
  JCodec, pure Java).
- `THIRD-PARTY.md` — generated by `native/third-party.py` (rerun when a dependency or pinned version changes); shipped
  with `LICENSE` in the packages. Unichat's own code is 0BSD.
- Code signing (Windows): applied to SignPath Foundation's free OSS program (README «Code signing policy», required wording and roles; every release page links it from build.yml). Their terms: whatever reaches a system the person didn't choose is in docs/PRIVACY.md, shown before installing (`packaging/install-notice.txt`, the .msi's license page; keep it true when adding a connection) and can be turned off in Ajustes. Once approved: their GitHub Action (`signpath/github-action-submit-signing-request`) in build.yml's windows job, with the secret `SIGNPATH_API_TOKEN`, their organization id and project/policy slugs, signing the zip's contents and the .msi before release; product name "Unichat" and the pom's version must match (`--name`, `--app-version`). macOS isn't covered: notarizing needs an Apple Developer account.
- macOS minimum: `MACOS_MIN` in package.sh (13.3, whisper-cli's), passed to every native build (swiftc otherwise targets the Mac it runs on) and written to Info.plist; `native/check-macos-min.sh` fails the package if any binary inside needs more.
- `package.sh` / `package.ps1` — jpackage, version read from the pom; `.github/workflows/build.yml` builds Windows zip/msi + macOS dmg, and a tag `v<pom version>` publishes them as a GitHub release (a `-suffix` tag is a pre-release, which the update check skips).
- Version: the pom's, read at run time from the filtered `version.properties` (`support/AppVersion`; "dev" when unfiltered, never offered an update). `update/UpdateChecker` asks GitHub's latest release once a day (`app.checkUpdates`, Ajustes → Privacidad; `app.update.*` stay on this machine), `ui/UpdateBar` says so at the foot of the chat list; any failure is one log line. Ajustes → Acerca de (`ui/AboutPage`): check now, open the logs folder, copy an error report (`support/ErrorReport`: version, system and the log's last lines, redacted again). Cuentas → Agregar cuenta warns that networks don't authorize bridges.
- `.github/workflows/natives.yml` — what has no official build: tuwunel for both platforms and the bridges for Windows (cross-compiled from Linux with MinGW, `-tags goolm`; Discord's legacy bridge also `nocrypto` and a newer zeroconfig), published as the release `NATIVES` in `versions.env` names; `NATIVES_UNBUILT` (Signal) is what Windows can't offer (`Manifest.builds`). Bump `NATIVES` with any version change. `native/fetch-natives.sh` and package.ps1 put its tuwunel in the app. Users download from it, which is why the repository is public (since 2026-11-09).

## Checking UI changes
`-Dunichat.snapshot=out.png` (`SnapshotRun`) writes the window to a PNG and exits; combine with `-Dunichat.dataDir=<dir>` (put
`session.backend=demo` and optionally `ui.theme=LIGHT` in `<dir>/settings.properties`),
`-Dunichat.openChat=<id>` (demo ids like `!familia:demo`), `-Dunichat.openSpace=<id>` (a server's channels, e.g. `!servidor:demo`), `-Dunichat.info=true`, `-Dunichat.panel=EMOJIS|STICKERS|GIFS`,
`-Dunichat.overlay=command|newchat|add|folderNew|folderDelete|settings:<Página>`, `-Dunichat.openFolders=true` (folder list), `-Dunichat.openFolder=<name>` (inside one), `-Dunichat.network=<protocolo>` (settings snapshots the settings window).
Run via `JAVA_OPTS=... ./run-dev.sh`, then read the PNG. Do this after every visual change.

## Accessibility (user requirement — keep it working)
Settings → Accesibilidad (`a11y.*` keys); `Theme` adds `contrast`, `strong-focus`, `wide-spacing` root classes and
follows OS high contrast / reduced motion. Every new control needs an accessible text (icon buttons get it from
`Icons.iconButton`), keyboard reachability, and must survive 160 % text + high contrast. Icons grow with the text (`Icons.SCALE`, set by `Theme`): give paddings that make room for one in `em`, and check alignment with `-Dunichat.snapshotScale=2` and `ui.fontScale=1.6`. The composer puts the text on its own line above the buttons when they'd leave it under 14 em (`Composer.stack`, decided in a runLater after the layout that changed the width: moved mid-layout, the frame kept the stacked height; `NotificationOpenUiTest`); the info panel's four actions go two by two rather than cut. The composer has one media button (the face): it opens the side panel on the media tab used last (`SidePanel.lastMediaTab`, `panel.mediaTab`, default Emojis); a sticker or GIF's right-click menu has "Ver en grande" (`LibraryMenu.enlarge`). A plain key pressed outside a text box with a chat open writes in the composer (`WindowShortcuts.typeIntoComposer`, a handler so the timeline's own keys win). ⌘L (Ctrl+L) goes to the message box from anywhere. Every search box has a ✕ (`ui/SearchFields`, out of the Tab order) and Esc empties it before closing what it's in. A message's menu (Enter on it) has what only the mouse could do: view its photo/video, go to the message it answers, open its links (`MessageActionsUi`). `KeyboardUiTest`
(`-Dunichat.uiTests=true`, needs a display) checks F6 zones, timeline keys, zoom and screen-reader texts;
`FilterUiTest` (same flag) checks that the rail keeps the chosen chip when switching network. `./mvnw verify -Pheadless-ui` runs them with no display or windows (Monocle); `AudioUiTest`, `ReactionEmojiUiTest` and `NetworkSettingsUiTest` still need a display (`-Dunichat.uiTests=true`): JavaFX stops under Monocle there. It proves logic, not focus, tray or Dock.

## Rules
- KISS, DRY, SOLID (`docs/ARCHITECTURE.md`). Java files stay under 800 lines, methods under 100 (Checkstyle fails the build); split by responsibility.
- Run `./mvnw verify` before committing (tests, architecture rules, copied code). Never point tests at the real data dir (surefire sets `unichat.dataDir`).
- Nothing from Beeper's app (proprietary): no code, icons, texts or other assets.
- See `.claude/mistakes.md` before touching CSS sizing, icons, AWT/tray or Javadoc.
