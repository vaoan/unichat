# Unichat — notes for Claude

Java 25 + JavaFX 27 desktop unified inbox over Matrix + mautrix bridges, inspired by Beeper (no code or assets of theirs). Maven via wrapper
(`./mvnw`); use `JAVA_HOME=/opt/homebrew/opt/openjdk@25` on this Mac (JavaFX 27 needs Java 25). User-facing text through `support/I18n` (`I18n.t("key")`, `I18n.n` for counts): `src/main/resources/app/unichat/i18n/messages.properties` (English, the fallback) and
`messages_es.properties`; a new language is one more `messages_<code>.properties` (found by `I18n.available`, offered in Ajustes → Apariencia; `I18nTest` demands the same keys and placeholders in every file).
The language changes live (`UnichatApp.relocalize` rebuilds the window), so never keep a text in a `static final` or anything built once. Tests run in Spanish (`unichat.language=es` in the pom).
Everything in the repo is in **English** (README, docs, scripts, code, commits); `README.es.md` and `docs/PRIVACIDAD.md` are the Spanish translations of the README and `docs/PRIVACY.md` (SignPath's application links the latter), keep them in step. The app itself is bilingual. Must keep working on **Windows** (user's target).

## Layout
Package rules: `docs/ARCHITECTURE.md`, enforced by `ArchitectureTest` (no cycles, JavaFX only in `ui`, `ui` talks to `service`). Read it before adding a dependency between packages.
- `model/` — mutable `Chat`, `Message`, records `Member`, `Account`; `Network` maps each network to its bridge
  bot localpart / puppet prefix / protocol id (must match `server/setup.*`).
- `support/` — leaf utilities (`Os`, `Hashes`, `Redactor`, `BundledTools`, `Processes`, `Folders`, `Urls`, `Errors`). Use them instead of writing another: process timeouts, folder deletion and URL encoding had each drifted apart.
- `bridge/` — what `matrix` and `server` share about bridges (`BridgeStates`, `BridgePorts`).
- `service/ChatService` — the only API the UI uses (made of small role interfaces; take the narrowest one). Live model objects, listeners on any thread (UI marshals with
  `Platform.runLater`, coalesced in `MainView` by `ui/Throttle`). `MockChatService` = demo mode. `BridgeAccess` = what only bridge-backed services add.
- Data dir files: `preferences.json` (per-chat archived/muted/favorite/lowPriority/pinned + folders; `service/PreferencesFile`), `settings.properties`,
  `media-library.json` and `media-library/` (a copy of each favourite sticker/GIF, `matrix/SavedMedia`) and `writing-style.md` (how the person writes, for AI drafts) travel with the person (copy them to a new machine); `session.properties` (token, `matrix.*`, `server.*`, `window.*`; `Settings.staysOnThisMachine`
  decides, older keys migrate out of settings.properties) and `server-seen.json` stay. An older version will ask you to log in again, because the session moved to session.properties; nothing is lost. `preferences.json.bak` is the version before the last save, tried when the main file is damaged. Saves happen on a coalescing daemon thread (never on the caller's, which may be the UI or hold `proc`), so a test reading the file calls `flush()` first; `ChatSession.stop()` flushes, and quit, logout and a shutdown hook in `UnichatApp` all reach it. Preference rules (`matrix/RoomPreferences`): the file wins; a field the
  person never touched follows the server; a server false counts only if the same server (identity `homeserver|deviceId`) said true, so a fresh server doesn't
  erase copied choices. Only the mute rule still goes to the server (unread counts come from it). Chat identity across servers: `service/ChatKeys`,
  `<protocol>:<channel.id>`. `service/ChatFolders` is the role for folders (`FolderActions`, `FolderForwarding`); a folder can be a favorite (`Folder.favorite`, in preferences.json; its menu), shown at the end of the favorites row with a folder tile that opens it. The favorites are one row, never wider than the column nor scrolled (`ui/FavoritesRow`: tiles narrow down to the avatar's width, then the last place is "+N" and opens the Favorites view). Favorite tiles are up to 4.4 em wide, names centered and cut with "…" (`Formats.favoriteName`: the first word unless it's under 4 letters; `FavoritesRowUiTest`); `ui/FolderView` (+ `FolderRows`, `FolderDialogs`) shows them, each folder a row as tall as a chat's (tile, name, time and last message of its most recent chat).
- `matrix/` — `MatrixChatService` (facade: lifecycle, sync loop) over `MatrixCore` (shared), `MessageSender`, `ChatActions`,
  `BridgeAccounts`, `DiscordServers`, `ContactActions`, `MediaDownloader`, `SyncCache`, `MatrixLogin`; `SyncProcessor`
  (pure /sync → model, unit tested) with `RoomFields`, `SystemMessages`, `SyncEvents`; `BridgeProtocol` (pure), `BotChat`, `MatrixClient` (HTTP). `MatrixLiveIT` = end-to-end test, needs `UNICHAT_IT_HOMESERVER`.
- `ui/` — `MainView` (rail | `ChatListPane` | `ThreadPane` + `InfoPane`, overlays; keys, F6 and zoom in `WindowShortcuts`), `ChatListPane` (+ `ChatRowCell`, `SpaceChannelsView`), `ThreadPane` (+ `TimelineScroll`, `MessageRowView`, `MessageLine`), `Composer`,
  `CommandBar`, `AccountsPane` (+ `DiscordServersPage`, `LoadingView`), `SettingsWindow` (pages built with `SettingsForm`: `AppearancePages`, `PrivacyPage`, `NetworksPage`, `SpeechPage`, `AiReplyPage`), `Notifier` (AWT tray), `Theme`. Pure logic with tests: `A11yText` (what a screen reader and the voice say),
  `ChatFilter`, `ThreadRows`, `RichText`, `Formats`, `MediaSizes`, `LoginTexts`. Shared bits: `Nodes` (show, style), `Labels.help`, `Chips.sticky`, `Icons.iconButton`, `MediaTile`.
- Lists never `setAll` the same rows nor call `ListView.refresh()` on a data change (`ui/ListRows`): both pile every cell and hand them out again in another order, so each row draws another chat and the whole list repaints; rows redraw in place (`ListRows.Redrawable`). Redraws touch only what changed: each change redraws the visible rows (opening a chat marks it read), so a row (`ChatRowCell`) keeps its nodes and only toggles them (flag icons, account tag), `Avatar` keeps one network icon per network, `Rail` keeps its unread badges, the favorites row is rebuilt only when its chats change, and `Nodes.style` leaves classes alone when already so. `ListRepaintUiTest` checks it.
- `ui/InfoPane` is built again only when what it shows changes (`InfoPane.shown`): the window refreshes it on every message, and rebuilding blanked its photos (a flash).
- Following the newest message (`ui/TimelineScroll`): the person going towards older messages (wheel/trackpad up, ↑ PgUp Home, dragging the thumb up) stops it at once; it follows again only when the newest message is wholly in view, in pixels; a growing photo decides nothing. No time windows nor "near the bottom" fractions: 0.2 % of a long chat is hundreds of pixels and pulled the person back down (`AutoScrollUiTest.aSmallScrollUpInALongChatIsNotUndone`).
- Timeline updates: `ThreadRows.update` touches only rows that differ (`MessageRow.revision`, from `Message.revision()`: a new drawn field must go in there), since replacing the whole list redraws all that's on screen; `ThreadPane.redraw` is for changes of appearance; `MainView` updates the open chat at most every 250 ms. `ScrollPerfUiTest` (`-Dunichat.perfTests=true`, the real display: only the person runs it; ffmpeg) prints before/after numbers for a giant chat; compare with the Mac under similar load, which moves them a lot.
- `css/app.css` — single stylesheet; light palette on `.root`, dark on `.root.dark`; `-accent` and font size
  set inline by `Theme`.
- `server/` — Synapse + Postgres + bridges docker-compose, `setup.sh` / `setup.ps1`. `docs/BRIDGES.md`.
- `native/` — no-Docker stack (tuwunel + mautrix bridge binaries + SQLite): `versions.env` pins every component,
  `setup-mac.sh` / `run-mac.sh` are the reference for the installer Unichat will run at startup (install whatever
  is missing, start and supervise). Read `docs/NATIVE-SERVER.md` before touching it.
  Bridges run with `direct_media` (`mxc://media-<bridge>.localhost/…`, nothing copied to the server); Unichat
  downloads those from the bridge's port (`LocalServer.directMediaBase`), and `matrix/MediaCache` caps `cache/media`
  (`cache.mediaMb`, LRU; files over 1 MB go first, saved stickers/GIFs are pinned, `MediaSource.keepCached`; one file per direct-media URL whatever the size). `model/MediaLibrary.same` says when two items are one sticker (bridge id, else format, dimensions and bytes), since direct media gives the same file a new URL in each message. An animation over `AnimatedImage.MAX_ANIMATION_BYTES` first loses resolution, down to its size on screen (`shrinkToKeep`), and only then frames: dropping them halved a sticker's frame rate. Media grids keep their tiles (`ui/TileCache`) and `MessageMedia.loadMedia` shows what `AnimatedImage` already decoded at once. `server/MediaPrune` deletes Discord attachments older than `discord.mediaDays` (default 30, 0 = never; Ajustes →
  Redes) on each server start; avatars/emoji kept.
- Read receipts (`Settings.readReceipts`, Ajustes → Privacidad): ALWAYS sends `m.read` on opening a chat; ON_REPLY and NEVER send `m.read.private`, which tuwunel never passes to appservices, so the bridge never tells the network; ON_REPLY then sends a public `m.read` for the newest message of someone else just before each message we send (`MessageSender.readOnReply`). The person's phone app still marks read on its own.
- Formatting what's sent: WhatsApp's marks (`*bold*`, `_italic_`, `~strike~`, `` `code` ``, ```` ``` ```` blocks, `> ` quotes) plus Discord's `__underline__` and `||spoiler||` become `formatted_body` (`model/Markup`, pure; nothing inside a word, code or a link), which each bridge writes its network's way; with no marks the message is plain text as before. The box's right-click menu (`ui/FormatMenu`, ⌘B ⌘U ⌘⇧X) offers only what the chat's bridge lists in `formatting` (`RoomFeatures.formats`) and wraps or unwraps the selection (`model/TextFormat`).
- Bridges send `com.beeper.message_send_status` for each message (`BridgeConfig`: `message_status_events`, plus the error notice that says why); `SyncProcessor.applySendStatus` marks ours FAILED when the network refused it, so a message never looks sent when it wasn't.
- `server/LocalServer` runs the processes; `server/BridgeInstaller` leaves a bridge ready (download, config, setup processes; tests with a temp dir and `FakeService`), `server/ServerSecrets` holds the secrets file.
- Staying current: `support/WakeWatch` notices the computer waking (macOS stops awake time while asleep, so a long poll left open would wait out its timeout on a dead connection); `MatrixChatService.wake` drops it and catches up at once. The top bar (`MainView.showConnection`) says "Conectando…" until the server answered and "Sincronizando <redes>…" while a network's bridge reconnects (`AccountAlerts.syncingLine`); bridges never report when their backfill ends, so that's as far as Unichat can tell.
- `server/StatusEndpoint` + `BridgeStates` (bridges POST their account states, mautrix `status_endpoint`) feed
  `MatrixChatService.accounts()` and `ui/AccountAlerts` + `AccountAlertBar` (foot of the chat list, so chats don't jump); `server/Watchdog` restarts hung,
  stuck or flapping processes (awake time, backoff), and all but Meta's bridges when the internet returns; `server/MetaSessions` keeps Meta cookies safe from the bridge erasing them over a redirect (see docs/NATIVE-SERVER.md). Demo: `-Dunichat.demoAccounts=WHATSAPP:NEEDS_LOGIN,...`.
- macOS Dock: the package declares `LSUIElement` (package.sh), so by default there's no Dock icon, ⌘Tab or app menu; Ajustes → Notificaciones `app.showInDock` adds one while the window is open (`ui/DockIcon`), also forced if the menu bar icon is missing. ⌘Tab only lists apps with a Dock icon (macOS has no way around it), so any window besides the main one (photo, video, settings) also brings the Dock icon while open (`DockIcon.regular`), and ⌘` / ⌘⇧` (also ⌘< on a Spanish keyboard) moves between Unichat's windows (`ui/AppWindows`; macOS gives that only to apps with a Window menu); a menu that opens activates Unichat and focuses its window (`ui/MenuDismiss`): a right-click on a window of a background app shows the menu without activating it, and then neither a click outside nor Esc reached JavaFX (`MenuDismissUiTest`, the real mouse and keyboard); so `native/UnichatBar.swift` registers a global ⌃⌥U (`app.globalShortcut`, Carbon: no Accessibility permission) that brings the window back. `UnichatApp` handles ⌘Q itself, and activation with no window brings it back (`TrayReopen`). Don't build nodes while the window is hidden: nothing is drawn, so JavaFX never empties `Scene.dirtyNodes` and everything built stays in memory (`MainView.catchUp` brings it up to date on opening; only the menu bar count updates meanwhile).
- `native/UnichatBar.swift` (`native/build-bar.sh`) — macOS helper, built as `UnichatBar.app` (bundle id
  `app.unichat.helper`, shown as "Unichat"): the menu-bar item (narrower than Java's TrayIcon, real NSMenu; its icon is a template drawn there, `Bar.glyph`, so macOS colours it like its own; as in Telegram, a left click brings the window when it is put away or behind other apps (`Notifier.setWindowFocused`: no Unichat window has the focus) and opens the menu while it is open and focused, a right click or Control-click always opens it: minimize to tray or open, notifications off/on, quit) and
  **system notifications** (UNUserNotificationCenter needs a bundle; clicks come back as `open <chat id>`). Driven by
  `ui/NativeBar` over stdin (the unread count, `ChatFilter.inboxUnread` like the inbox badge, shows beside the icon, with a red dot on the icon's corner, a view of its own since the template icon can't keep a colour; the AWT tray draws it on the icon, `Notifier.withCount`); `Notifier` uses it when macOS allows notifications, else `DesktopToast` (own card, must
  never take keyboard focus), and the AWT TrayIcon if the helper is missing or dies. package.sh ships it as
  `Contents/app/native/UnichatBar.app`.
- Message HTML: `ui/HtmlView` draws `formatted_body` tag by tag, as a browser would (jsoup, so badly nested HTML reads the same), with no cases per network or bridge: Discord embeds are just HTML, and `matrix/MessageHtml` writes `com.beeper.linkpreviews` as HTML too. Pictures only from `mxc://`, links only http(s), no scripts or frames. `Message.body` stays plain text for lists, replies and editing (`withoutEmbedText` drops the "> " lines the bridge repeats an embed in). Discord's bridge drops the video of a rich embed, so `links/LinkInspector` opens each link when its message shows (`MediaSource.linkMedia`; at most 5 per message) and asks the server what it is, or the page's `og:video`; `MessageMedia.linkPlayers` shows it. Those links come from anyone: no cookies, and every hop refuses this machine and its network; `MediaDownloader` fetches all web addresses through it too. A browser's User-Agent gets redirected by FixupX, hence "compatible". Ajustes → Privacidad → Conexiones can turn it off (`privacy.linkPreviews`, checked in `MediaDownloader.linkMedia`).
- Video: `Message.playsInline` decides by what the bridge reports (GIF flag, video stickers, or up to 2 MB and 15 s); `ui/InlineVideo` (muted loop in the timeline, a native player only while on screen, none with reduced motion), `ui/VideoViewer` (window; downloads on opening) with `ui/VideoControls` (±10 s, volume, speed, repeat, watch again, full screen with controls that hide while playing, always on top, save the video or the frame; YouTube's keys: K J L, ←→ ↑↓, M, F, < >, , ., Home/End, digits). javafx-media comes with javafx-web; WebM it can't play goes through `video/WebmStickers` (ffmpeg to animated WebP or, if that ffmpeg lacks the encoder like Homebrew's, GIF; cached in `cache/media`; `video/Ffmpeg` uses the person's own or downloads a pinned build on first use, `video.ffmpegAuto`, Ajustes → Redes), `VideoViewer` converts other unreadable videos to H.264 (`video/VideoTranscoder`), and what still can't play falls back to a file chip and the system player. Trust the file, not its label: a sticker labelled `video/webm` may be delivered as a GIF; `.mov` is cached as `.mp4` because JavaFX refuses that name. Reels that arrive as a picture + `external_url` open their page (`Message.isReelLink`).
- Photos: `ui/MediaViewer` (window and controls; steps through the chat's pictures with ← → / Page Up/Down and the side buttons, `ui/Gallery`: photos and pictures sent as documents, which open there too; the arrows pan while zoomed in; F full screen, Esc leaves it then closes) over `ui/PhotoPane` (mouse) and `ui/PhotoZoom` (pure: scale, turn, position). Animated GIF/WebP stay decoded at up to 1600 px, so real size there is the decoded one. A still WebP over 3 MP (a phone's photo) is never decoded in Java: TwelveMonkeys takes ~25 bytes/pixel, 600 MB+ for 24 MP; `video/BigPictures` makes a 1600 px PNG with `sips` (Mac) or ffmpeg, cached (`AnimatedImage.isBigWebp`, read from the header).
- Audio: `ui/AudioPlayback` (one per window: starting another stops it; survives changing chats), shown by `AudioControls` in the message and in `AudioBar` on top. JavaFX refuses Ogg/Opus: `stt/PlayableAudio` makes a 48 kHz WAV once (`OggOpus.toPlayableWav`; 16 kHz is only for Whisper).
- Sending files: pasting (⌘V in the box, or anywhere with a chat open, `WindowShortcuts`) sends copied files as they are and a copied picture (a browser's "Copy image") as a `PHOTO`, saved as a PNG in `cache/sending` (`ui/Pasting`: files win over text, text over a picture). The clip opens a menu (`Composer.attachMenu`: file, photos/videos, document = `m.file` whatever it is, many files, or many photos = a batch as `PHOTO`), each a `service/SendAs`. Photos (`PHOTO`) are made into what networks show as a photo: Telegram's bridge sends as a file any picture over ~16.7 MP (`image_as_file_pixels`), 10 MB or 10,000 px of width + height, i.e. every phone photo, and WebP/HEIC are photos nowhere; `matrix/OutgoingPhotos` + `video/SendablePhotos` make a JPEG of at most 2560 px with sips or ffmpeg (in `cache/sending`, kept a day), JPEG/PNG within those limits go as they are, GIFs and videos untouched, a failed conversion sends the original. A picture's size comes from its header (`support/ImageHeaders`), never by decoding it. Several files (or a drop of several) go through `service/UploadQueue`, one per service so it survives `relocalize`: one at a time, in order, a pause between them (bridges take bursts as spam). Reliable: a file that fails is tried again for as long as it takes (30 s doubling to 5 min; only a file gone from disk is given up), and the batch is kept in `uploads.json` (`uploads-demo.json` for the demo; this computer's paths, so it stays) and resumes after a restart. A file to a bridged chat is done when the bridge's `com.beeper.message_send_status` says the network has it (`matrix/SendStatuses`, 5 min patience), not when our server does: sending on before that piled hundreds of uploads in Telegram's bridge, all lost when its connection dropped; `ui/UploadBar` shows it on top like `AudioBar`. Upload progress comes from `matrix/UploadProgress` counting the request body. `-Dunichat.upload=<file>,<file>` (snapshot; `-Dunichat.uploadAs=PHOTO|DOCUMENT`) sends a batch to the open chat. A file in the chat shows a picture instead of its icon when it has one (`ui/FilePreview`: the attached `thumbnail_url`, else the file itself if it's a picture up to 15 MB).
- Protected photos (clip → "Foto protegida contra IA…", `ui/CloakSend` + `CloakBar`, `cloak/`): Mist's textural attack written anew (Mist is GPL, Unichat 0BSD: no code of theirs), `resources/app/unichat/cloak/cloak.py`: PGD on Stable Diffusion 1.x's image encoder only (34M parameters; the encoder alone was checked against the original to 6e-5) toward Mist's target pattern, in tiles of at most 256 px at up to 768 px per side, so memory stays ~1.5 GB whatever the picture (the person's hard limit is 4 GB: the script stops itself past it, `check_memory`). The full Mist (with the diffusion network) needs ~12 GB and didn't fit an 8 GB Mac. `CloakLevel` LIGHT/MEDIUM/STRONG = 10/30/100 steps (~3/8/25 min on an M1). `cloak/CloakTool` installs on first use into `<data>/tools/cloak/`: pinned uv, which brings Python 3.12 and `requirements.txt` (exact versions with hashes, `--require-hashes --no-build`, regenerate with `uv pip compile --generate-hashes --exclude-newer <2 weeks ago>`), plus the encoder weights (Hugging Face) and `MIST.png` (GitHub), both pinned; bump `CloakTool.VERSION` when any of it changes. `cloak/CloakJob`: one at a time for the app, cancellable; the result goes as a `DOCUMENT` through `UploadQueue`. Only Apple-chip Macs and 64-bit Windows (PyTorch has no Intel Mac build). `CloakToolTest` with `-Dunichat.networkTests=true` installs for real and protects a picture.
- Emoji picker (`ui/EmojiPicker`, side panel `ui/EmojiGrid`): Unicode's Emoji 15.0 list (`resources/app/unichat/emoji/emoji.txt`, made by `native/emoji-list.py` from the pinned emoji-test.txt; 1870 without skin-tone variants; 15.0 because macOS 13.3 draws no newer). JavaFX lays out flags, keycaps and ZWJ sequences in pieces (490 of them on a Mac), so `ui/EmojiArt` measures which and draws those with Java2D (which joins them) as pictures, off the FX thread; one Java2D can't join either stays hidden. The list is virtual (`ui/EmojiGrid`, a `ListView` of rows from `ui/EmojiRows`, pure): 1870 buttons at once scrolled at 110 ms a step, the virtual one at 35 (`EmojiScrollPerfUiTest`, `-Dunichat.perfTests=true`); columns follow the width of a real button (`probe`), every emoji button in it has one size in em so text and pictures line up, and the arrow keys move between emoji since those off screen have no button. The side panel's tab starts with Favoritos (a hint while empty: right-click → Agregar a favoritos) and Recientes (updated when the tab is shown, so nothing moves under the pointer); the reaction picker (`EmojiGrid.Mode.REACTIONS`) is the same list starting with the ones reacted with most. Both have a search box: Unicode's names and keywords in the language in use (`ui/EmojiSearch`, `emoji/names_<lang>.txt` from CLDR by the same script, English for a language without; every word typed begins a word of the name, accents and case aside), ↓ goes to the emoji, Enter takes the first. The quick reactions (popup, message menu, keys 1–6) are the six the person reacts with most (`MediaLibrary.reacted` / `mostReacted`, in media-library.json, so they travel; the usual six fill in until there's history; taking a reaction away isn't a use; `QuickReactionsUiTest`). In messages, emoji JavaFX draws in pieces (flags, joined ones, skin tones: any cluster of more than one character, measured once) are pictures inside the text (`ui/EmojiInline` from `EmojiArt.segments`, `EmojiInlineUiTest`); the text box (a TextArea, plain text only) still shows them in pieces. `EmojiPickerUiTest` (Mac: its emoji font; the headless platform uses the system's fonts too). Messages and the text box still draw those emoji with JavaFX, in pieces.
- Saving everything a chat receives (`autosave/AutoSave`, the profile's "Guardar todo lo que envíen", `ChatPreferences.setAutoSave` = `PreferencesFile.Flag.AUTO_SAVE`, Unichat's own: no server says it): every message from someone else as it arrives (`ChatService.Listener.received`, muted chats too, never bot chats; not history), so view-once and timed ones are kept. Media but stickers (`FileNames.forMessage`, the same names as "Guardar como…", never overwriting: `FileNames.free`), and the video behind each link (`support/Urls.in`) with `video/YtDlp` (pinned, downloaded on first use like ffmpeg; one video, never the playlist, up to 1080p, the link after `--`). One at a time on its own thread, into `~/Downloads/Unichat/<chat>/` (`-Dunichat.autosaveDir`; surefire points it into target/).
- Sending voice notes: `voice/` records from `Microphone` (Java Sound) and encodes Ogg/Opus in pure Java (`VoiceEncoder`, Concentus; `OggOpusWriter`); `ui/VoiceBar` replaces the composer row while recording. `voice/VoiceEnhancer` (`voice.enhance`) cleans the raw recording before sending with ffmpeg (highpass, RNNoise `arnndn`, speechnorm), downloading ffmpeg and the pinned model on first use; any failure sends it as recorded and says so. Two ffmpeg passes, noise then volume: chained in one, Homebrew's ffmpeg 9 never finished some notes (output stuck at 2^20 samples); each pass may take 15 s plus twice the note's length. While it works the composer shows "Preparando la nota de voz… N s" (`ui/WorkingLine`). Measure changes to the filter with speech (`say`), not tones: RNNoise leaves a tone alone. `VoiceEnhancerTest` does with `-Dunichat.networkTests=true`. `RoomFeatures.voiceSend` says, per chat, the MIME (WhatsApp needs `audio/ogg; codecs=opus`) or null (no mic). A Mac without permission hands over pure silence, not an error: `VoiceBar` detects it.
- Login steps asking for request headers (LinkedIn): `LoginWebView.openCapturing` watches the page's own XHR/fetch headers through a script and builds the Cookie header from the cookie store (`BridgeCookies.captured`); LinkedIn cancels a session used under another browser's identity within seconds (mautrix/linkedin#61: its bridge always says Chrome 141/Linux), so cookies from the person's own browser don't work, and Google refuses embedded windows. So `login/ChromeLogin` opens their real Chrome on a throwaway profile (on a Mac through `open`: a child process would have its permissions charged to Unichat, and passkeys on the phone need Bluetooth), uses a chosen debugging port (port 0 makes `navigator.webdriver` true and Google refuses), gives only the site's tab the bridge's identity over the debugging port (`Emulation.setUserAgentOverride`, client hints included; Google's popup is another tab, unattached, because Google rejects a browser that contradicts itself), reads the cookies once the feed loads and deletes the profile (`-Dunichat.chromeTests=true` runs it for real, off screen); the window remains for email and password, and stops waiting for headers after 8 s (`BridgeCookies.headerFallbacks`).
- `assist/` + `ui/AiReplyButton`, `AiReplyPage` — AI reply drafts, and correcting what's written (`FixPrompt`: only that text goes, no chat, instructions or folder; undoable with ⌘Z), through the person's own `claude` or `codex` (`AiEngine`, prompt on stdin, `ai.*` settings, off by default). Only ever text in the composer, never sent by itself; it goes in as an edit (`replaceText`, not `setText`, which forgets the undo history), so ⌘Z brings back what was written before it (`DraftUndoUiTest`): a draft built on it can still change what the person meant. A draft is one call to the program, so it's fast (~5 s; ~17 s when it searches the web): the voice notes it answers (`ReplyPrompt.voiceNotesToHear`: the chosen one and the newest since my last message, at most 6; `ai.voiceNotes`, on by default) are transcribed ahead, when the chat opens or one arrives (`Composer.hearAhead`, `Transcripts.requestAhead`, which never retries a failure), and `AiReplyButton.heard` only waits for what's left (3 minutes in all); they go in the prompt as their text, so `AiReplyButton.Request` carries a supplier, run off the UI thread. The prompt also says when it is now (day, time and time zone) and how long ago the last message was (`ReplyPrompt.when`), so a late reply doesn't sound instant. The draft uses how the person writes as learned so far; learning (`ai.learnStyle`, on by default) comes after each draft, in the background (`Composer.learnAfter`, one at a time, ~10 s): when there's something new (corrections or newer messages of mine in the chat), `assist/StyleLearner` has the same program update `writing-style.md` (`StylePrompt`: at most 40 bullets / 3 000 characters, told to it with the file's current size, style only, nobody else's data; an answer only too long is sent back once to be shortened (`StylePrompt.shorten`), any other failure keeps the old file and the log says why (`StylePrompt.problem`); 2 minutes), from my last 30 messages and the pending corrections (`WritingStyle`: `writing-style-corrections.json`, last 20, from `DraftCorrections`, the draft put in a chat's box against what was sent there). While it searches the web the working line says so (`aiButton.searchingWeb`). Drafts and fixes (⌘O) carry the file; Ajustes → Escribir con IA shows and edits it. A finished draft or fix plays a short sound (`assist/ReadySound`, synthesized in Java so Windows sounds the same; `ai.readySound` CHIME|SOFT|BELL|OFF, `ai.readyVolume` 0–100; never on a failure or cancel; surefire sets `unichat.silent`). From anywhere in the window ⌘I writes and ⌘O corrects (`Composer.aiKeyPressed`), leaving the focus in the text box; the info panel is ⌘⇧I. Chats are written by others and can carry instructions: keep the CLI's tools minimal (`AiEngine.command`: Claude reads only the chosen folder, tested by `ReplyWriterTest` with `-Dunichat.networkTests=true`) and never log the prompt.
- `stt/` — voice notes to text: `Transcriber` runs whisper.cpp's `whisper-cli` (`native/build-whisper.sh` on Mac,
  pinned official zip in package.ps1; shipped in `app/server/whisper/`) or the user's own command (`CommandLine`);
  `OggOpus` decodes Opus at 48 kHz then low-passes to 16 kHz (Concentus returns silence for the first CELT frames
  at 16 kHz); `WhisperModel` downloads the pinned model on first use; `Transcripts` caches per media URL.
  Claude Code / Codex CLIs can't take audio (tested), so they aren't engines.
- `native/build-gif2webp.sh` — libwebp's `gif2webp` (and `anim_dump`, which `video/AnimDump` runs to decode animated WebP: TwelveMonkeys gets some lossy frames' colours wrong, black blotches; it's the fallback) built from pinned sources (with GIFLib; Google's Mac binary needs macOS 15) and shipped in `app/server/` (Windows: Google's build, pinned in package.ps1);
  `matrix/StickerConverter` uses it when a chat's room_features refuse a sticker's MIME (GIF → WebP on WhatsApp), keeping `fi.mau.bridged_sticker` when the sticker is the chat's own network's (`MessageSender.ownSticker`): Telegram's bridge first rejects a type the chat doesn't take (image/gif), then sends the original from its pack; without the mark it passes the file through its ffmpeg, which fails without a WebP encoder (Homebrew's).
  Ajustes → Redes (`<network>.animatedStickers` = STICKER|GIF|VIDEO) can send them as mp4 instead (`GifFrames` +
  JCodec, pure Java).
- `THIRD-PARTY.md` — generated by `native/third-party.py` (rerun when a dependency or pinned version changes); shipped
  with `LICENSE` in the packages. Unichat's own code is 0BSD.
- Code signing (Windows): applied to SignPath Foundation's free OSS program (README «Code signing policy», required wording and roles; every release page links it from build.yml). Their terms: whatever reaches a system the person didn't choose is in docs/PRIVACY.md, shown before installing (`packaging/install-notice.txt`, the .msi's license page; keep it true when adding a connection) and can be turned off in Ajustes. `session.backend=demo` and optionally `ui.theme=LIGHT` in `<dir>/settings.properties`),

## Accessibility (user requirement — keep it working)
Settings → Accesibilidad (`a11y.*` keys); `Theme` adds `contrast`, `strong-focus`, `wide-spacing` root classes and
follows OS high contrast / reduced motion. Every new control needs an accessible text (icon buttons get it from
`Icons.iconButton`), keyboard reachability, and must survive 160 % text + high contrast. Icons grow with the text (`Icons.SCALE`, set by `Theme`): give paddings that make room for one in `em`, and check alignment with `-Dunichat.snapshotScale=2` and `ui.fontScale=1.6`. The message box is as tall as the text it draws (its own Text node, measured after each layout and when the text re-wraps: guessing from the font size cut lines), up to 40 % of the window, then scrolls (`ComposerHeightUiTest`). Notices (`MainView.toast`) sit just above the message box, never over it (`ToastPlacementUiTest`). The composer puts the text on its own line above the buttons when they'd leave it under 14 em (`Composer.stack`, decided in a runLater after the layout that changed the width: moved mid-layout, the frame kept the stacked height; `NotificationOpenUiTest`); the info panel's four actions go two by two rather than cut. The composer has one media button (the face): it opens the side panel on the media tab used last (`SidePanel.lastMediaTab`, `panel.mediaTab`, default Emojis); a sticker or GIF's right-click menu has "Ver en grande" (`LibraryMenu.enlarge`). A plain key pressed outside a text box with a chat open writes in the composer (`WindowShortcuts.typeIntoComposer`, a handler so the timeline's own keys win). ⌘L (Ctrl+L) goes to the message box from anywhere. Every search box has a ✕ (`ui/SearchFields`, out of the Tab order) and Esc empties it before closing what it's in. A message's menu (Enter on it) has what only the mouse could do: view its photo/video, go to the message it answers, open its links (`MessageActionsUi`). `KeyboardUiTest`
(in `-Pheadless-ui`) checks F6 zones, timeline keys, zoom and screen-reader texts;
`FilterUiTest` (same flag) checks that the rail keeps the chosen chip when switching network. `./mvnw verify -Pheadless-ui` runs them with no display or windows (JavaFX's own headless platform, `-Dglass.platform=Headless`, since JavaFX 25; Monocle was never published past JavaFX 21); All of them run there (Audio, ReactionEmoji and NetworkSettings, which stopped under Monocle, too). Its virtual screen is a fixed 1000×1000 and a window drawn outside it (moved off-screen, or taller than the rest) throws on every frame, on the UI thread, into whatever test comes next: keep test windows on it, hidden with opacity 0, and close them when done. It proves logic, not focus, tray or Dock.

## Rules
- Nothing ever runs on the person's screen: no window, focus, mouse or keyboard of theirs while they work. UI tests run with `-Pheadless-ui`, snapshots are headless by themselves. A test that needs the real display (`MenuDismissUiTest`: the real mouse, macOS activating the app) sits behind its own flag (`-Dunichat.realInputTests=true`) and only the person runs it.
- All code is SOLID, DRY and KISS (`docs/ARCHITECTURE.md`): one responsibility per class, nothing written twice (reuse or extract what exists), the simplest thing that works. Java files stay under 800 lines, methods under 100 (Checkstyle fails the build); split by responsibility.
- Every fix comes with a test that fails without it (watch it fail first), and every feature with tests of what it does.
- Tests never wait for a length of time nor carry a timeout of their own: no `Thread.sleep`, no `await(5, SECONDS)`, `poll(200, MILLISECONDS)`, `join(5000)`, `waitFor(30, …)` or `get(30, …)`. They wait on what the code actually does: a latch or future the code completes, a listener, `FxWait.until` / `FxWait.settled` on screen, the code's own `flush()`. JUnit's global timeout (junit-platform.properties) is the only limit. To check that something did *not* happen, first wait for the point where it would have (flush, settled, the call that would have caused it returned). If the code gives no way to know when it's done, change the code so it does (a listener, a returned future, a flush) rather than guess a time. A time the code under test takes as input is given as zero or as no limit (`Duration.ZERO` with a program that never ends shows the timeout path; `NO_LIMIT` when it ends by itself), never a guess of how long something takes. The one timed pause allowed is a profiler's sampling rate (`ScrollPerfUiTest`'s sampler): it measures, it doesn't wait.
- A flaky test is a bug, never tolerated nor retried away: find the race and fix it (usually a wait on time, or work still running when the test ends: wait for it).
- Run `./mvnw verify` before committing (tests, architecture rules, copied code). Never point tests at the real data dir (surefire sets `unichat.dataDir`).
- Nothing from Beeper's app (proprietary): no code, icons, texts or other assets.
- See `.claude/mistakes.md` before touching CSS sizing, icons, AWT/tray or Javadoc.
